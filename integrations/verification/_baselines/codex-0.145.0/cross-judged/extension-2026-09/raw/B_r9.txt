## Workflow | 工作流程

> 📖 以下為流程的**參考結構**，非可執行步驟；自動化／強制執行請用 adoption layer 工具鏈（XSPEC-095）。
> The steps below are a **reference structure**, not an executable workflow.

1. **Identify changes** - Get diff of files to review via `git diff` or `git show`
2. **Apply checklist** - Check each review category systematically
3. **Generate report** - Output findings with standard comment prefixes
4. **Summarize** - Provide overall assessment and recommended actions

## Review Categories | 審查類別

1. **Functionality** - Does it work correctly? | 功能是否正確？
2. **Design** - Is the architecture appropriate? | 架構是否合適？
3. **Quality** - Is the code clean and maintainable? | 程式碼是否乾淨可維護？
4. **Readability** - Is it easy to understand? | 是否容易理解？
5. **Tests** - Is there adequate test coverage? | 測試覆蓋是否足夠？
6. **Security** - Are there any vulnerabilities? | 是否有安全漏洞？
7. **Performance** - Is it efficient? | 是否有效率？
8. **Error Handling** - Are errors handled properly? | 錯誤處理是否妥當？

## Purpose

This skill provides systematic checklists for code review and pre-commit verification.

## Quick Reference

### Comment Prefixes

| Prefix | Meaning | Action Required |
|--------|---------|------------------|
| **❗ BLOCKING** | Must fix before merge | 🔴 Required |
| **⚠️ IMPORTANT** | Should fix, but not blocking | 🟡 Recommended |
| **💡 SUGGESTION** | Nice-to-have improvement | 🟢 Optional |
| **❓ QUESTION** | Need clarification | 🔵 Discuss |
| **📝 NOTE** | Informational, no action | ⚪ Informational |

### Review Checklist Categories

1. **Functionality** - Does it work?
2. **Design** - Right architecture?
3. **Quality** - Clean code?
4. **Readability** - Easy to understand?
5. **Tests** - Adequate coverage?
6. **Security** - No vulnerabilities?
7. **Performance** - Efficient?
8. **Errors** - Properly handled?
9. **Docs** - Updated?
10. **Dependencies** - Necessary?

### Pre-Commit Checklist

- [ ] Build succeeds (zero errors, zero warnings)
- [ ] All tests pass
- [ ] Code follows project standards
- [ ] No security vulnerabilities
- [ ] Documentation updated
- [ ] Branch synced with target

## Detailed Guidelines

For complete standards, see:
- [Review Checklist](./review-checklist.md)
- [Pre-Commit Checklist](./checkin-checklist.md)

## Example Review Comments

```markdown
❗ BLOCKING: Potential SQL injection vulnerability here.
Please use parameterized queries instead of string concatenation.

⚠️ IMPORTANT: This method is doing too much (120 lines).
Consider extracting validation logic to a separate method.

💡 SUGGESTION: Consider using a Map here instead of an array for O(1) lookup.

❓ QUESTION: Why are we using setTimeout here instead of async/await?

📝 NOTE: This is a clever solution! Nice use of reduce here.
```

## Core Principles

1. **Be Respectful** - Review code, not the person
2. **Be Thorough** - Check functionality, not just syntax
3. **Be Timely** - Review within 24 hours
4. **Be Clear** - Explain WHY, not just WHAT

  - "Feature incomplete (would break functionality)"

  - "Build failures"

  - "Incomplete features"

ideal_size:

  lines: "50-300"

split_principle:

## 1. Functionality

- [ ] **Code does what it's supposed to do**
  - Requirement/spec alignment verified
  - Acceptance criteria met
  - Edge cases handled

- [ ] **No obvious bugs**
  - Null/undefined checks present
  - Array bounds checked
  - Error conditions handled

- [ ] **Logic is correct**
  - Conditions make sense
  - Loops terminate properly
  - Calculations are accurate

---

## 2. Design & Architecture

- [ ] **Follows project architecture**
  - Layering respected
  - Separation of concerns maintained
  - Dependency direction correct

- [ ] **Appropriate design patterns used**
  - Not over-engineered
  - Not under-engineered
  - Patterns applied correctly

- [ ] **Code is in the right place**
  - Files organized logically
  - Related code grouped together

---

## 3. Code Quality

- [ ] **Follows coding standards**
  - Naming conventions adhered to
  - Formatting consistent
  - Style guide followed

- [ ] **No code smells**
  - Methods ≤50 lines
  - Classes have single responsibility
  - Cyclomatic complexity ≤10
  - No deeply nested conditionals (≤3 levels)

- [ ] **DRY principle applied**
  - No duplicated code blocks
  - Common logic extracted

---

## 4. Readability

- [ ] **Code is easy to understand**
  - Variable names are descriptive
  - Function names reveal intent
  - Logic flows naturally

- [ ] **Comments are helpful**
  - Complex logic explained
  - WHY documented, not WHAT
  - No commented-out code

---

## 5. Testing

- [ ] **Tests are present**
  - New code has tests
  - Tests cover happy path
  - Tests cover error cases
  - Edge cases tested

- [ ] **Tests are good quality**
  - Tests are readable
  - Test names describe scenarios
  - Assertions are clear
  - No flaky tests

- [ ] **Test coverage maintained**
  - Coverage not decreased
  - Critical paths covered

---

## 6. Security

- [ ] **No security vulnerabilities**
  - No SQL injection risks
  - No XSS vulnerabilities
  - No hardcoded secrets
  - No insecure dependencies

- [ ] **Input validation present**
  - User input sanitized
  - Type checking performed
  - Size limits enforced

- [ ] **Auth/Authorization correct**
  - Proper auth checks
  - Role-based access enforced
  - Sensitive data protected

---

## 7. Performance

- [ ] **No obvious performance issues**
  - No N+1 queries
  - No unnecessary loops
  - No blocking operations in hot paths

- [ ] **Efficient algorithms used**
  - Complexity considered
  - Appropriate data structures
  - Caching where beneficial

- [ ] **Resource management proper**
  - Connections closed
  - Memory leaks prevented
  - File handles released

---

## 8. Error Handling

- [ ] **Errors handled appropriately**
  - Try-catch blocks present
  - Specific exceptions caught
  - Generic catch avoided

- [ ] **Error messages helpful**
  - Messages are descriptive
  - Actionable information included
  - No sensitive data exposed

- [ ] **Logging is adequate**
  - Errors logged with context
  - Log levels appropriate
  - No excessive logging

---

## 9. Documentation

- [ ] **API documentation present**
  - Public methods documented
  - Parameters explained
  - Return values described
  - Exceptions documented

- [ ] **README updated if needed**
  - New features documented
  - Setup instructions current

- [ ] **CHANGELOG updated (if applicable)**
  - User-facing changes added to `[Unreleased]`
  - Breaking changes marked with **BREAKING**

---

## 10. Dependencies

- [ ] **Dependencies justified**
  - New dependencies necessary
  - License compatible
  - No security vulnerabilities
  - Actively maintained

- [ ] **Dependency versions locked**
  - Exact versions specified
  - Lock file updated

## Findings

- ❗ **BLOCKING** — Database credentials are hard-coded in source at [checkout.js:3](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:3). This exposes production access to everyone with repository access. Revoke/rotate this password and load credentials from a secret manager or environment configuration.

- ❗ **BLOCKING** — The connection has no `database` configured ([checkout.js:3](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:3)). A newly created MySQL connection has no selected database, so the unqualified `products` and `orders` queries will fail unless this is configured elsewhere—which this connection does not inherit.

- ❗ **BLOCKING** — Client-controlled `uid` is persisted as the order owner ([checkout.js:24](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:24)). An authenticated customer can submit another user’s ID and create orders under that account. Derive it from authenticated server-side identity.

- ❗ **BLOCKING** — Stock is decremented without checking availability ([checkout.js:14](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:14), [checkout.js:17](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:17)). The fetched `stock` is never used, allowing negative inventory and overselling.

- ❗ **BLOCKING** — The read/decrement sequence is race-prone ([checkout.js:14](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:14)-[checkout.js:17](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:17)). Concurrent checkouts can both observe stock and both decrement it. Use a transaction with row locking, or an atomic conditional update (`… WHERE stock >= ?`) and check affected rows.

- ❗ **BLOCKING** — Cart input is not validated ([checkout.js:10](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:10)-[checkout.js:17](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:17)). Negative quantities increase stock and can create a negative total; fractional, zero, malformed, oversized, or non-array carts also produce invalid inventory changes or uncaught exceptions.

- ❗ **BLOCKING** — Checkout mutations are not atomic ([checkout.js:13](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:13)-[checkout.js:24](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:24)). A failure after one stock update leaves prior inventory changes committed, and an order can be inserted after only some items are reserved. Wrap reservation and order creation in a DB transaction with rollback.

- ❗ **BLOCKING** — The payment charge is fire-and-forget ([checkout.js:26](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:26)-[checkout.js:31](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:31)). The API reports a successful order before knowing whether payment was accepted; failures become unhandled rejections and leave an unpaid order/reserved stock. Persist payment state and use a transactional outbox/job with retries and idempotency.

- ⚠️ **IMPORTANT** — Missing product IDs cause `p.price` to throw ([checkout.js:15](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:15)), potentially after earlier inventory changes have already committed.

- ⚠️ **IMPORTANT** — There is no error handling around database or payment operations. In Express 4, a rejected async handler is not automatically forwarded to error middleware; the request can hang and failures are not translated to safe client responses.

- ⚠️ **IMPORTANT** — Monetary totals are calculated with JavaScript floating point ([checkout.js:16](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:16), [checkout.js:21](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:21)). This can charge/store values such as `27.599999999`; use integer minor units or a decimal-money library and define rounding.

- ⚠️ **IMPORTANT** — The payment request lacks explicit JSON headers and any visible authentication/idempotency token ([checkout.js:26](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:26)). Many payment APIs will reject it or parse the body incorrectly; retries without idempotency can double-charge.

- ⚠️ **IMPORTANT** — A single long-lived `createConnection` is shared globally ([checkout.js:3](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:3)). It has no pooling or recovery strategy, so a dropped connection can take down all subsequent checkouts.

- 💡 **SUGGESTION** — Each cart item causes a separate select and update ([checkout.js:13](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:13)-[checkout.js:17](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:17)). Large carts incur N+1 sequential round trips. Batch-fetch products and reserve inventory efficiently.

- 💡 **SUGGESTION** — `fmt` throws for any truthy non-string `x` ([checkout.js:35](/private/tmp/claude-502/-Users-alberthsu-Documents-GitHub-AsiaOstrich-dev-platform/6e8cec64-003b-4359-b385-60b4f94661ca/scratchpad/codex-extend/work-B_r9/src/checkout.js:35)). Validate its contract or coerce deliberately.

No tests are present, including for insufficient stock, concurrent checkout, invalid input, missing products, payment failure, and discount/rounding boundaries.

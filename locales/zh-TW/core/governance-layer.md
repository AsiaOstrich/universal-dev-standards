# 治理層標準

> **語言**: [English](../../../core/governance-layer.md) | 繁體中文

**版本**: 1.1.0
**最後更新**: 2026-08-20
**適用範圍**: 所有具有多 Agent 或多角色 AI 工作流程的軟體專案
**範疇**: universal
**產業標準**: 無（UDS 原創）

---

## 目的

治理層為專案中所有 Agent 與角色提供共同錨點：
Vision（方向）→ Mission（邊界 + 紅線）→ Goals（可量測的 KPI）。

它是 **Standard #0**：在所有其他標準之前評估。當本標準與其他領域標準發生衝突時，本標準優先。

---

## 三層架構

### Vision（願景）

| 欄位 | 要求 |
|------|------|
| 格式 | 單一句子，≤ 50 tokens |
| 內容 | 長期方向；永恆不變；不含量測指標 |
| 變更頻率 | 每年審查 |

**範例**：
> "成為全球軟體團隊最值得信賴的 AI 開發工作流程標準。"

---

### Mission（使命）

| 欄位 | 要求 |
|------|------|
| 格式 | 3–5 項承諾陳述 + 紅線清單（合計 ≤ 300 tokens） |
| 內容 | 我們做什麼 / 不做什麼；含觸發條件與處置動作的紅線 |
| 變更頻率 | 每季審查 |

**紅線必備欄位**：

| 欄位 | 型別 | 說明 |
|------|------|------|
| `id` | 字串 | 唯一識別碼（例如：R1、GUARD-001） |
| `category` | 字串 | 分類（quality / safety / compliance / ethics） |
| `clause` | 字串 | 人類可讀的禁止或要求陳述 |
| `action` | 列舉 | `block` \| `warn` \| `escalate_to_human` 之一 |

---

### Goals（目標）

| 欄位 | 要求 |
|------|------|
| 格式 | KPI 清單，≤ 500 tokens |
| 變更頻率 | 每個 Sprint 校準 |
| 可否證性 | 每個 KPI 必須可量測——禁止使用「改善」、「提升」等模糊詞彙 |

**KPI 必備欄位**：

| 欄位 | 型別 | 說明 |
|------|------|------|
| `id` | 字串 | 唯一識別碼（例如：KPI-01） |
| `metric_name` | 字串 | 追蹤的指標名稱 |
| `threshold` | 字串 | 量化目標（例如：≥ 95%、< 200 ms） |
| `measurement_method` | 字串 | 量測方式與時機 |

---

## 優先順序

治理層對所有其他標準具有**更高優先權**。衝突時的解析順序：

1. **治理層**（本標準）— 方向、紅線、KPI
2. **領域標準**（測試、提交訊息、部署等）
3. **專案特定覆寫**（本地 `.standards/` 客製化）

---

## 紅線格式

每條紅線必須包含所有必備欄位。執行動作說明：

| 動作 | 行為 |
|------|------|
| `block` | 立即停止 pipeline；不繼續執行 |
| `warn` | 記錄違規並繼續；超過閾值時升級 |
| `escalate_to_human` | 暫停並要求人類決策後才繼續 |

此外，每條紅線應包含 `mission_clause_ref` 欄位，參照其所強制執行的使命承諾。

---

## 評估器整合

當專案使用 AI 評估器 Agent 時，治理層提供評分錨點：

| 評估軸 | 權重 | 否決閾值 |
|--------|------|----------|
| 正確性 | 0.4 | < 0.3 → 不通過 |
| 使命對齊度 | 0.3 | < 0.3 → 不通過 |
| 目標達成度 | 0.3 | < 0.3 → 不通過 |

- **mission_alignment_score**：輸出與使命承諾的對齊程度
- **goal_achievement_score**：輸出推進目標 KPI 的程度
- 任何單一評估軸低於 0.3 即觸發不通過，無論加權總分為何

## 風險接受（trace_only 模式）

若專案放寬人工閘門（例如 `gate.mode = trace_only`），必須在 `mission.md` 中明確撰寫**風險接受條款**，包含：

| 必填欄位 | 說明 |
|----------|------|
| `date` | 接受風險的日期 |
| `signatory` | 接受風險的人員或角色 |
| `gates_bypassed` | 列舉所有繞過的人工閘門 |
| `risks_accepted` | 明確描述已接受的風險 |
| `review_by` | 本次接受失效、必須重新做一次判斷的日期 |

若無有效的風險接受條款，pipeline **必須拒絕啟動（fail-closed）**。

### 接受到期

`review_by` 已過的條款**不是有效條款**。pipeline 必須 fail closed，與完全沒有條款時一模一樣。

`date` 記錄的是「何時接受了這個風險」，不是「何時該重新判斷」。沒有 `review_by`，簽過一次的接受就永遠有效——當初支持它的條件可能已經改變、簽署人可能已經離開專案，而條款裡每一個欄位讀起來仍然完全正確。

到期時，必須施用且只能施用下列三種處置之一，與[技術債標準 → 到期處置](tech-debt-standards.md#到期處置)所定義的三種相同：

| 處置 | 意義 |
|------|------|
| **重新接受** | 由當下的簽署人重新簽署，並給出新的 `review_by` |
| **撤銷** | 移除該繞過，恢復人工閘門 |
| **延期** | 新的 `review_by` **與**書面理由，一起記下 |

**禁止自動延長 `review_by`。** 那會把一道 fail-closed 的閘門變成 fail-open，而所有欄位看起來都還是對的——失效之所以隱形，正是因為條款仍然驗證得過。

## 待裁決事項

「還沒決定」是一種治理狀態，不是治理的缺席。規格裡的未決問題、提出但未批准的紅線、沒有 owner 的 KPI——每一項都是有人被期待要做的決定，而每一項對「只讀已做成決定」的檢查都是隱形的。

待裁決事項與已接受風險**同級受治理**：它們帶時鐘，而且必須可被列舉。

**規則 GOV-PD-001（必要）**——專案必須宣告待裁決事項**記在哪裡**，以及**什麼標記代表一項待裁決**：一個固定的 token（狀態值、標籤、字面標記字串），不得是自由書寫的散文。列舉不該取決於讀者猜中當初用了哪些字。三份分別寫「TBD」「待拍板」「待確認」的文件，是三份無法被列舉的文件；一個宣告過的標記讓三份都找得到。

**規則 GOV-PD-002（必要）**——列舉待裁決事項時，必須同時回報總數**與**無法解析的來源份數（見[匯總報告](#匯總報告)）。「查無待裁決事項」在不知道走訪集合有多大時，不帶任何資訊。

**規則 GOV-PD-003（必要）**——每一項待裁決事項都帶一個**裁決期限日期**。到期時適用與逾期技術債相同的三種處置——**做出決定**、**撤回這個問題**、或**延期並寫明理由**。禁止自動延期。

**規則 GOV-PD-004（必要）**——若沒有任何東西在排程上列舉待裁決事項，專案必須帶一份**無人看管宣告**，寫明負責人、複查頻率與最後複查日期——與技術債登記表被要求的兩態規則相同。沒有被列舉是可接受的；沒有被列舉又沒有宣告則不可接受。

> 一項沒有日期的待裁決事項，在行為上與「決定不做」完全相同。差別只在於待裁決的形式讓人以為還有人會去看它。

## 匯總報告

每一份治理報告——合規摘要、閘門報告、KPI 匯總、紅線掃描——都是對某個集合提出的宣稱。這個宣稱的價值，恰好等於它對「自己判不了什麼」的交代的價值。

**規則 GOV-RPT-001（必要）**——報告必須印出三個數字，不能只印兩個：**通過**、**失敗**、**判不了**（無法解析的檔案、缺欄位、來源不可達、不支援的格式）。

**規則 GOV-RPT-002（必要）**——「判不了」**不得**併入「通過」，也**不得**省略。一份解析不了的檔案不是一份乾淨的檔案。只印「N 項檢查通過」的報告，不論 N 是多少都不合規。

**規則 GOV-RPT-003（必要）**——報告必須寫出自己的**分母**以及分母是怎麼推導出來的。範圍來自硬編碼清單的報告，是一份關於那份清單的報告，不是關於這個專案的報告：清單之外的東西全部腐壞，它照樣是綠的。要用「走訪並排除」推導集合，不要用列舉——見[類別層級修正](class-level-fix.md)。

**規則 GOV-RPT-004（必要）**——正向與負向計數分開回報；絕不合併成單一的合規分數。**一個「什麼都不做」與「把工作做完」得分相同的指標，量的不是那份工作。**「11 項中通過 5 項」與「檢查器從未啟動」產生同一個數字，而單一分數分不出這兩者。

**規則 GOV-RPT-005（建議）**——當報告的正確性取決於它自己的工具能運作時，加一隻金絲雀：一個輸入已知會失敗、因此**必須**失敗的檢查。若金絲雀通過了，整份報告不可信，必須整份回報為「判不了」，而不是綠燈。

## 新鮮度指標

**規則 GOV-FRESH-001（必要）**——任何新鮮度／停滯指標都必須指名它讀的是下列哪一個時鐘：

| 時鐘 | 回答的問題 | 可以從哪裡讀 |
|------|-----------|-------------|
| **編輯時間** | 這份產物上次被改動是多久以前？ | 檔案 mtime、最後動到它的 commit、「最後更新」欄位 |
| **對帳時間** | 這份產物上次與它宣稱在描述的真實來源做比對是多久以前？ | 那次比對被記下的日期——沒有別的東西能提供它 |

**規則 GOV-FRESH-002（必要）**——兩者**不得**共用同一個欄位或同一個欄位標題。它們回答不同的問題，而同一份產物可以在其中一個上滿分、在另一個上任意地舊：一份今天剛編輯、內容從未與現實對過的文件，以編輯時間算是零天，以對帳時間算是無上限。

**規則 GOV-FRESH-003（必要）**——只有編輯時間可取得時，報告必須把該欄標示為編輯時間，**並且**把對帳時間回報為「判不了」（GOV-RPT-001）——絕不能標成新鮮，也絕不能省略不提。

**規則 GOV-FRESH-004（建議）**——對帳時間只有在「由執行該比對的東西自己記下」時才有意義。事後由人手動填入的日期是一項斷言，不是一次量測；請如實標示。

> 這是「單軸裝多維」的失敗：一個欄位，被兩個不同的問題讀取。這個欄位永遠不會被抓到是錯的，因為從來沒有人問過它在回答哪一個問題。

## 治理檔案結構

採用本標準的專案應維護以下檔案：

```
governance/
├── vision.md          # 單一句子願景陳述
├── mission.md         # 承諾 + 紅線清單
└── goals.md           # KPI 清單（每個 Sprint 更新）
```

---

## 合規檢查清單

- [ ] Vision 為單一句子且 ≤ 50 tokens，不含量測指標
- [ ] Mission 有 3–5 項承諾及含所有必備欄位的紅線清單
- [ ] 每條紅線均有：id、category、clause、action
- [ ] Goals 清單存在，每個 KPI 均含：id、metric_name、threshold、measurement_method
- [ ] 沒有任何 KPI 使用模糊詞彙（「改善」、「提升」、「更好」）
- [ ] 若 `gate.mode = trace_only`，`mission.md` 中存在風險接受條款
- [ ] 每一份風險接受條款都有 `review_by` 日期，且沒有任何一份已經過期
- [ ] 專案已宣告待裁決事項記在哪裡、以及哪一個固定標記代表一項待裁決
- [ ] 每一項待裁決事項都有裁決期限日期
- [ ] 待裁決事項要麼被某個會執行的東西列舉，要麼被無人看管宣告涵蓋
- [ ] 每一份治理報告都分開印出「通過／失敗／**判不了**」，並寫出分母與分母的推導方式
- [ ] 沒有任何報告把正向與負向計數合併成單一分數
- [ ] 每一個新鮮度指標都指名自己讀的是編輯時間或對帳時間，且兩者不共用欄位
- [ ] 所有 AI 評估器以 0.4/0.3/0.3 權重評分，且任一軸 < 0.3 即不通過

## 執行現實

> **本標準對「待裁決事項」「匯總報告」「新鮮度指標」三節的規則不提供任何檢查器——這是已知代價，寫在這裡，而不是留給採用者自己撞到。**
>
> UDS 定義的是這些要求，它不提供執行這些要求的程式。想要它們被執行的採用者必須自己寫那支列舉器、那支三態計數報告器、那個對帳日期記錄器——而多數人不會寫。那正是本標準所描述的失敗，現在同樣適用於本標準自己。
>
> 所以最低標準**不是**「去把工具做出來」，而是：**任何被記載為待裁決、已接受、或新鮮的東西，要麼指向一個會執行的檢查，要麼明白說出沒有東西在看它。** 宣告「無人看管」是合規的。無人看管卻不宣告，才是這些規則真正禁止的唯一結果，因為只有它會讓讀者對「有沒有東西在看」產生誤解。

# AI 協作防幻覺標準

> **語言**: [English](../../../core/anti-hallucination.md) | 繁體中文

**版本**: 1.5.1
**最後更新**: 2026-04-13
**適用性**: 所有使用 AI 助理的軟體專案
**範圍**: 通用 (universal)
**業界標準**: 無（UDS 原創）

> **如需詳細範例與案例研究，請參閱 [防幻覺指南](guides/anti-hallucination-guide.md)**

---

## 目的

本標準為 AI 助理定義了嚴格的準則，以防止在分析程式碼、提出建議或撰寫系統文件時產生幻覺（生成虛假或未經證實的資訊）。

---

## 核心準則

### 1. 僅限以證據為基礎的分析

| 應做事項 (DO) | 禁做事項 (DO NOT) |
|---------------|-------------------|
| ✅ 分析已讀取的程式碼檔案 | ❌ 猜測未見過的 API、函式或設定 |
| ✅ 引用已擷取的說明文件 | ❌ 在未驗證的情況下假設框架行為 |
| ✅ 引用已檢查過的設定檔 | ❌ 捏造需求細節 |

### 2. 明確標註來源

**程式碼引用格式**:
```
[Source: Code] file_path:line_number - Description
```

**外部文件引用格式**:
```
[Source: External] URL - Description (Version: x.x.x, Accessed: YYYY-MM-DD)
```

**AI 知識引用格式**:
```
[Source: Knowledge] Topic - Description (⚠️ Requires verification)
```

### 3. 來源類型可靠度

| 來源類型 | 標籤 | 可靠度 |
|----------|------|--------|
| 專案程式碼 | `[Source: Code]` | ⭐⭐⭐⭐⭐ 最高 |
| 專案文件 | `[Source: Docs]` | ⭐⭐⭐⭐ 高 |
| 外部文件 | `[Source: External]` | ⭐⭐⭐⭐ 高 |
| 網路搜尋 | `[Source: Search]` | ⭐⭐⭐ 中 |
| 使用者提供 | `[Source: User]` | ⭐⭐⭐ 中 |
| AI 知識 | `[Source: Knowledge]` | ⭐⭐ 低 |

---

## 確定性分類標籤

| 標籤 | 使用時機 |
|------|----------|
| `[Confirmed]` | 來自程式碼／文件的直接證據 |
| `[Inferred]` | 來自現有證據的邏輯推論 |
| `[Assumption]` | 基於常見模式（需要驗證） |
| `[Unknown]` | 資訊不可得 |
| `[Need Confirmation]` | 需要使用者釐清確認 |

---

## 衍生標籤（用於生成內容）

| 標籤 | 目的 | 範例語境 |
|------|------|----------|
| `[Source]` | 來自規格／需求的直接內容 | SPEC 標題、逐字引用的 AC 文字 |
| `[Derived]` | 從來源內容轉換而來 | 從項目符號 AC 轉換的 GWT |
| `[Generated]` | AI 生成的結構 | 測試骨架、TODO 註解 |
| `[TODO]` | 需要人工實作 | 步驟定義、斷言 |

---

## 禁止行為

| # | 禁止事項 | 替代做法 |
|---|----------|----------|
| 1 | **捏造 API 或函式簽章** | 讀取實際原始碼或詢問使用者 |
| 2 | **假設需求** | 當需求不明確時提出釐清問題 |
| 3 | **猜測未讀取的程式碼** | 聲明「需要讀取 [檔案] 以確認」 |
| 4 | **虛構設定** | 檢視實際的設定檔 |
| 5 | **憑空捏造錯誤或 Bug** | 分析實際程式碼並引用具體行號 |
| 6 | **僅提供選項而未給出建議** | 務必包含附帶理由的推薦選項 |
| 7 | **未進行副作用分析即實作** | 在實作前列出至少 3 個潛在副作用 |

---

## 建議要求

**規則**：當提供多個選項時，務必包含附帶理由的推薦選項。

| 情境 | 要求 |
|------|------|
| 提供 2 個以上選項 | 必須指出推薦選項並附上理由 |
| 存在明顯的最佳解 | 直接推薦最佳選項並附上理由 |
| 存在取捨權衡 | 根據目前語境推薦，並說明權衡考量 |
| 無法判斷 | 說明需要哪些資訊才能提出建議 |

---

## 下一步建議

**規則**：完成一項任務或子任務後，提出合乎邏輯的下一步建議，並指出最推薦的一項。

**準則**：
- **積極主動**：不要等使用者詢問「現在該做什麼？」
- **貼合語境**：建議應遵循專案的工作流程
- **明確最佳路徑**：使用 `[Recommended]` 標記最佳路徑

---

## 實作檢查清單

在對程式碼、需求或架構做出任何陳述之前：

- [ ] **已驗證來源**：我是否已讀取實際的檔案／文件？
- [ ] **已標註來源類型**：我是否指定了來源類型？
- [ ] **已引用參考資料**：我是否包含了檔案路徑與行號（針對程式碼）？
- [ ] **已指定版本**：在適用的情況下，我是否包含了函式庫／框架版本？
- [ ] **已分類確定性**：我是否已標記為 [Confirmed]、[Inferred] 等？
- [ ] **已標示 AI 知識**：我是否使用 ⚠️ 警告標記了 `[Source: Knowledge]`？
- [ ] **無捏造內容**：我是否避免了虛構 API、設定或需求？
- [ ] **已請求使用者釐清**：針對不明確之處，我是否已請求釐清？
- [ ] **已包含推薦建議**：提供多個選項時，我是否包含了推薦選項？
- [ ] **已識別副作用**：在實作前，我是否已列出潛在的副作用？

---

## 版本敏感度

**規則**：當引用函式庫、框架或 API 時，只要資訊可用，務必包含版本資訊。

| ✅ 良好 | ❌ 不良 |
|---------|---------|
| `[Source: External] Next.js App Router (v14.x) - Server Components are the default` | "Next.js uses Server Components" |
| `[Source: Code] package.json:12 - Using "express": "^4.18.2"` | "Express handles routing" |

## 代理認識校準 (Agent Epistemic Calibration) (v1.4.0, XSPEC-008)

代理必須使用 Answer/Ask/Abstain 框架聲明其認識狀態：

| 行動 | 使用時機 | 必要欄位 |
|------|----------|----------|
| `answer` | 擁有充足資訊 | 無（完整度／信心程度為選填） |
| `ask` | 缺少關鍵資訊 | `missing_variables` 清單 |
| `abstain` | 確實超出能力範圍 | `abstain_reason` |

**故障閉鎖型代理 (Fail-closed agents)**（必須一律回答）：`evaluator`、`guardian`

**向後相容性**：缺少 `epistemic` 欄位時，預設為 `action_type: "answer"`。

參見：XSPEC-008, DEC-014 (PassiveQA)

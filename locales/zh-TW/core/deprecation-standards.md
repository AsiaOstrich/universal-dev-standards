# 棄用與日落標準

> **語言**: [English](../../../core/deprecation-standards.md) | 繁體中文

**版本**: 1.1.0
**最後更新**: 2026-06-24
**適用性**: 所有軟體專案
**範圍**: 通用
**產業標準**: RFC 8594 (Sunset Header), RFC 8288 (Web Linking)
**參考資料**: [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594), [API Deprecation Best Practices](https://swagger.io/blog/api-strategy/api-versioning-deprecation/)

---

## 概述

本文件定義棄用全生命週期管理標準——涵蓋從 API 版本退役、功能日落到完整系統除役。結構化的棄用流程保護消費者、防止資料遺失，並確保基礎設施乾淨。

---

## API 棄用

### Sunset 時間線

當退役 API 版本時，請遵循以下 6 階段時間線：

| 階段 | 時間點 | 行動 |
|-------|-----------|---------|
| **宣布** | T-6 個月 | 公布退役計畫；發布 Sunset 日期；通知所有已知消費者 |
| **棄用** | T-3 個月 | 標記為 deprecated；在回應中加入 Deprecation 與 Sunset 標頭 |
| **遷移** | T-3 到 T-1 個月 | 積極協助消費者遷移；提供遷移指南與工具 |
| **警告** | T-1 個月 | 發送最終警告；在回應中加入倒數資訊 |
| **日落** | T | 停止提供服務；所有端點返回 410 Gone |
| **歸檔** | T+1 個月 | 歸檔文件與資料；移除基礎設施 |

### HTTP 棄用 Headers

當 API 版本進入 **Deprecate** 階段時，所有回應都必須包含：

```
Deprecation: true
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
Link: <https://api.example.com/v3/docs>; rel="successor-version"
```

| 標頭 | 目的 | 格式 |
|--------|---------|--------|
| `Deprecation` | 標記此 API 已被棄用 | `true` (boolean) |
| `Sunset` | API 將被移除的日期 | RFC 7231 HTTP-date |
| `Link` | 指向後繼版本文件 | 帶有 `rel="successor-version"` 的 URL |

### 版本平行期

當新版本發布時，舊版本必須至少維持到以下兩者中較晚者：

- 新版本達到正式發布（GA）後 **6 個月**
- 最後一個活躍消費者完成遷移後 **3 個月**

這可確保消費者有足夠的時間進行遷移而不會中斷服務。

### 依 API 分級的最短棄用期間

上方的 6 階段 Sunset 時間線呈現的是**公開 API 的預設節奏**（從宣布到日落約 6 個月通知期）。*最短*棄用期間會隨 API 的受眾與關鍵程度而調整。請取下表的分級最低值與上方版本平行期兩者中**較長者**：

| API 分級 | 最短棄用期間 |
|----------|--------------|
| **內部 API** | 1 個 minor 版本 |
| **合作夥伴 API** | 2 個 minor 版本 + 3 個月 |
| **公開 API** | 2 個 minor 版本 + 6 個月 |
| **關鍵基礎設施** | 最少 1 年 |

以上皆為最低值；SLA 或合約義務可能要求更長的期間（見[功能日落 → 影響分析](#impact-analysis)）。何謂觸發棄用的破壞性變更、以及 API 版本化機制本身，則歸[API 設計標準](api-design-standards.md#api-versioning-strategies)——本標準僅就棄用時間線與這些通知期間作為單一真實來源。

## 消費者通知策略

有效的棄用需要透過多個管道接觸消費者。請至少使用 5 個通知管道：

| 管道 | 時機 | 內容 |
|---------|--------|---------|
| **CHANGELOG / Release Notes** | 宣布階段 | 退役計畫、Sunset 日期、遷移指南連結 |
| **API Response Header** | 棄用階段起 | Sunset 標頭 + successor-version 連結 |
| **Email / 通知** | 宣布 + 警告階段 | 直接通知已知消費者 |
| **API 文件** | 宣布階段起 | 明確標記為 deprecated；提供新版本連結 |
| **Dashboard / 監控** | 棄用階段起 | 追蹤剩餘消費者數量與流量 |

**最佳實踐：**
- 在每次通知中都附上遷移指南連結
- 提供專門的遷移支援管道（Slack、電子郵件別名）
- 追蹤通知送達率與確認率

## 功能日落

### 影響分析

在移除功能之前，請評估 5 個分析維度：

| 維度 | 關鍵問題 |
|-----------|--------------|
| **使用量** | 過去 30 天內有多少使用者使用過此功能？趨勢為何？ |
| **依賴** | 哪些其他功能、服務或整合依賴此功能？ |
| **資料** | 此功能是否產生或管理獨特資料？是否需要遷移或歸檔？ |
| **合約** | 是否有與此功能掛鉤的 SLA 承諾、合約義務或合規要求？ |
| **替代方案** | 是否有替代品？使用者是否知道如何遷移？替代方案功能是否完整？ |

### 功能日落執行檢查清單

在完成影響分析並確認移除決策後，請驗證每個項目：

- [ ] 通知受影響的使用者（至少提前 30 天）
- [ ] 提供替代方案或遷移指南
- [ ] 移除功能程式碼（不留死碼）
- [ ] 移除相關的 Feature Flags
- [ ] 遷移或歸檔相關資料
- [ ] 更新 API 文件與使用者文件
- [ ] 設定重導向（舊 URL → 替代功能或說明頁面）
- [ ] 更新 CHANGELOG

## 系統除役

### 除役流程

當退役整個系統或服務時，請遵循以下 7 個階段：

| 階段 | 行動 | 驗證 |
|-------|--------|-------------|
| **1. 依賴分析** | 識別所有上游與下游依賴 | 依賴圖無未解節點 |
| **2. 消費者遷移** | 協助所有消費者遷移至替代服務 | 流量降至 0 |
| **3. 資料歸檔** | 依合規與保留要求歸檔資料 | 歸檔完整性已驗證 |
| **4. DNS/重導向** | 舊端點返回 410 Gone 或重導向至替代服務 | 回應已驗證正確 |
| **5. 基礎設施清理** | 移除伺服器、資料庫、佇列、儲存空間 | 資源釋放已確認 |
| **6. 監控移除** | 移除告警、儀表板、Runbook | 無孤立告警殘留 |
| **7. 文件歸檔** | 將文件標記為已歸檔 | 文件索引已更新 |

### 資料歸檔策略

在系統退役期間歸檔資料時，請遵循以下保留規則：

| 資料類型 | 保留期間 | 歸檔方式 |
|-----------|-----------------|-----------------|
| **使用者資料** | 依隱私法規（GDPR：刪除；其他：5–7 年） | 加密冷儲存 |
| **交易紀錄** | 依稅務／稽核要求（通常為 7 年） | 唯讀封存 |
| **日誌** | 1 年 | 壓縮封存 |
| **設定／程式碼** | 永久（已在 Git 中） | Git 歷史紀錄 |

**歸檔原則：**
- 在刪除來源資料前，使用校驗和（checksum）驗證歸檔完整性
- 記錄歸檔位置與存取程序
- 確保歸檔資料仍可供合規稽核存取

## 退役指標

使用以下 4 個指標追蹤棄用進度：

| 指標 | 定義 | 目標 |
|--------|-----------|--------|
| **消費者遷移率** | 已遷移消費者 / 總消費者 | Sunset 時 100% |
| **剩餘流量** | 每日對已棄用端點的請求數 | Sunset 時 0 |
| **依賴清理率** | 已清理依賴 / 總依賴 | Archive 時 100% |
| **資料歸檔完成率** | 已歸檔資料集 / 需歸檔資料集總數 | Archive 時 100% |

**監控建議：**
- 在棄用期間每週檢視指標
- 若在期中時消費者遷移率低於 50%，應向上呈報升級
- 若剩餘流量高於門檻，則阻擋日落

## 快速參考卡

### Sunset 時間線摘要
```
T-6 個月   → 宣布（發布計畫）
T-3 個月   → 棄用（加入 headers）
T-3 到 T-1 → 遷移（協助消費者）
T-1 個月   → 警告（最終通知）
T          → 日落（410 Gone）
T+1 個月   → 歸檔（清理）
```

### 功能移除決策
```
30 天內使用量 > 0？         → 仔細評估
有依賴？                   → 先盤點並遷移
有合約義務？               → 需法律審查
無替代方案？               → 先建立替代方案
```

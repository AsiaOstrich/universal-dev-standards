# 技術債管理標準

> **語言**: [English](../../../core/tech-debt-standards.md) | 繁體中文

**版本**: 1.1.0
**最後更新**: 2026-08-20
**適用性**: 所有軟體專案
**範圍**: universal
**產業標準**: Martin Fowler's Technical Debt Quadrant, Ward Cunningham's Debt Metaphor
**參考**: [martinfowler.com/bliki/TechnicalDebt](https://martinfowler.com/bliki/TechnicalDebt.html)

---

## 概述

技術債代表因現在選擇權宜之計、而非耗時較長的更佳方案，所產生的未來重工隱含成本。本標準定義如何在整個軟體開發生命週期中分類、登記、排序、編列預算、衡量及追蹤技術債。

---

## 1. 技術債類型

所有技術債都歸屬於下列六種類別之一：

| 類型 | 說明 | 範例 |
|------|------|------|
| **Design Debt** | 架構捷徑或次優設計決策 | 缺少抽象層、緊耦合、分層被破壞 |
| **Code Debt** | 增加維護負擔的程式碼品質問題 | 重複程式碼、過長方法、Magic Number、死碼 |
| **Test Debt** | 不足或低品質的測試覆蓋 | 缺少單元測試、不穩定測試、沒有整合測試 |
| **Documentation Debt** | 缺失、過時或不正確的文件 | 未文件化的 API、過時 README、缺少架構文件 |
| **Dependency Debt** | 過時、有漏洞或不必要的依賴 | 未修補的函式庫、已棄用框架、未使用的套件 |
| **Infrastructure Debt** | 次優的建置、部署或維運工具 | 手動部署、缺少監控、過時的 CI/CD |

### 蓄意 vs 非蓄意

技術債可能經由兩種不同模式產生：

| 模式 | 說明 | 範例 |
|------|------|------|
| **蓄意（Deliberate）** | 在了解後果的情況下，有意識地選擇捷徑 | 「我們知道這不是正確的抽象，但我們週五前必須上線」 |
| **非蓄意（Inadvertent）** | 因知識不足或疏忽而無意間產生的債務 | 「我們沒料到這個模式會造成擴充性問題」 |

蓄意債務一律應立即登記。非蓄意債務應在發現後立即登記。

## 2. 技術債登記表

### 登記表範本

每個技術債項目都必須以下列 11 個欄位記錄在登記表中：

| # | 欄位 | 說明 | 範例 |
|---|------|------|------|
| 1 | **ID** | 唯一識別碼，格式 `TD-NNN` | TD-001 |
| 2 | **Title** | 簡短描述性標題 | 「單體式 auth 模組需要拆解」 |
| 3 | **Type** | 上述 6 種類型之一 | Design |
| 4 | **Source** | 引入方式（蓄意／非蓄意／事故事後檢討——見 [postmortem-standards](postmortem-standards.md) 的行動項目交接） | 蓄意（或 `postmortem PM-042`） |
| 5 | **Impact** | 業務與技術影響描述 | 「每個 Sprint 拖慢功能開發約 2 天」 |
| 6 | **Estimated Cost** | 解決所需工作量（故事點或人天） | 8 故事點 |
| 7 | **Interest** | 不解決的持續成本（見利息類型） | 每個 Sprint 額外 1 天除錯 |
| 8 | **Priority** | 依影響矩陣得出的優先等級（P0-P3） | P1 |
| 9 | **Owner** | 負責解決的團隊或個人 | @backend-team |
| 10 | **Created Date** | 登記日期 | 2026-01-15 |
| 11 | **Target Resolution Date** | 計劃解決日期 | 2026-Q2 |

### 登記表儲存選項

登記表可存放於下列任一位置。每個選項**只有在同時滿足右欄條件時才合法**——見下方[到期處置](#到期處置)。

| 選項 | 適用對象 | 格式 | 到期檢查條件 |
|------|---------|------|-------------|
| `docs/tech-debt-registry.md` | 小型團隊、簡易追蹤 | Markdown 表格 | 有一支 repo 檢查會解析該表格，並在有列超過 Target Resolution Date 時失敗——**或**該檔帶有「無人看管宣告」 |
| Issue tracker（GitHub Issues、Jira） | 較大團隊、工作流程整合 | 帶 `tech-debt` 標籤的 Issue | 對到期日欄位的排程查詢實際會**執行**並發出告警；沒有人打開的儲存查詢不算檢查——**或**帶有「無人看管宣告」 |
| 專用試算表 | 非技術利害關係人 | 含 11 個欄位的 CSV/Excel | 僅當該表以明訂頻率匯出到某個會被檢查讀取的位置時才合法——**或**帶有「無人看管宣告」 |

> **這一欄為什麼必須加。** 一份沒有任何程式讀得到的登記表，滿足本節其餘每一條要求：11 個欄位齊全、有 Owner、有 Target Resolution Date。它沒有任何地方是錯的——直到日期過了，然後什麼都沒發生。試算表選項**刻意不移除**（試算表常是出錢的人唯一會打開的格式）；不再合法的是「任何一種儲存方式成為日期無聲過期的地方」。

### 到期處置

一個過了卻沒有任何後果的 **Target Resolution Date**，與根本沒有日期無從分辨。本小節定義「日期到了」是什麼意思。

#### 三種合法處置

項目到達 Target Resolution Date 時，必須發生且只能發生下列三者之一，並且必須留下痕跡：

| 處置 | 意義 | 必留痕跡 |
|------|------|---------|
| **做掉（Resolve）** | 把事情做完 | 關閉登記項 + `Tech-Debt: TD-NNN resolved` commit footer（見 [Commit 標記](#6-commit-標記)） |
| **撤銷（Withdraw）** | 決定不做，並刪掉這筆記載 | 標記為撤銷，附理由與日期。它不再被計為技術債，因為它已經不是了 |
| **延期（Extend）** | 設定新的 Target Resolution Date | 新日期**與**書面理由必須一起記下；先前的日期保持可見（用附加，不要覆蓋） |

沒有第四種處置。「仍然開著、日期過了、沒有人看」不是本標準允許的狀態——那正是本小節存在要指名的失敗。

**規則 TD-EXP-001（必要）**——項目超過 Target Resolution Date 而三種處置皆未施用，該登記表即不合規。到期是一個發現，不是中性的背景狀態。

**規則 TD-EXP-002（必要，禁止事項）**——到期**不得**被實作成**自動延期**或**自動關閉**。

- 自動延期使日期變得不可證偽：它永遠不會被錯過，所以它從未量到任何東西。
- 自動關閉在沒有任何人做出決定的情況下刪掉了那筆記載。

兩者都讓時鐘停止，且都不留下「時鐘停了」的痕跡。一個唯一的消費者是「把它往後推的排程」的日期，只是裝飾。

**規則 TD-EXP-003（必要）**——延期時理由必須記在新日期旁邊。只改日期不是延期，那是一次蓋了時間戳的刪除。

**規則 TD-EXP-004（建議）**——被延期三次以上、期間沒有記錄任何進度的項目，應重新分流為**撤銷**候選。反覆延期是「沒有人打算做這件事」的證據；老實記下這件事，比第四個日期對下一位讀者更有用。

#### 無人看管宣告

不是每個團隊都有能力跑一支檢查。**沒有自動到期檢查的登記表仍然合規——但前提是它把這件事寫出來。**

「無人看管宣告」是寫在登記表內部、可見且帶日期的一段陳述：

```
無人看管——沒有任何自動檢查在讀這份登記表的到期項目。
由 <負責人> 以 <頻率> 人工複查。最後複查日期：<日期>。
```

**規則 TD-EXP-005（必要）**——登記表必須處於下列兩種狀態之一，且必須讓讀者看得到它處於哪一種：

1. **已受檢（Checked）**——有一支具名、跑得起來的檢查在讀這份登記表，並在項目超過 Target Resolution Date 時失敗。
2. **無人看管（Unattended）**——沒有這樣的檢查，但帶有無人看管宣告，且宣告中寫明負責人、複查頻率與最後複查日期。

兩種狀態都不處於的登記表即為不合規。這份宣告不是形式：它就是「知道沒有東西在看的讀者」與「以為有東西在看的讀者」之間的全部差別。

**規則 TD-EXP-006（必要）**——無人看管宣告裡的「最後複查日期」本身，受該宣告自己所寫的頻率約束。最後複查日期比自己宣告的頻率還舊的宣告，本身就是一個到期項目，三種處置同樣適用於它。

> **本標準不提供任何檢查器，這是已知代價——寫在這裡，而不是留給採用者自己撞到。**
>
> UDS 定義的是要求，它不提供一支執行該要求的程式。想要**已受檢**狀態的採用者必須自己寫那支檢查，而多數團隊不會寫——那正是上面描述的失敗模式，現在同樣適用於本小節自己。
>
> 所以這裡的最低標準**不是**「去建一支檢查器」，而是**「絕不讓一份登記表在無聲中變成無人看管」**。宣告 `無人看管` 只要一段文字，而且完全合規。無人看管**卻不宣告**才是本標準真正禁止的唯一結果，因為只有它會讓讀者對「有沒有東西在看」產生誤解。

## 3. 預算分配

### 依團隊狀態的預算比例

團隊應依目前狀態，將每個 Sprint 產能的一定百分比分配給技術債償還：

| 團隊狀態 | 預算 | 說明 |
|---------|------|------|
| **新專案**（< 6 個月） | **10%** | 預防性維護；及早建立良好模式 |
| **成熟專案**（6+ 個月，穩定） | **15%** | 持續維護；防止債務累積 |
| **高債務專案**（有關鍵債務積壓） | **20-30%** | 積極償還；恢復開發速度 |

### 預算使用追蹤

團隊必須追蹤技術債預算的使用情況以落實當責：

1. **Sprint 規劃**：為債務工作保留適當百分比的產能
2. **Sprint 審查**：回報實際花在償債上的時間與預算的對比
3. **Sprint 回顧**：評估預算分配是否恰當，必要時調整
4. **季度報告**：彙整債務趨勢、預算使用率與對開發速度的影響

## 4. 優先排序矩陣

### 3x3 影響 x 工作量矩陣

使用此矩陣，依影響（業務／技術嚴重度）與工作量（解決成本）決定優先等級：

|  | **低工作量** | **中工作量** | **高工作量** |
|--|---------|---------|---------|
| **高影響** | P0 — 立即 | P1 — 下個 Sprint | P1 — 下個 Sprint |
| **中影響** | P1 — 下個 Sprint | P2 — 本季 | P2 — 本季 |
| **低影響** | P2 — 本季 | P3 — Backlog | P3 — Backlog |

### 優先等級定義

| 等級 | 緊急程度 | SLA |
|------|---------|-----|
| **P0** | 關鍵——阻礙開發或構成安全風險 | 於當前 Sprint 內解決 |
| **P1** | 高——顯著影響開發速度或品質 | 於下個 Sprint 內解決 |
| **P2** | 中——影響明顯但可控 | 於本季內解決 |
| **P3** | 低——目前影響極小，可能隨時間擴大 | 放入 Backlog，每季檢視 |

### 利息類型

技術債會累積「利息」——不解決所帶來的持續成本。請追蹤下列三種利息類別：

| 利息類型 | 說明 | 範例 |
|---------|------|------|
| **時間利息** | 為繞過債務而額外花費的開發時間 | 因資料層過於複雜，每個功能多花 2 小時 |
| **風險利息** | Bug、當機或安全事件的機率增加 | 有已知 CVE 卻未修補的依賴 |
| **人才利息** | 對開發者體驗、新人上手與留才的負面影響 | 因架構未文件化，新進人員需要 2 倍時間才能上手 |

## 5. 量化指標

追蹤下列五項關鍵指標以監控技術債健康度：

| # | 指標 | 公式 | 目標 |
|---|------|------|------|
| 1 | **總債務量** | 所有未關閉債務項目數 | 下降趨勢 |
| 2 | **債務比率** | 未關閉債務項目 / 總 Backlog 項目 × 100% | < 15% |
| 3 | **平均存活天數** | 所有債務項目存活天數總和 / 債務項目數 | < 90 天 |
| 4 | **類型分布** | 各類型數量 / 總債務項目 × 100% | 單一類型不超過 40% |
| 5 | **高優先比率** | (P0 + P1 項目) / 總債務項目 × 100% | < 20% |

### 報告頻率

| 頻率 | 報告內容 |
|------|---------|
| 每週 | 新增債務項目、已解決項目、P0/P1 狀態 |
| 每月 | 全部 5 項指標及趨勢分析 |
| 每季 | 完整債務審查、預算調整建議 |

## 6. Commit 標記

### Commit Footer 格式

當 commit 引入或解決技術債時，在 commit message 加上一行 footer：

**引入債務：**
```
feat(auth): add temporary session cache bypass

Skipping cache validation for admin sessions to meet launch deadline.

Tech-Debt: TD-042 introduced
```

**解決債務：**
```
refactor(auth): implement proper session cache validation

Replace temporary bypass with full cache validation pipeline.

Tech-Debt: TD-042 resolved
```

### 標記規則

1. commit 明知會引入技術債時，使用 `Tech-Debt: TD-NNN introduced` 格式
2. commit 完整解決一筆已登記的債務項目時，使用 `Tech-Debt: TD-NNN resolved` 格式
3. TD-NNN 識別碼必須對應技術債登記表中的條目
4. 單一 commit 可引用多筆債務項目（每行一筆）
5. 部分解決時應在 commit body 描述進度，但不標記為 resolved

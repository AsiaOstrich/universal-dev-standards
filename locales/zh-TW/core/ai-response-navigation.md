# AI 回應導航標準

> **語言**: [English](../../../core/ai-response-navigation.md) | 繁體中文 | [简体中文](../../zh-CN/core/ai-response-navigation.md)

**版本**: 1.3.0
**最後更新**: 2026-08-17
**適用範圍**: 所有使用 AI 輔助開發的專案
**範圍**: universal
**產業標準**: 無（新興 AI 工具實踐）
**參考**: [SPEC-STD-08](../../../docs/specs/standards/SPEC-STD-08-ai-response-navigation.md)

---

## 目的

本標準定義 AI 回應的導航行為：每個實質性的 AI 回應必須包含情境化的下一步建議與推薦選項。確保使用者在開發工作流程中持續被引導，無需記憶所有可用命令。

**問題**：使用者在收到 AI 回應後不知道下一步該做什麼。面對 30+ 個斜線命令，認知負擔高且工作流程連續性中斷。

**解決方案**：在每個實質性 AI 回應結尾附加標準化的「導航區塊」，包含情境模板、推薦標記和彈性選項數量。

**範圍註記（v1.2.0，v1.3.0 擴充）**：規則 1–6 管的是答案**之後**要附什麼。
規則 7–11 **全部屬選用**，管的是答案本身：先講發現（R7）、每輪重述進度（R8）、不要開場白（R9）、
白話是主詞（R10）、每個選項都要帶自己的優劣而非只有推薦項有（R11）。新增的理由是——
一個回應可以滿足規則 1–6 的每一條，同時把結論埋起來；
**而找不到答案的讀者，不會因為結尾有一個正確的導航區塊被告知下一步而得到幫助。**

## 核心規則

### 規則 1：每個實質性回應都包含導航

每個構成「邏輯回應單元」的 AI 回應必須以導航區塊作為結尾。

**以下情況視為邏輯回應單元：**

1. 完成了一項任務或子任務
2. 提供了分析、解釋或建議
3. 向使用者詢問問題或要求選擇
4. 報告了錯誤或異常狀態
5. 展示了程式碼變更結果

**豁免**：極短確認回覆（如「好的」「已完成」「了解」）不構成獨立的邏輯單元，可以省略導航區塊。

### 規則 2：推薦並說明理由

提供多個選項時，使用 ⭐ **推薦** 標記最佳選項，並在 ` — ` 之後附上理由。

| 情境 | 標記方式 |
|------|----------|
| 有一個選項明顯較優 | ⭐ **推薦** — [理由] |
| 各選項無明顯優劣 | 說明各選項適用場景，不標記 ⭐ |
| 只有一個合理的下一步 | 直接建議，不需要 ⭐ |

### 規則 3：匹配情境

根據回應類型使用對應的模板（參見[情境模板](#情境模板)）。

### 規則 4：彈性數量

根據情境複雜度調整選項數量：

| 情境 | 選項數量 | 理由 |
|------|----------|------|
| 任務完成 | 2–3 | 建議後續工作流程步驟 |
| 使用者詢問 | 2–5 | 依問題複雜度調整 |
| 錯誤/失敗 | 1–3 | 聚焦修復方向 |
| 進行中 | 1–2 | 繼續或調整 |
| 資訊回覆 | 1–3 | 探索方向 |

**硬性上限**：不得超過 5 個選項。裁減至最相關的選項。

### 規則 5：優先使用斜線命令

當下一步建議對應到已知的斜線命令時，使用 `` `/command` `` 格式引用，讓使用者可以直接複製執行。沒有對應命令的步驟使用自然語言描述。

### 規則 6：模型級別標注（選用）

當某個下一步選項明確對應到特定的複雜度等級時，可**選擇性**附加模型級別提示。此標注**嚴格為選用**——既有技能無需回頭修改；新增或修訂技能時建議帶入。

**標注方式**：在選項描述後加上 `〔模型：Fast〕`、`〔模型：Standard〕` 或 `〔模型：Capable〕`。

**等級判斷依據**：參考 [model-selection](model-selection.md) 標準的複雜度信號：
- `Fast` — 修改單一檔案、spec 完全明確、無需設計判斷
- `Standard` — 2-5 個檔案、需要模組間理解
- `Capable` — 5+ 個檔案、架構決策、跨系統正確性

等級名稱**與廠商無關**——各工具或平台自行將等級映射到可用的模型。

**英文標注對照**：`〔model: Fast〕` / `〔model: Standard〕` / `〔model: Capable〕`

**示例**（任務完成，含模型標注）：

```markdown
> **建議下一步：**
> - 執行 `/derive bdd` 推導 BDD 場景 `〔模型：Fast〕` — 格式轉換工作
> - 執行 `/checkin` 進行品質關卡驗證 ⭐ **推薦** `〔模型：Standard〕` — 需要模組間判斷
> - 執行 `/sdd` 整合架構設計 `〔模型：Capable〕` — 跨系統影響分析
```

## 導航之前的那個答案（規則 7–11，選用）

> **規則 7–9 借鑒自**：[`ayghri/i-have-adhd`](https://github.com/ayghri/i-have-adhd)（MIT），十條中取三條。
> **規則 10–11 於 1.3.0 新增**，來源不同——使用者在同一次工作階段中兩度指出，
> 一個正確且完整的回答讀不懂。當時規則 7–9 已經出貨且正在被遵守。
> 其餘七條刪去：兩條已被上方規則 1–2 涵蓋，五條與本標準衝突
> （它的「不要 recap／不要結語」與規則 1 的導航區塊直接矛盾；它的「清單上限 5 項」
> 會切斷證據表格與走訪分母）或與 [estimation-standards](estimation-standards.md) 重複。

**這一節為何存在**：規則 1–6 管的是答案**之後**要附什麼，而答案本身沒有任何規則在管——
一個回應可以把結論埋在一整面證據底下，只要結尾附上正確的導航區塊，
它仍然滿足本標準的每一條。**找不到答案的讀者，不會因為被告知下一步而得到幫助。**

**這五條是選用的**，語義同規則 6：採用專案不必啟用，既有 skill 也不需回頭補。
專案**可以**在自己的設定中把任一條提升為必須。**不可選的是它們必須有精確的觸發條件**——
一條鬆到永遠不會啟動的規則，與沒有這條規則無從分辨。

### 規則 7：先講發現，不要先講過程（選用）

**觸發條件**：回答問題、回報調查結果、或提出決策的回應。

第一行寫**查到了什麼**或**該做什麼**。不是方法、不是把問題複述一遍、不是回答的計畫。

證據——`file:line`、指令輸出、表格、量測數字——是**佐證**，應放在它所支持的主張**之後**。
以證據開場會迫使讀者自行重建結論，而那正是他請你做的工作。

| 不要寫 | 改寫成 |
|---|---|
| 「我檢查了 44 天、63 個網域的資料，發現……」 | 「那三組查詢刪掉。它回傳的東西有 46% 是下載頁。」 |
| 「讓我看看這是怎麼設定的。」 | 「設定在 `x.yaml:12`，值是錯的，因為……」 |

**這不代表可以省略證據**，它規範的是順序。

### 規則 8：多輪工作中每一輪重述進度（選用）

**觸發條件**：跨 3 輪以上的對話，或含 3 個以上步驟的任務。

每則回應用一行說明工作進行到哪裡。不能假設讀者能在訊息之間記住
「我們在 5 步中的第 3 步」，而重述它的成本是一個句子。

本條與下方模板 4（進行中）互補：**規則 8 管開頭，模板 4 管結尾。**

### 規則 9：不要開場白（選用）

**觸發條件**：任何實質性回應。

從答案開始。不要以「我接下來要做什麼」的預告、對請求的確認、或對問題本身的評價開場。

本條把一項既有禁令一般化：[anti-sycophancy-prompting](anti-sycophancy-prompting.md)
已經禁止「以正面肯定開場批評」，但**僅限批評情境**。規則 9 把同一項禁令擴及每一個實質回應，
理由不同：不是為了防拍馬屁，而是為了消除它在讀者與答案之間製造的延遲。

**規則 9 不適用於結語。** 規則 1 要求的導航區塊依然成立——
回應的結尾正是本標準安放「讀者下一步」的位置。

### 規則 10：白話是主詞，識別字是佐證（選用）

**觸發條件**：任何向人解釋一個情況、一個缺陷、或一個系統行為的回應。

用讀者會用的話說清楚發生了什麼。檔案路徑、符號名稱、行號、指令輸出、版本字串是**佐證**——
它們屬於它們所支持的那句話**之後**，而不是那句話本身。

| 不要寫 | 改寫成 |
|---|---|
| 「`intel-scout.py:883` 的 `load_topics()` 讀 `intel-topics.yaml`，`:1033` 的 `load_feeds()` 讀 `intel-feeds.yaml`。」 | 「它有兩種取材方式：搜關鍵字，和訂閱固定幾個部落格。」*（然後再附兩個呼叫點）* |
| 「`manifest.skillHashes` 有 137 條，key 是 `claude-code/project/<n>/SKILL.md`，而查詢用的是 `.claude/skills/<n>`。」 | 「雜湊值存在一套命名下，查詢用的是另一套，所以一個都找不到。」*（然後再貼兩邊的 key）* |

這**不是**可以省略識別字的許可——想驗證的讀者必須驗得了。它規範的是**兩者之中哪一個當主詞**。

**為什麼它與 R7 是兩條**：R7 規範的是**先講發現再給證據**的順序。R10 規範的是**語域**——
一個回應可以先講發現，卻仍然用只有作者持有的詞彙講那個發現。兩者都讓讀者無法行動，但它們是不同的失效。

### 規則 11：每個選項都要帶自己的優劣（選用）

**觸發條件**：要求讀者在兩個以上做法之間選擇的回應。

規則 2 要求標示推薦選項並給出**它的**理由。規則 11 把這件事擴及其餘：
**每一個**選項都要用它自己的話說明它換到什麼、代價是什麼。

一份只有推薦項被論證的選項清單，等於**把比較的工作丟回給讀者**——而那正是他請你做的事。
而一個沒有標出代價的選項，讀起來像是沒有代價，這很少為真，且從清單本身無從驗證。

```markdown
> **請選擇：**
> | 選項 | 換到什麼 | 代價是什麼 |
> |---|---|---|
> | **(A) …** ⭐ **推薦** — [為什麼是這個] | … | … |
> | **(B) …** | … | … |
```

**優劣不是模稜兩可。**「這可能會稍微難一點」不是代價；「這要重寫 110 個檔，而且翻譯需要人審」才是。
若某個選項真的沒有值得一提的代價，**明說**，不要留空——空白讀起來是「沒有分析過」，而讀者分不出這兩者。

**與規則 4 相輔**：選項數維持在 1–5。優劣讓每個選項讀起來更花力氣，所以這條規則讓規則 4 的上限**更**要緊，不是更不要緊。

## 情境模板

### 模板 1：任務完成

任務、技能執行或程式碼修改完成時使用。

```markdown
> **建議下一步：**
> - 執行 `/command1` 做 X
> - 執行 `/command2` 做 Y ⭐ **推薦** — [理由]
> - 執行 `/command3` 做 Z
```

### 模板 2：使用者詢問

AI 需要使用者做出選擇或提供資訊時使用。

```markdown
> **請選擇：**
> - **(A) 選項描述** — 補充說明
> - **(B) 選項描述** ⭐ **推薦** — [理由]
> - **(C) 選項描述** — 補充說明
```

### 模板 3：錯誤/失敗

報告錯誤、失敗或異常狀態時使用。

```markdown
> **建議修復方向：**
> - 選項描述 ⭐ **推薦** — [理由]
> - 選項描述
```

### 模板 4：進行中

完成多步驟任務的中間階段時使用。

```markdown
> **目前進度：[N/M]。下一步：**
> - 繼續下一階段 ⭐ **推薦**
> - 調整方向或參數
```

### 模板 5：資訊回覆

回答知識性問題或提供說明時使用。

```markdown
> **建議下一步：**
> - 深入了解 [相關主題]
> - 執行 `/command` 將知識應用到實作
```

## 格式規範

### 結構

所有導航區塊使用 Markdown 引用區塊（`>`）：

```markdown
> **[標題]：**
> - [選項/建議] ⭐ **推薦** — [理由]
> - [選項/建議] — [補充說明]
```

### 依情境的標題

| 情境 | 標題 |
|------|------|
| 任務完成 | `建議下一步` |
| 使用者詢問 | `請選擇` |
| 錯誤/失敗 | `建議修復方向` |
| 進行中 | `目前進度：[N/M]。下一步` |
| 資訊回覆 | `建議下一步` |

### 本地化

對於雙語專案，導航區塊遵循對話語言。本地化對照：

| English | 繁體中文 | 简体中文 |
|---------|----------|----------|
| Suggested next steps | 建議下一步 | 建议下一步 |
| Please choose | 請選擇 | 请选择 |
| Suggested resolution | 建議修復方向 | 建议修复方向 |
| Progress: [N/M]. Next | 目前進度：[N/M]。下一步 | 当前进度：[N/M]。下一步 |
| Recommended | 推薦 | 推荐 |

## 與技能的整合

### 現有技能

已有 `## Next Steps Guidance | 下一步引導` 區塊的技能：

1. **保留**技能特有的場景化建議內容
2. **對齊**格式以符合本標準定義的模板
3. **加入**推薦標記（⭐）

### 新技能

新技能應包含遵循本標準模板的 `## Next Steps Guidance | 下一步引導` 區塊。

### 超越技能

本標準適用於**所有 AI 回應**，不僅限於技能執行。一般對話、程式碼審查、除錯過程及任何其他互動，在產生實質性回應時都必須遵循這些導航規則。

## 跨 AI 工具適用性

本標準與工具無關。適用於所有使用 UDS 標準的 AI 工具：

- Claude Code
- Cursor
- Windsurf
- GitHub Copilot
- Cline
- Roo Code
- Augment Code
- Trae
- 其他相容工具

每個工具的整合層負責根據其 UI 能力渲染導航區塊，但行為規則保持一致。

## 範例

### 範例 1：完成功能實作後

```markdown
> **建議下一步：**
> - 執行 `/test` 為新功能撰寫測試
> - 執行 `/commit` 提交變更 ⭐ **推薦** — 變更已完整且通過驗證
> - 執行 `/code-review` 進行自我審查
```

### 範例 2：詢問使用者設計問題

```markdown
> **請選擇：**
> - **(A) 使用新的資料庫表** — 更靈活，遷移成本較高
> - **(B) 擴展現有表增加欄位** ⭐ **推薦** — 遷移更簡單，滿足當前需求
> - **(C) 使用 NoSQL 儲存** — 適合非結構化資料但增加基礎設施
```

### 範例 3：報告測試失敗

```markdown
> **建議修復方向：**
> - 檢查 `tests/auth.test.js:42` 的失敗斷言 ⭐ **推薦** — 錯誤訊息指向空引用
> - 執行 `/debug` 進行系統性除錯
> - 還原上次變更並調查
```

### 範例 4：工作流程中間進度更新

```markdown
> **目前進度：[2/5]。下一步：**
> - 繼續第 3 階段：實作 ⭐ **推薦**
> - 在繼續前重新檢視第 2 階段需求
```

### 範例 5：回答技術問題

```markdown
> **建議下一步：**
> - 探索 `config/auth.yaml` 中的相關配置
> - 執行 `/sdd` 建立規格（若計畫修改此行為）
```

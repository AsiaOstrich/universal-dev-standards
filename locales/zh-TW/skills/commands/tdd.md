# TDD 助手

> **Language**: [English](../../../../skills/commands/tdd.md) | 繁體中文

> [!WARNING]
> **實驗性功能**
>
> 此功能正在積極開發中，可能在 v4.0 中有重大變更。

引導測試驅動開發（TDD）流程：紅-綠-重構。

## 前置檢查

在執行 TDD 階段前，AI 助手必須驗證前置條件。如果檢查失敗，停止並引導使用者。

### 階段閘門矩陣

| 目標階段 | 前置檢查 | 失敗時 |
|---------|---------|--------|
| `RED` | 1. 功能/函式已清楚定義 | → 要求使用者描述行為 |
| | 2. 若為 SDD 專案：規格存在且已核准 | → 引導至 `/sdd` |
| `GREEN` | 1. 至少有一個失敗的測試存在 | → 引導回 RED 階段 |
| | 2. 執行測試 → 確認失敗（非錯誤） | → 先修復測試語法/設定 |
| `REFACTOR` | 1. 所有測試通過（確認 GREEN） | → 停留在 GREEN 階段 |
| | 2. 前一個 RED 週期沒有失敗的測試 | → 先完成 GREEN |

### 紅燈優先強制

```
🔴 RED：撰寫測試 → 執行 → 必須失敗
   ↓ （僅在測試以預期的斷言失敗時才繼續）
🟢 GREEN：撰寫最少程式碼 → 執行 → 必須通過
   ↓ （僅在所有測試通過時才繼續）
🔵 REFACTOR：清理程式碼 → 執行 → 仍必須通過
```

**關鍵規則**：AI 不得在失敗測試存在之前撰寫實作程式碼。如果使用者要求「直接寫程式碼」，提醒 TDD 契約並建議先寫測試。

## 方法論整合

當調用 `/tdd` 時：
1. **自動啟用 TDD 方法論**（如果尚未啟用）
2. **將當前階段設為紅燈**（撰寫失敗的測試）
3. **追蹤階段轉換**隨著工作進展
4. **在回應中顯示階段指示器**（🔴 紅燈、🟢 綠燈、🔵 重構）

參見 [methodology-system](../dev-methodology/SKILL.md) 了解完整方法論追蹤。

## 工作流程

### 1. RED - 撰寫失敗的測試
- 為預期行為撰寫測試
- 執行測試 - 應該失敗
- 確認測試有效

### 2. GREEN - 讓測試通過
- 撰寫最少程式碼讓測試通過
- 不加額外功能
- 執行測試 - 應該通過

### 3. REFACTOR - 改善程式碼
- 清理程式碼
- 移除重複
- 所有測試應仍然通過

## FIRST 原則

| 原則 | 說明 |
|------|------|
| **F**ast | 快速執行 |
| **I**ndependent | 無相依性 |
| **R**epeatable | 可重複 |
| **S**elf-validating | 自我驗證 |
| **T**imely | 及時撰寫 |

## 使用方式

- `/tdd` - 啟動互動式 TDD session
- `/tdd calculateTotal` - 針對特定函式進行 TDD
- `/tdd "user can login"` - 針對用戶故事進行 TDD

## AI 代理行為

> 遵循 [AI 命令行為標準](../../core/ai-command-behavior.md)

### 進入路由

| 輸入 | AI 動作 |
|------|---------|
| `/tdd` | 詢問要實作的功能，進入 🔴 RED 階段 |
| `/tdd <function>` | 以指定函式為目標，直接進入 🔴 RED |
| `/tdd "user story"` | 以使用者故事為目標，進入 🔴 RED |

### 互動腳本

#### 🔴 RED 階段

1. 確認目標功能/行為
2. 撰寫一個會失敗的測試
3. 執行測試，確認失敗（assertion failure，非 syntax error）

**決策：測試結果**
- IF 測試失敗（assertion） → 進入 🟢 GREEN
- IF 測試出錯（syntax/runtime error） → 修正測試本身，重新執行
- IF 測試通過 → 告知使用者測試不應該通過，檢查是否功能已存在

🛑 **STOP**：展示失敗測試後等待使用者確認進入 GREEN

#### 🟢 GREEN 階段

1. 撰寫最小量程式碼使測試通過
2. 執行測試

**決策：測試結果**
- IF 所有測試通過 → 建議進入 🔵 REFACTOR
- IF 仍有失敗 → 繼續修改程式碼（最多 3 次），超過則 🛑 STOP

🛑 **STOP**：測試通過後等待使用者確認進入 REFACTOR

#### 🔵 REFACTOR 階段

1. 分析剛寫的程式碼是否有改善空間
2. 提出重構建議

**決策：重構範圍**
- IF 有明顯重複或改善點 → 列出建議，等使用者選擇
- IF 程式碼已足夠簡潔 → 告知不需重構，建議進入下一個 RED 循環

3. 執行重構，確認所有測試仍通過

🛑 **STOP**：重構完成後等待使用者決定繼續下一個 RED 循環或結束

### 停止點

| 階段 | 停止點 | 等待內容 |
|------|--------|---------|
| RED | 失敗測試撰寫後 | 確認進入 GREEN |
| GREEN | 測試通過後 | 確認進入 REFACTOR |
| REFACTOR | 重構完成後 | 決定繼續或結束 |

### 錯誤處理

| 錯誤條件 | AI 動作 |
|----------|---------|
| 使用者要求跳過 RED 直接寫程式碼 | 提醒 TDD 契約，建議先寫測試 |
| 測試框架未偵測到 | 詢問使用者指定框架 |
| 測試語法錯誤導致無法執行 | 修正語法後重新執行，不計入嘗試次數 |
| GREEN 階段 3 次仍無法通過 | 停止，分析失敗原因，等待使用者指導 |

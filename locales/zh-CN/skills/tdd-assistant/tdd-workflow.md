## 红灯阶段深入解析

### 目标

编写一个测试，它应当：
- 描述预期行为（而非实现方式）
- 因**正确的**原因而失败
- 具有清晰、具描述性的名称

### 逐步说明

1. **选择要测试什么**
   - 从最简单的场景开始
   - 专注于「一个」行为

2. **编写测试结构**
   ```typescript
   test('should [预期行为] when [条件]', () => {
     // Arrange - 准备测试数据

     // Act - 执行行为

     // Assert - 验证结果
   });
   ```

3. **填写测试内容**
   - Arrange：创建测试数据和依赖
   - Act：调用被测试的方法/函数
   - Assert：验证预期结果

4. **运行测试**
   - 它应该「失败」
   - 确认失败是因为正确的原因

### 常见错误

| 错误 | 示例 | 修正方式 |
|------|------|----------|
| **断言过多** | 在一个测试中测试 5 件事 | 每个测试只测一个行为 |
| **测试名称模糊** | `test('works')` | `test('should return sum of two numbers')` |
| **没有断言** | 缺少 `expect()` | 始终断言预期结果 |
| **测试实现细节** | 检查私有方法调用 | 测试可观察的行为 |
| **测试一开始就通过** | 测试已有的行为 | 针对「新」行为编写 |

### 红灯阶段检查清单

```
□ 测试名称清楚描述行为
□ 测试遵循 AAA 模式
□ 测试只有「一个」断言（或一组相关断言）
□ 运行时测试「失败」
□ 失败信息清楚
□ 失败是因为「正确的原因」（而非语法错误）
```

## 绿灯阶段深入解析

### 目标

编写让测试通过的**最少**代码。

### 逐步说明

1. **分析失败原因**
   - 测试期望的是什么？
   - 满足它最简单的方式是什么？

2. **编写最少代码**
   - 第一个测试可以硬编码
   - 不要预先考虑未来的需求

3. **运行测试**
   - 它应该「通过」
   - 其他所有测试应该仍然通过

### 「先假装实现」策略

对于第一个测试，假装实现是完全可以的：

```typescript
// 测试：should return sum of 2 and 3
test('should return sum of two numbers', () => {
  expect(add(2, 3)).toBe(5);
});

// 第一个实现（假装实现！）
function add(a: number, b: number): number {
  return 5; // 直接返回预期值
}
```

然后添加更多测试来迫使实现泛化：

```typescript
// 第二个测试迫使真正的实现
test('should return sum of 1 and 1', () => {
  expect(add(1, 1)).toBe(2);
});

// 现在必须泛化
function add(a: number, b: number): number {
  return a + b;
}
```

### 常见错误

| 错误 | 示例 | 修正方式 |
|------|------|----------|
| **过度设计** | 添加目前还不需要的功能 | 只为当前测试编写代码 |
| **过早优化** | 性能调优 | 先让它能运行 |
| **添加错误处理** | 为未测试的情况加 try-catch | 只处理已测试的错误 |
| **复制大段代码** | 从其他项目复制 | 编写最少的代码 |

### 绿灯阶段检查清单

```
□ 编写了「最少」的代码让测试通过
□ 没有添加测试不需要的功能
□ 当前测试通过
□ 其他所有测试仍然通过
□ 没有过早优化
```

## 重构阶段深入解析

### 目标

在保持所有测试为绿色的同时改善代码质量。

### 逐步说明

1. **识别代码坏味道**
   - 重复
   - 过长的方法
   - 命名不佳
   - 复杂的条件判断

2. **选择「一项」改进**
   - 不要试图一次修好所有问题

3. **进行修改**
   - 小步、渐进式的修改

4. **立即运行测试**
   - 如果测试失败，立即回退

5. **视需要重复**

### 常见重构手法

| 手法 | 适用时机 | 示例 |
|------|----------|------|
| **提取方法** | 方法过长、代码重复 | 把 10 行提取到 `calculateTax()` |
| **重命名** | 名称不清楚 | `x` → `totalAmount` |
| **内联** | 不必要的间接层 | 移除包装函数 |
| **提取变量** | 表达式复杂 | `const isEligible = age >= 18 && hasId` |
| **替换魔法数字** | 硬编码的值 | `7` → `DAYS_IN_WEEK` |

### 重构安全规则

```
1. 开始前测试为「绿色」
2. 一次只做「一个」修改
3. 「每次」修改后都运行测试
4. 如果测试「失败」→ 立即「回退」
5. 重构时绝不添加新功能
```

### 常见错误

| 错误 | 示例 | 修正方式 |
|------|------|----------|
| **跳过此阶段** | 直接进入下一个测试 | 始终寻找改进空间 |
| **一次修改太多** | 同时重构 5 处 | 一次只做一个修改 |
| **添加功能** | 「既然都改到这里了……」 | 只清理现有代码 |
| **不运行测试** | 到最后才一起运行 | 每次修改后都运行 |

### 重构阶段检查清单

```
□ 开始前所有测试为「绿色」
□ 已识别具体的改进点
□ 做了「一个」小修改
□ 测试仍然为「绿色」
□ 代码更整洁/更简单
□ 没有添加新功能
□ 对其他改进点重复上述步骤
```

## BDD 工作流程

### Gherkin 语法

```gherkin
Feature: [功能名称]
  As a [角色]
  I want [目标]
  So that [好处]

  Background:
    Given [所有场景共用的准备]

  Scenario: [场景名称]
    Given [初始情境]
    And [更多情境]
    When [动作]
    And [更多动作]
    Then [预期结果]
    And [更多结果]

  Scenario Outline: [参数化场景]
    Given [带有 <parameter> 的情境]
    When [动作]
    Then [带有 <expected> 的结果]

    Examples:
      | parameter | expected |
      | value1    | result1  |
      | value2    | result2  |
```

### BDD 工作流程步骤

```
┌─────────────────────────────────────────────────────────────────┐
│                        BDD 工作流程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 探索会议（Discovery Session）                               │
│     ├─ 开发人员、BA、QA、利益相关者一起参与                     │
│     ├─ 讨论用户故事                                             │
│     └─ 识别验收标准                                             │
│                                                                 │
│  2. 制定（Formulation）                                         │
│     ├─ 用 Gherkin 编写场景                                      │
│     ├─ 每个 AC → 一个或多个场景                                 │
│     └─ 与团队一起评审                                           │
│                                                                 │
│  3. 自动化（Automation）                                        │
│     ├─ 创建 step definitions                                    │
│     ├─ 每个 step → 执行该步骤的代码                             │
│     └─ 用 TDD 实现各个 step                                     │
│                                                                 │
│  4. 实现（Implementation）                                      │
│     ├─ 运行场景（它们会失败 - RED）                             │
│     ├─ 实现功能代码（GREEN）                                    │
│     └─ 重构                                                     │
│                                                                 │
│  5. 活文档（Living Documentation）                              │
│     └─ 场景作为始终保持最新的文档                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Step Definitions 示例（JavaScript/Cucumber）

```javascript
const { Given, When, Then } = require('@cucumber/cucumber');

Given('I have a shopping cart with {int} items', async function (count) {
  this.cart = new ShoppingCart();
  for (let i = 0; i < count; i++) {
    this.cart.addItem({ name: `Item ${i}`, price: 10 });
  }
});

When('I apply discount code {string}', async function (code) {
  this.result = await this.cart.applyDiscount(code);
});

Then('the cart total should be {float}', function (expectedTotal) {
  expect(this.cart.getTotal()).toBeCloseTo(expectedTotal, 2);
});
```

### BDD 最佳实践

| 实践 | 说明 |
|------|------|
| **声明式优于命令式** | 描述「做什么」，而不是「怎么做」 |
| **业务语言** | 避免技术术语 |
| **场景相互独立** | 每个场景都自成一体 |
| **步骤精简** | 每个场景 5-10 个步骤 |
| **步骤可复用** | 编写通用的 step definitions |

```gherkin
# ❌ 命令式（过于细节）
Scenario: Login
  Given I navigate to "http://example.com/login"
  And I click on the username field
  And I type "john@example.com"
  And I click on the password field
  And I type "secret123"
  And I click the "Login" button
  Then I see "Welcome John"

# ✅ 声明式（聚焦行为）
Scenario: Successful login
  Given I am on the login page
  When I login with valid credentials
  Then I should see my dashboard
```

## ATDD 工作流程

### 验收标准格式

```markdown
## 用户故事

**作为** [角色]
**我想要** [功能]
**以便** [好处]

## 验收标准

### AC-1：[标准名称]
**Given** [前置条件]
**When** [动作]
**Then** [预期结果]

### AC-2：[标准名称]
**Given** [前置条件]
**When** [动作]
**Then** [预期结果]

## 不在范围内
- [明确不包含的事项]

## 技术备注
- [实现提示、约束]
```

### ATDD 工作流程步骤

```
┌─────────────────────────────────────────────────────────────────┐
│                        ATDD 工作流程                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 规格研讨会（Specification Workshop）                        │
│     ├─ 产品负责人介绍用户故事                                   │
│     ├─ 团队提出澄清问题                                         │
│     ├─ 共同定义验收标准                                         │
│     └─ 为每个 AC 编写示例                                       │
│                                                                 │
│  2. 提炼（Distillation）                                        │
│     ├─ 把示例转换为可执行的测试                                 │
│     ├─ 消除歧义                                                 │
│     └─ 取得产品负责人签核                                       │
│                                                                 │
│  3. 开发（Development）                                         │
│     ├─ 验收测试为 RED                                           │
│     ├─ 功能层级测试使用 BDD                                     │
│     ├─ 单元层级测试使用 TDD                                     │
│     └─ 验收测试变为 GREEN                                       │
│                                                                 │
│  4. 演示（Demo）                                                │
│     ├─ 展示已通过的验收测试                                     │
│     ├─ 产品负责人确认                                           │
│     └─ 接受或细化标准                                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### AC 与测试的对应

| 验收标准 | 测试层级 | 工具 |
|----------|----------|------|
| 面向用户的行为 | 验收测试 | FitNesse, Cucumber |
| 功能行为 | BDD | Cucumber, SpecFlow |
| 单元逻辑 | TDD | Jest, xUnit |
| API 契约 | 集成测试 | Supertest, REST Assured |

## 团队协作模式

### 结合 TDD 的结对编程

#### 乒乓模式

```
┌─────────────────────────────────────────────────────────────────┐
│                    乒乓 TDD（Ping-Pong）                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   开发人员 A                     开发人员 B                     │
│   ───────────                    ───────────                    │
│   1. 编写失败的测试 ──────────────────────────▶                 │
│                          ◀───────────────────── 2. 让它通过     │
│                          ◀───────────────────── 3. 编写测试     │
│   4. 让它通过 ────────────────────────────────▶                 │
│   5. 编写测试 ────────────────────────────────▶                 │
│                          ◀───────────────────── 6. 让它通过     │
│                                                                 │
│   任何一方都可以随时重构                                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**好处**：
- 双方始终保持投入
- 知识共享
- 及早发现错误

#### 驾驶员-领航员模式

```
┌─────────────────────────────────────────────────────────────────┐
│                    驾驶员-领航员 TDD                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   驾驶员（键盘）                 领航员（思考）                 │
│   ─────────────────              ───────────────────            │
│   - 输入代码                     - 思考设计                     │
│   - 专注于语法                   - 考虑测试用例                 │
│   - 实现想法                     - 检查错误                     │
│   - 提出问题                     - 建议方向                     │
│                                                                 │
│   每 15-30 分钟交换角色                                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**好处**：
- 角色清晰
- 领航员可以进行策略性思考
- 持续评审

### 结合 TDD 的群体编程

```
┌─────────────────────────────────────────────────────────────────┐
│                    群体编程 TDD（Mob Programming）              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   团队（3-6 人）                                                │
│   ─────────────────                                             │
│   - 一名驾驶员（负责输入）                                      │
│   - 多名领航员（负责引导）                                      │
│   - 每 5-10 分钟轮换驾驶员                                      │
│                                                                 │
│   TDD 流程：                                                    │
│   1. 团队讨论下一个测试                                         │
│   2. 驾驶员编写测试（领航员引导）                               │
│   3. 团队确认测试失败                                           │
│   4. 团队讨论实现方式                                           │
│   5. 驾驶员实现（领航员引导）                                   │
│   6. 轮换驾驶员                                                 │
│   7. 下一位成员进行重构或编写下一个测试                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**好处**：
- 全团队认知一致
- 集体所有权
- 实时知识传递

## CI/CD 集成

### 流水线结构

```yaml
stages:
  - test:unit      # 快速 (< 2 分钟)
  - test:integration  # 中等 (< 10 分钟)
  - test:e2e       # 慢速 (< 30 分钟)
  - coverage-check
  - deploy
```

### 质量门禁

| 门禁 | 阈值 | 失败时的动作 |
|------|------|--------------|
| 单元测试通过率 | 100% | 阻止合并 |
| 集成测试通过率 | 100% | 阻止合并 |
| 代码覆盖率 | 80% | 警告 / 阻止 |
| 新代码覆盖率 | 90% | 警告 |
| 测试执行时间 | < 基准 | 警告 |

### CI 配置示例

```yaml
# GitHub Actions
name: TDD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npm run test:unit -- --coverage
      - uses: codecov/codecov-action@v4

  integration-tests:
    needs: unit-tests
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: test
    steps:
      - uses: actions/checkout@v4
      - run: npm run test:integration

  e2e-tests:
    needs: integration-tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run test:e2e
```

### 测试报告

```yaml
# 添加测试报告
- name: Test Report
  uses: dorny/test-reporter@v1
  if: success() || failure()
  with:
    name: Test Results
    path: reports/junit.xml
    reporter: jest-junit
```

## 快速决策指南

### 该编写哪种测试？

```
你正在实现什么？
│
├─ 新功能
│   └─ 从验收标准开始 → BDD → TDD
│
├─ Bug 修复
│   └─ 编写能重现 bug 的失败测试 → TDD
│
├─ 重构
│   └─ 确保现有测试已覆盖相关行为 → 重构
│
├─ 性能改进
│   └─ 编写性能测试 → 实现 → 验证
│
└─ 新 API 端点
    └─ 逻辑用 TDD + HTTP 用集成测试
```

### 测试粒度

```
这个测试应该多具体？
│
├─ 测试公开 API → 每个行为一个测试
├─ 测试内部逻辑 → 将相关断言归为一组
└─ 测试边界情况 → 每个边界情况一个测试
```

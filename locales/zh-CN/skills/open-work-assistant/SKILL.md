# 开放工作追踪

> **语言**: [English](../../../../skills/open-work-assistant/SKILL.md) | [繁體中文](../../../zh-TW/skills/open-work-assistant/SKILL.md) | 简体中文

**版本**: 1.0.0 | **最后更新**: 2026-10-30 | **适用**: Claude Code Skills

帮助避免工作在会话之间漏掉。想用才用。UDS 没有任何东西要求你用。

## 目的

这个技能以前是一条标准，叫 `open-work-tracking`。UDS 把它搬到这里，是因为那条标准只在一个项目上试过，而那个项目自己的使用没有证实它。技能比较合适：工作开始漏掉时你拿起它，没有漏掉时你放下它。

旧标准的全文保留成参考文档：[open-work-tracking](../../../../core/open-work-tracking.md)。UDS 不再安装它。本技能放的是其中值得保留的部分。

## 什么时候用、什么时候不用

先找出真正的问题是哪一个。去问用户。不要为了一个没有人遇到的问题去开一份追踪清单。

| 出了什么问题 | 什么有帮助 |
|---|---|
| 做事做到一半冒出新想法，没有便宜的地方可以放 | 一个只要两个字段的收件点 |
| 某个项目暂停「等待中」，之后没人知道在等什么 | 在等待旁边写下解除条件 |
| 已规划的项目没动工，时间过去，没有东西指回它 | 一个日期，或定期看一眼清单 |

三个都不是真的，就停下来并说明。项目已经有 issue 追踪器或项目看板、而且在那里没有漏掉东西，就继续用它。没有人读的第二份清单，只是多一个漏掉工作的地方。

## 工作流程

### 1. 收件：两个字段

写下日期和一句话。不要多写。

| 日期 | 内容 |
|---|---|
| 2026-10-30 | 确认结构调整之后导出作业还有没有在跑 |

这一步不要问分类、优先级或负责人。那些等整理清单时再决定。必填字段多一个，大家就不再用这份清单。

### 2. 等待：写下什么会解除它

每个标为「等待中」的项目要有两样东西：在等什么，以及什么事件结束这个等待。优先选机器看得到的事件：日期、会出现的文件、标签、标识符。

| 项目 | status | asked-at | waiting for | release |
|---|---|---|---|---|
| 厂商报价 | asked-awaiting | 2026-10-27 | 厂商的回复 | 文件 `quotes/vendor-a.md` 存在 |

写明是哪一种等待：

- `not-yet-asked`：请求已经拟好或决定好，还没有人送出。点名那份草稿或那个命令，送出它就解除这个等待。
- `asked-awaiting`：已经送出，还没有回音。写 `asked-at`（含年份的完整日期）。有年龄的项目可以在阈值到了时重新浮现，没有年龄的不行。

等待的是另一个项目里的东西，就写成 `<项目>:<对象>`，例如 `uds:v6.15.0` 或 `vibeops:docs/handoff.md`。项目是逻辑名称，绝不是某一台机器上的目录。

### 3. 下一步：要点名东西

下一步至少点名一个读的人找得到的东西：文件路径、测试名称、命令，或需求标识符。「继续」和「处理剩下的」什么都没点名。

| 弱 | 较好 |
|---|---|
| 继续做迁移 | 运行 `npm run migrate -- --dry-run`，并读 `migrations/0042.sql` |

已经问过、在等回复的项目，可以把那个回复当作下一步。这时它需要 `asked-at`、在等什么、什么解除它。

### 4. 整理清单：三个出口

挑一个固定的日子整理收件的项目。每个项目去三个地方之一：

1. 变成规格或被追踪的项目。
2. 进入要做的工作清单。
3. 丢掉，并写一句为什么。

停在未整理状态超过大约两周的项目，要在报告里被点名。没有理由的丢弃，看起来和被误删的项目一模一样。

### 5. 报告：说出你看不到的部分

报告「还有 N 项未完成」时，也要说你看了几个来源、有几个看不到。看不到的来源不是零。没有这句话的报告，读起来像是完整的。

在回合结束、控制权交回给人的时候印出报告。报告绝不能挡住回合。「还有工作没做完」几乎永远为真，而一个永远红灯的检查会被关掉。

### 6. 你看不到的事实

有些事实，助手没有任何来源可以读：消息有没有寄出、对方有没有回复、有没有核准。要手写它们，必须附三样东西：谁看到的（`observed-by`）、何时（`observed-at`，含年份），以及值是 `yes`、`no` 或 `unknown`。`unknown` 是正式的值，单独计数，永远不算完成。每笔观察都显示年龄。时间戳只说有人看过一次，不说现在仍然如此。

版本控制、规格标记或 CI 结果已经说明的事，不要手写。

### 7. 选用：运行参考检查

UDS 在 CLI 里附了这些规则的参考检查程序：

```bash
uds open-work next-action [files...]   # 每个下一步都有点名东西吗？
uds open-work waiting [files...]       # 每个等待都有解除条件吗？
uds open-work observations [files...]  # 手写的事实都有时间戳吗？
uds open-work self-test                # 检查程序自己遇到坏样本还是会失败吗？
```

检查程序靠字段名称找字段，例如 `status`、`asked-at`、`waiting for`、`release`（上面的表格用的就是这些）。你的表格用别的词，就在 `uds.project.yaml` 的 `open_work` 下面声明。

结束码 0 表示没有违反，1 表示有违反，2 表示检查程序判定不了。2 不是通过。干净的结果只涵盖它认得的词。词汇是第一版的猜测，没有在真实使用上调整过。

## 放在哪里

放在你的项目本来就会看的地方：issue 追踪器、项目看板、repo 里的一个文件。UDS 不替你选。两个性质重要：那个地方受版本控制、或至少每个需要它的会话都读得到，而且不是只放在某一个人私有的助手记忆里。等待另一个项目的工作，要记在两个项目的会话都读得到的地方。

## 本技能不宣称的事

- 上面的规则来自一个项目。UDS 没有证据显示它们对其他项目有效。
- 阈值（两个字段、两周、观察七天算旧）是第一版的判断，不是量测。
- 检查程序读的是表格和清单的结构。它分辨不出一则记录是不是真的。

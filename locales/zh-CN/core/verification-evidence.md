# 验证证据标准

**版本**: 1.4.0
**最后更新**: 2026-11-28
**适用范围**: 所有 AI 辅助开发工作流
**范围**: universal
**灵感来源**: [Superpowers](https://github.com/obra/superpowers) — verification-before-completion (MIT)

---

## 目的

建立"铁律"：无验证证据不可声称完成——并确保**证据本身站得住脚**。本标准防三种不同的失败：

1. **无证据就宣称成功**——代理断言它从未查过的事（Iron Law）。
2. **证据撑不起它的主张**——代理**确实查了**，而查询工具静默地没有运作（证据有效性，v1.2.0 新增）。
3. **主张只有作者自己一个证人**——写下主张的那一位，同时决定它成不成立（非作者裁决，v1.4.0 新增）。

第一种是幻觉的一种，**第二种不是**——没有任何东西被捏造，是一个真实的命令产生了真实的输出，而那个输出的意思不是它看起来的意思。**第三种也不是**——作者可以诚实、工具可以健康，但只由提出者自己裁决的主张，等于没有被裁决。三者殊途同归：一个不成立的完成声明。

## 术语表

| 术语 | 定义 |
|------|------|
| 验证证据 | 验证命令执行及其结果的结构化记录 |
| 铁律 | 绝对规则：无证据 = 不可声称完成 |
| RED-GREEN 循环 | 通过显示测试修复前失败、修复后通过来证明 Bug 修复 |
| 退出码 (Exit Code) | 命令的数字返回值。**"`0 = 成功`"是工具的惯例，不是保证** —— 见"证据有效性" |
| 环境层次 (Environment Layer) | 该证据是从哪个环境收集而来（`local` / `uat` / `prd`） |
| 证据有效性 (Evidence Validity) | 证据*本身*是否可信 —— 即验证命令究竟有没有真的执行、有没有真的测到它声称测到的东西 |
| 工具静默失败 (Silent Tool Failure) | 验证命令根本没跑起来，或跑了但什么都没测到，却产生了与真实结果无从分辨的输出 |
| 证据新鲜度 (Evidence Freshness) | 证据是否由一次在受测代码、提示词或配置*最近一次编辑之后*执行的运行所产生 —— 而不是沿用针对较早状态的运行结果 |
| 裁决者 (Adjudicator) | 决定一项主张是否成立的一方。绝不是该主张的作者（VE-013） |
| 裁决结果 (Adjudication Outcome) | 三者择一：**证实**（Confirmed）、**推翻**（Refuted）、**无法判断**（Undecidable）—— 见"非作者裁决" |
| 被检物指纹 (Subject Fingerprint) | 能指认"被检查的究竟是哪一份东西"的标识（内容哈希、修订版本号）—— 让第三方能判断它此后有没有变动 |
| 裁判 (Judge) | 一个项目里决定"对不对"的东西：测试、断言、验收场景、校准集、检查器（VE-018、VE-019） |

## 铁律

> **无验证证据 = 不可声称完成。**

代理声称"已完成"不是证据。验证必须是可独立执行且产生可观察输出的。

### 非证据的声明

以下声明**不构成**验证证据：

| 声明 | 原因 |
|------|------|
| "已完成" | 无可观察的输出 |
| "应该可以了" | 未执行验证 |
| "我改了代码" | 修改 ≠ 验证 |
| "测试应该会通过" | 预测 ≠ 事实 |
| "命令返回 0。" | 仅在该命令有可能测到它所主张的事时才成立 —— 见"证据有效性" |

## 证据格式

每次验证必须产生结构化的证据记录：

```json
{
  "command": "pnpm test -- --filter core",
  "exit_code": 0,
  "output": "Tests: 47 passed, 0 failed\nDuration: 3.2s",
  "timestamp": "2026-03-20T14:30:00Z",
  "environment_layer": "local"
}
```

### 必需字段

| 字段 | 类型 | 必需 | 描述 |
|------|------|------|------|
| `command` | string | 是 | 实际执行的验证命令 |
| `exit_code` | number | 是 | 命令的退出码。**须依"证据有效性"解读 —— 此字段是一项主张，不是事实** |
| `output` | string | 是 | 命令输出（截断至 2000 字符，保留关键信息） |
| `timestamp` | string | 是 | ISO 8601 格式的执行时间 |
| `environment_layer` | string | 条件性 | 该证据来自哪一层（`local` / `uat` / `prd`）。**任何具外部服务依赖的 AC（短信、支付、IdP）均为必需**；未填写时，该 AC 的验证层级视同仅限于 local |
| `subject_fingerprint` | string | 条件性 | 被检物的指纹（内容哈希、修订版本号；工具版本也值得记）。**任何影响决策且依 VE-013 裁决的主张均为必需**，其余情况选填（VE-017） |
| `rerun_method` | string | 条件性 | 第三方如何重跑这项检查，不必信任本记录就能得到结果（命令或精确步骤）。**与 `subject_fingerprint` 同条件必需**（VE-017） |

## 证据类型

| 类型 | 适用场景 | 示例 |
|------|----------|------|
| **测试结果** | 功能开发、Bug 修复 | `npm test` 输出 |
| **类型检查** | 静态类型的代码库 | `pnpm tsc --noEmit` 无错误 |
| **构建成功** | 编译、打包 | `npm run build` 的 exit code 0 |
| **Lint 通过** | 代码质量 | `npm run lint` 无错误 |
| **RED-GREEN** | Bug 修复 | 修复前失败 → 修复后通过 |
| **健康探测** | 已部署的服务 | `curl https://<service>/health` —— 须声明 `environment_layer`；对 `localhost` 的探测验到的是本机 process，不是那个部署 |
| **手动验证** | UI 变更、视觉效果 | 截图或屏幕录像 |

## 环境层次

> **铁律（环境）**：验收前，必须先确立*此环境层次究竟有能力验证此流程的哪些维度*。

环境无法演练到的维度，测试通过也证明不了什么。在 `local` 用 mock 的支付网关跑过，并没有验证支付集成 —— 验到的是那个 mock。因此证据必须声明它是在哪里收集的。

| 层次 | 含义 |
|------|------|
| `local` | 开发机或 CI；外部依赖通常为 mock 或 stub |
| `uat` | 使用真实（或 sandbox）外部服务的 staging 环境 |
| `prd` | 生产环境 |

对于依赖外部服务的 AC，仅有 `local` 证据**不足采信**：要么补上 `uat`/`prd` 证据，要么明确声明此缺口。见 VE-005 / VE-006。

> 该声明应写入项目的**环境分层责任矩阵**（`docs/testing/environment-stratification-matrix.md` 或测试计划）—— 这是由 `deployment-standards` 标准所定义的逐项目交付物，用以回答"哪些测试流程能在哪个环境中被完整验证？"。无法验证的组合应在该处标记 ⚠️/❌，而不是任由一次通过的 local 执行把它们含混带过。

## RED-GREEN 循环

对 Bug 修复与回归测试，验证必须同时展示"失败"与"修好"：

### 步骤 1：RED —— 证明 Bug 存在

在修复**之前**执行测试，确认它会失败：

```json
{
  "command": "pnpm test -- parser.test.ts",
  "exit_code": 1,
  "output": "FAIL: expected null to equal { name: 'test' }",
  "timestamp": "2026-03-20T14:25:00Z"
}
```

### 步骤 2：应用修复

进行代码变更。

### 步骤 3：GREEN —— 证明修复有效

在修复**之后**执行测试，确认它会通过：

```json
{
  "command": "pnpm test -- parser.test.ts",
  "exit_code": 0,
  "output": "PASS: 12 tests passed",
  "timestamp": "2026-03-20T14:28:00Z"
}
```

### 步骤 4：两者都记录

证据记录必须同时包含 RED 与 GREEN 两个阶段。

## 证据有效性

> **证据本身会骗人。要验的不只是主张，还有证据本身。**

铁律拦下的是"**没有**证据就声称成功"。它拦不住反向的失败：代理**确实**跑了验证，命令**确实**返回了，`exit_code`**确实**是 `0` —— **而输出毫无意义**，因为那道命令根本没测到任何东西。

这不是幻觉。幻觉是虚构你没查过的事。这是反过来：**你查了，而那个查询工具骗了你。** `anti-hallucination` 标准覆盖不到这一块 —— 该标准的每一条禁令都是某种形式的"不要编造"，而这里没有任何东西被编造。

### 五条有效性规则

**1. 只有在"成功时返回 0"的工具上，`exit_code = 0` 才代表成功。**

这个惯例近乎普世，正因如此才无人质疑。当一个工具在受测情境下**按设计**就是会失败时，它的非零退出码并不携带任何关于受测对象的信息 —— 该读的是*输出*。反向亦然：非零退出码并不足以确立受测对象是坏的。

**2."输出为空"/"未找到"/`0` 不等于"它不存在"。**

在断定"不存在"之前，先确立查询工具*成功执行过*：它不是 `command not found`，不是被拒绝权限，它的参数也没有被中间的 shell 吃掉。**先验证查询工具能用，再去相信查询结果的沉默。**

**3. 用来检测存在与否的命令，不得丢弃 stderr。**

抑制 stderr（`2>/dev/null` 及其等价写法）消音掉的，恰好就是那个本来会报告"这个工具坏了"的通道。失败于是穿上了与真阴性一模一样的外衣。

**4. pipeline 的退出码不属于其中任何单一阶段。**

在 `set -o pipefail` 下，`producer | grep -q pattern` 会继承 `producer` 的非零值，与 `grep` 有没有匹配到无关。当决策取决于内容时，**先捕获输出，再评估它** —— 不要让一个 pipeline 把两个问题压缩成一个数字。

**5. 证据必须晚于它所验证对象的最后一次编辑。**

在受测代码、提示词或配置最近一次变更*之前*捕获的验证运行，确实证明了某件事 —— 只是不是被主张的那件事。这个陷阱是静默的：完整套件跑出全绿，之后某样东西被编辑了（一个提示词、一个配置值、一个阈值），而在那次编辑之后只跑了较窄的检查（lint、部分套件）—— 但较早那次全绿的运行却被引用为当前状态的证据。**证据是在最后一次编辑之后捕获的单次新鲜执行，而不是恰好通过的最近一次执行。**

### 过期证据 —— 一种失效样态

规则 1–4 假设证据**在正确的地方**被收集且被正确解读。它们没有回答"**什么时候**"这个问题。一个执行了、测量正确、也返回真结果的命令，依然可能撑不起一个完成声明 —— 如果它跑完之后有东西又变了。

**失效样态**：完整测试套件跑过且通过。之后，某个提示词或配置值被编辑 —— 没有任何测试直接覆盖那次编辑。提交前只跑了 `lint`，也通过。commit 引用"测试通过"作为证据。接着 CI 红在一个钉住刚刚被改掉那份内容的测试上 —— 那个"通过"的套件，跑的是一个在主张被提出时已经不存在的版本。

### 此失效模式的实例证据

以下是某 AI 代理于 2026-07-17 实际执行的验证命令，每一道都导出了自信而错误的结论，并被当成事实报告出去：

| 验证命令 | `exit_code` | 输出 | 实际真相 |
|---|:---:|---|---|
| `sudo -n find /backup/immich -type f 2>/dev/null \| wc -l` | **0** | `0` | `sudo` 因无 tty 而失败，`2>/dev/null` 吃掉了错误信息，空输入让 `wc -l` 打印出 `0`。**实际存在 31 个文件。** 被报告为"备份是空的" |
| `gpg --list-packets <valid-file.gpg>` | **≠ 0** | 格式良好的 packet 列表 | 该主机**按设计**就不持有私钥；gpg 在此情境必定以非零退出。**该文件是有效的。** 据此删掉了一份完好的加密备份 |
| `gpg … \| grep -q "tag=1"`（在 `pipefail` 下） | **≠ 0** | grep *确实*匹配到了 | pipeline 继承了 gpg 的非零值；匹配与否根本无关。**第二次删掉了一份完好的备份** |
| 以双引号包住、通过 SSH 执行的 `grep -c "${VAR}/path" file` | **0** | `0` | `${VAR}` 被*本地* shell 展开成空字符串；远端的 grep 搜的是错的文本 |
| `gpg --import key.asc 2>/dev/null` | — | （空） | gpg **根本没安装**；`command not found` 进了被抑制的 stderr |
| `until ! ssh host 'systemctl is-active svc'; do …` | — | 循环退出 | **SSH 连接失败与服务已结束，产生的退出码一模一样。** 事后读到的"结果"是前一次执行留下的过期值 |
| 以非特权用户执行 `du -sh /data/*` | **0** | `4.0K` | 读不到的目录被报告成几近空目录，而非报告为错误 |
| 以 `case "$tag" in *M*)` 搜索 monthly 快照 | **0** | （无匹配） | 该 tag 的实际值是 `monthly` —— 没有大写 `M`。差点变成"没有任何 monthly 快照" |

**其中四笔 `exit_code = 0` 却是错的；两笔 `exit_code ≠ 0` 却是对的。** 此字段在两个方向上都不可靠 —— 而在那两笔非零的案例中，遵循 VE-002（"标记验证失败、触发修复循环"）摧毁了一份健康的产物。

> **来源说明（Provenance）**：所有实例均出自单一代理（Claude Opus 4.8）单日的工作，记录于 AsiaOstrich XSPEC-340。此样本密集但狭窄。它是作为证据而非证明提出的 —— 但请注意，上述每一项失败都源自*工具本身的语义*（sudo、gpg、pipefail、POSIX 退出码），而非任何模型特性，因此任何驱动同一批工具的代理都暴露在同样的陷阱下。

## 信任规则

| 规则 | 说明 |
|------|------|
| 代理说"完成"但没有 `verification_evidence` | 标记为**未验证** |
| 有 `verification_evidence` 但 `exit_code ≠ 0` | 标记为**验证失败** —— **除非**已知该工具在受测状态下本就会以非零退出（证据有效性规则 1），此时改以输出判定 |
| `exit_code = 0`，但该命令不可能测到它所声称的事 | 标记为**未验证** —— 一道在错的地方执行、或根本没执行的通过命令，不是证据 |
| 证据主张"不存在"（`0`、空输出、"未找到"） | 在证明查询工具成功执行过之前，标记为**未验证** |
| 证据的时间戳早于它所验证对象的最近一次编辑 | 标记为**过期** —— 在编辑之后重跑；不得引用较早的通过结果 |
| 影响决策的主张只有其作者的话或作者的自我复查 | 结果为**无法判断** —— 作者自己的检查不算裁决（VE-013） |
| 多个验证步骤 | **全部**步骤都必须通过 |
| 代理提供的是错误命令的证据 | 标记为**未验证** |

## 非作者裁决

> **声明的作者不是它的裁判。** 只有作者自己检视过的主张，是被提出，不是被裁决。

铁律要求证据。证据有效性问证据站不站得住。两者都没问：**谁决定**证据撑得起主张？当写下主张的那一位同时读了证据并宣布它足够时，这个主张只有一个证人，而那位证人与答案有利害关系。本节补上这个缺漏的问题。八条规则是 VE-013 至 VE-020。

本节管的是**影响决策**的主张："文件存在""测试通过""没有这个漏洞""任务已完成"。顺口提一句的话不需要裁决者。

### 八条规则

**1. 影响决策的主张由非作者裁决（VE-013）。**

优先顺序：(a) 读取真实事物的**确定性工具**，例如测试运行器、类型检查器、文件系统查询；(b) 没有工具能判定时，交给**不带作者任何上下文、并被要求试图推翻该主张的全新 agent**。作者自己的复查可以当预检，但**不算裁决**。

**2. 结果只有三种，而"无法判断"既不是为假也不是通过（VE-014）。**

| 结果 | 含义 | 对应既有的状态用语 |
|---|---|---|
| **证实**（Confirmed） | 裁决者检视了实物，主张成立 | 证据成立，不降级 |
| **推翻**（Refuted） | 裁决者检视了实物，主张不成立 | **验证失败** —— 前提是 VE-007 已确认工具健康 |
| **无法判断**（Undecidable） | 裁决者无法判断 | **未验证**与**过期** |

无法判断的结果，不得记为"为假""不存在"或"通过"。**查询工具故障，以及裁决者自身发生错误，一律归无法判断** —— 不是推翻，也不是证实。

**3. "全部证实"不等于通过（VE-015）。**

一组主张即使全部被证实，只要那些主张都是琐事，就没有通过。可由已知信息推得的主张、重复另一项主张的主张、只指涉自己的主张，**都不计入**。至少要有一项实质主张被证实。何谓实质、需要几项，由采用项目定义；本标准只定原则。

**4. 被推翻的主张会被记住；已证实的主张随被检物过期（VE-016）。**

被推翻的主张保留为**已知为假**，并附上它被检查时的被检物指纹。指纹未变动之前，不得换个说法再提出同一个主张。依赖被推翻主张的主张，随之失效。已证实的主张，在其被检物指纹变动后须**重新验证**。

**5. 记录要指明被检物与重跑方式（VE-017）。**

任何依 VE-013 裁决的主张，其证据记录须带 `subject_fingerprint` 与 `rerun_method`，让第三方可以重跑检查，而不是信任结论。

**6. 作者不修改自己的裁判（VE-018）。**

新增断言与验收场景一律允许。**删除、放宽或跳过**断言、场景或检查，由非作者裁决，实务上就是人。让裁判变宽松的修改，正是作者有动机去做的那一种修改，所以也是作者不得单独采纳的那一种。

**7. 裁判在被信任之前先校准（VE-019）。**

引用某验证机制的通过结果当证据之前，先在一次性副本中注入**一个已知错误**，确认该机制抓得到。每个错误记录：**抓到（caught）**、**漏网（escaped）**或**无法判断**。**没有实际注入成功的错误判无法判断，不得判通过。** 记录每个错误由哪一层抓到；瞄准某一层的错误，必须对更早的层不可见，否则这次运行只是把更早那一层又测了一次。错误注入的技术见[突变测试](../../../core/mutation-testing.md)。

**8. 单次成功不代表稳定（VE-020）。**

声称某事"稳定""可靠"或"会成功"，须附**k 次重跑全数成功的结果，并写出 k**。单次成功，或只报平均成功率，不支持这些词。证据只有一次运行的主张，判**无法判断**。重跑中有成有败，结果是**不稳定**，不稳定不算通过。k 要多大，由采用项目决定。

### 本节不决定什么

- **用哪个工具、哪个 agent、哪个模型。** 原则是谁裁决，不是用什么裁决。
- **门槛数值。** VE-015 的"实质"与 VE-020 的 k 由采用项目决定。写在这里的数字只会贴合某一个项目的证据，套不到别的项目。
- **裁决者一定对。** 全新 agent 也可能错。VE-019 的用意就是：任何裁判在被看见抓到已知错误之前，都不被信任。

## 窄覆盖必须登记，而非仅揭露

证据有效性与环境分层责任矩阵都允许一个被记录下来的缺口 —— 一个无法验证某个维度的环境层次、一项测量范围窄于它所支撑主张的检查。单纯写下这个缺口本身并不够：文字说明比真正补上缺口便宜，而一个从未被重新检视的揭露，会悄悄变成"这份证据其实撑不起它被用来支撑的主张"的永久借口。

**要求**：任何这一类已记录的缺口，必须同时登记到一份**带到期日的例外清册** —— 独立于标准正文或矩阵条目本身之外 —— 指名缺口、其成因，并附上复核或到期日期。只有一则脚注而没有对应清册条目，不满足本条。

**可证伪条件**：一则清册条目连续两期审查都未变动，代表该揭露已经变成逃生口，本条对该条目失效 —— 不是"部分满足"，是失效。清册放在哪里、什么格式、多久审一次，留给采用项目自行决定；本标准只要求"有这么一份东西存在，且条目会动"。

这与 [class-level-fix](../../../core/class-level-fix.md) 的窄覆盖规则是同一条要求，套用在验证证据而非类别层检查上：两种情况下，一个永远不必改变的揭露都不是揭露，是一份穿着揭露外衣的永久豁免。

## 规则

| ID | 触发条件 | 动作 | 优先级 |
|----|----------|------|--------|
| VE-001 | 代理报告成功但无 verification_evidence | 降级为 `done_with_concerns` | Critical |
| VE-002 | 证据中 `exit_code ≠ 0` | 标记验证失败、触发修复循环 —— 须**先**确认该工具在此状态下成功时会返回 0（见 VE-007） | High |
| VE-003 | Bug 修复缺少 RED-GREEN 循环 | 要求补上 RED 与 GREEN 两份证据 | High |
| VE-004 | 输出超过 2000 字符 | 截断，但保留错误信息与摘要行 | Medium |
| VE-005 | AC 具外部服务依赖（短信、支付、IdP） | 证据必须声明 `environment_layer`；仅有 local 证据不足采信 | Required |
| VE-006 | 具外部依赖的 AC 被标为完成，却无 `environment_layer` | 降级为 `done_with_concerns`；要求补上层次声明，或在 environment-stratification-matrix 中补上 ⚠️/❌ 条目 | High |
| VE-007 | 验证工具在受测状态下**按设计**就会以非零退出 | VE-002 不适用。改以输出内容判定；**不得对健康的产物触发修复循环** | Critical |
| VE-008 | 证据主张"不存在"（`0`、空输出、"未找到"） | 在证明查询工具成功执行过之前一律无效。以不抑制 stderr 的方式重跑 | High |
| VE-009 | 存在性／不存在性检查抑制了 stderr（`2>/dev/null` 或等价写法） | 证据不成立。以 stderr 可见的方式重跑 | High |
| VE-010 | 证据的 `exit_code` 来自 pipeline（尤其是在 `pipefail` 下） | 该退出码不归属于任何单一阶段。改为捕获输出并评估内容 | Medium |
| VE-011 | 证据的执行时间戳早于它所声称验证之产物的最近一次编辑 | 标记为**过期** —— 不是当前状态的有效证据；要求在编辑之后捕获一次新鲜的单次运行 | High |
| VE-012 | 已记录的证据/覆盖缺口（environment-stratification ⚠️/❌，或任何窄于其所支撑主张的检查）在带日期的例外清册中没有条目 | 仅有揭露不满足本规则 —— 要求一则已登记、带日期、指名缺口及其复核/到期日的清册条目 | Required |
| VE-013 | 影响决策的主张只由其作者（或作者的自我复查）裁决 | 结果为无法判断。要求确定性工具，或不带作者上下文、被要求试图推翻该主张的全新 agent | Critical |
| VE-014 | 记录裁决结果 | 只有证实／推翻／无法判断三种。无法判断绝不记为为假或通过；查询工具故障或裁决者自身错误一律为无法判断 | Critical |
| VE-015 | 一组主张全部被证实 | 除非至少一项实质主张被证实，否则不算通过；可推得的、重复的、自我指涉的主张不计入 | High |
| VE-016 | 被推翻的主张被再次提出，或已证实主张的被检物已变动 | 被推翻的主张保留为已知为假并附被检物指纹；被检物变动前不得重提同一主张；已证实的主张在被检物变动后须重验 | High |
| VE-017 | 依 VE-013 裁决之主张的证据缺 `subject_fingerprint` 或 `rerun_method` | 要求两者皆备，让第三方不必信任结论就能重跑检查 | Required |
| VE-018 | 裁判（测试、断言、场景、检查器）的作者删除、放宽或跳过其中一部分 | 作者不得自行采纳；由非作者（人）裁决。新增断言与场景一律允许 | Critical |
| VE-019 | 引用某验证机制的通过结果当证据，但它从未被证明抓得到已知错误 | 先在一次性副本注入已知错误；每个错记为 caught／escaped／无法判断；没注入成功的错为无法判断；记录每个错由哪一层抓到 | High |
| VE-020 | 声称"稳定""可靠"或"会成功" | 要求 k 次重跑全数成功并写出 k；单次或只有平均成功率为无法判断；有成有败为不稳定，不算通过 | High |

## 输出截断指引

当验证输出超过 2000 字符时：

1. **保留**：错误信息、失败摘要、测试计数、最终状态行
2. **移除**：冗长的进度输出、通过测试的 stack trace、重复行
3. **标记截断**：在被移除内容处加上 `[... truncated ...]`

## 示例

### 良好：完整的证据

```yaml
verification_evidence:
  - command: "pnpm test"
    exit_code: 0
    output: "Test Suites: 12 passed\nTests: 147 passed\nTime: 8.3s"
    timestamp: "2026-03-20T14:30:00Z"
  - command: "pnpm lint"
    exit_code: 0
    output: "No issues found"
    timestamp: "2026-03-20T14:30:05Z"
```

### 不良：没有证据

```yaml
status: success
message: "I've completed the task and everything should work now."
# ❌ No verification_evidence — violates Iron Law
```

### 不良：撑不起自身主张的证据

```yaml
claim: "The backup directory is empty — backups are not running."
verification_evidence:
  - command: "sudo -n find /backup/immich -type f 2>/dev/null | wc -l"
    exit_code: 0
    output: "0"
    timestamp: "2026-07-17T13:05:00Z"
# ❌ Passes the Iron Law: evidence exists, exit_code is 0, output is concrete.
# ❌ Violates VE-008, VE-009, VE-010:
#      - claims absence without showing the query tool ran (VE-008)
#      - suppresses the stderr that said "sudo: a terminal is required" (VE-009)
#      - the exit code is the pipeline's, i.e. `wc -l`'s — `find` never ran (VE-010)
#    31 files were present. Directory listed as empty because nothing looked.
```

### 良好：同一道检查，改为有效版本

```yaml
claim: "The backup directory holds 31 files."
verification_evidence:
  - command: "ssh host 'sudo find /backup/immich -type f | wc -l'"   # stderr not suppressed
    exit_code: 0
    output: "31"
    timestamp: "2026-07-17T13:07:00Z"
    environment_layer: "prd"
# ✅ stderr would have surfaced a sudo/permission failure instead of printing 0
# ✅ single-quoted so ${...} is not expanded by the local shell before transit
```

### 不良：只由作者裁决的主张

```yaml
claim: "All tests pass."
adjudicator: "the agent that made the change"
note: "I re-read the diff and ran the suite in my head; it looks fine."
# ❌ 违反 VE-013：作者是唯一的证人，也没有任何工具执行过。
#    结果：无法判断。不得算为通过，也不得算为失败。
```

### 良好：同一个主张，经过裁决

```yaml
claim: "All tests pass."
adjudicator: "test runner (deterministic tool)"
outcome: confirmed
verification_evidence:
  - command: "npm test"
    exit_code: 0
    output: "Tests: 147 passed, 0 failed"
    timestamp: "2026-11-28T09:30:00Z"
    subject_fingerprint: "commit 9f3c2ab"
    rerun_method: "git checkout 9f3c2ab && npm test"
# ✅ 由非作者裁决，且第三方可以重跑（VE-013、VE-017）
```

## 相关标准

- [反幻觉标准](anti-hallucination.md) —— 互补标准。它防的是*捏造*的主张（断言从未查证过的事）；证据有效性覆盖的是反向的失败 —— **确实**查证过、但查证工具静默失效的主张。
- [系统化调试](systematic-debugging.md) —— 当证据显示确实有失败时，如何往下调查

- [测试治理](test-governance.md) —— 规定哪些测试必须存在，因而也就规定了哪些证据必须存在
- [测试标准](testing-standards.md) —— 产生多数证据的那些测试是怎么写的

- [验证预言机](../../../core/verification-oracle.md) —— 什么是正确答案、由谁拥有；VE-013 至 VE-020 规定的是谁可以判定答案已经达成
- [自我审查协议](../../../core/self-review-protocol.md) —— 作者自己的检查。可作预检；在 VE-013 之下它不算裁决

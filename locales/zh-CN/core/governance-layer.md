# 治理层标准

> **语言**: [English](../../../core/governance-layer.md) | [繁體中文](../../zh-TW/core/governance-layer.md) | 简体中文

**版本**: 1.1.0
**最后更新**: 2026-08-20
**适用范围**: 所有具有多 Agent 或多角色 AI 工作流程的软件项目
**范畴**: universal
**产业标准**: 无（UDS 原创）

---

## 目的

治理层为项目中所有 Agent 与角色提供共同锚点：
Vision（方向）→ Mission（边界 + 红线）→ Goals（可量测的 KPI）。

它是 **Standard #0**：在所有其他标准之前评估。当本标准与其他领域标准发生冲突时，本标准优先。

---

## 三层架构

### Vision（愿景）

| 字段 | 要求 |
|------|------|
| 格式 | 单一句子，≤ 50 tokens |
| 内容 | 长期方向；永恒不变；不含量测指标 |
| 变更频率 | 每年审查 |

**示例**：
> "成为全球软件团队最值得信赖的 AI 开发工作流程标准。"

---

### Mission（使命）

| 字段 | 要求 |
|------|------|
| 格式 | 3–5 项承诺陈述 + 红线清单（合计 ≤ 300 tokens） |
| 内容 | 我们做什么 / 不做什么；含触发条件与处置动作的红线 |
| 变更频率 | 每季审查 |

**红线必备字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | 字符串 | 唯一标识符（例如：R1、GUARD-001） |
| `category` | 字符串 | 分类（quality / safety / compliance / ethics） |
| `clause` | 字符串 | 人类可读的禁止或要求陈述 |
| `action` | 枚举 | `block` \| `warn` \| `escalate_to_human` 之一 |

---

### Goals（目标）

| 字段 | 要求 |
|------|------|
| 格式 | KPI 清单，≤ 500 tokens |
| 变更频率 | 每个 Sprint 校准 |
| 可否证性 | 每个 KPI 必须可量测——禁止使用「改善」、「提升」等模糊词汇 |

**KPI 必备字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | 字符串 | 唯一标识符（例如：KPI-01） |
| `metric_name` | 字符串 | 追踪的指标名称 |
| `threshold` | 字符串 | 量化目标（例如：≥ 95%、< 200 ms） |
| `measurement_method` | 字符串 | 量测方式与时机 |

---

## 优先顺序

治理层对所有其他标准具有**更高优先权**。冲突时的解析顺序：

1. **治理层**（本标准）— 方向、红线、KPI
2. **领域标准**（测试、提交信息、部署等）
3. **项目特定覆盖**（本地 `.standards/` 定制化）

---

## 红线格式

每条红线必须包含所有必备字段。执行动作说明：

| 动作 | 行为 |
|------|------|
| `block` | 立即停止 pipeline；不继续执行 |
| `warn` | 记录违规并继续；超过阈值时升级 |
| `escalate_to_human` | 暂停并要求人类决策后才继续 |

此外，每条红线应包含 `mission_clause_ref` 字段，参照其所强制执行的使命承诺。

---

## 评估器集成

当项目使用 AI 评估器 Agent 时，治理层提供评分锚点：

| 评估轴 | 权重 | 否决阈值 |
|--------|------|----------|
| 正确性 | 0.4 | < 0.3 → 不通过 |
| 使命对齐度 | 0.3 | < 0.3 → 不通过 |
| 目标达成度 | 0.3 | < 0.3 → 不通过 |

- **mission_alignment_score**：输出与使命承诺的对齐程度
- **goal_achievement_score**：输出推进目标 KPI 的程度
- 任何单一评估轴低于 0.3 即触发不通过，无论加权总分为何

## 风险接受（trace_only 模式）

若项目放宽人工闸门（例如 `gate.mode = trace_only`），必须在 `mission.md` 中明确撰写**风险接受条款**，包含：

| 必填字段 | 说明 |
|----------|------|
| `date` | 接受风险的日期 |
| `signatory` | 接受风险的人员或角色 |
| `gates_bypassed` | 列举所有绕过的人工闸门 |
| `risks_accepted` | 明确描述已接受的风险 |
| `review_by` | 本次接受失效、必须重新做一次判断的日期 |

若无有效的风险接受条款，pipeline **必须拒绝启动（fail-closed）**。

### 接受到期

`review_by` 已过的条款**不是有效条款**。pipeline 必须 fail closed，与完全没有条款时一模一样。

`date` 记录的是「何时接受了这个风险」，不是「何时该重新判断」。没有 `review_by`，签过一次的接受就永远有效——当初支持它的条件可能已经改变、签署人可能已经离开项目，而条款里每一个字段读起来仍然完全正确。

到期时，必须施用且只能施用下列三种处置之一，与[技术债标准 → 到期处置](tech-debt-standards.md#到期处置)所定义的三种相同：

| 处置 | 含义 |
|------|------|
| **重新接受** | 由当下的签署人重新签署，并给出新的 `review_by` |
| **撤销** | 移除该绕过，恢复人工闸门 |
| **延期** | 新的 `review_by` **与**书面理由，一起记下 |

**禁止自动延长 `review_by`。** 那会把一道 fail-closed 的闸门变成 fail-open，而所有字段看起来都还是对的——失效之所以隐形，正是因为条款仍然验证得过。

## 待裁决事项

「还没决定」是一种治理状态，不是治理的缺席。规格里的未决问题、提出但未批准的红线、没有 owner 的 KPI——每一项都是有人被期待要做的决定，而每一项对「只读已做成决定」的检查都是隐形的。

待裁决事项与已接受风险**同级受治理**：它们带时钟，而且必须可被列举。

**规则 GOV-PD-001（必要）**——项目必须声明待裁决事项**记在哪里**，以及**什么标记代表一项待裁决**：一个固定的 token（状态值、标签、字面标记字符串），不得是自由书写的散文。列举不该取决于读者猜中当初用了哪些字。三份分别写「TBD」「待拍板」「待确认」的文件，是三份无法被列举的文件；一个声明过的标记让三份都找得到。

**规则 GOV-PD-002（必要）**——列举待裁决事项时，必须同时报告总数**与**无法解析的来源份数（见[汇总报告](#汇总报告)）。「查无待裁决事项」在不知道走访集合有多大时，不带任何信息。

**规则 GOV-PD-003（必要）**——每一项待裁决事项都带一个**裁决期限日期**。到期时适用与逾期技术债相同的三种处置——**做出决定**、**撤回这个问题**、或**延期并写明理由**。禁止自动延期。

**规则 GOV-PD-004（必要）**——若没有任何东西在排程上列举待裁决事项，项目必须带一份**无人看管声明**，写明负责人、复查频率与最后复查日期——与技术债登记表被要求的两态规则相同。没有被列举是可接受的；没有被列举又没有声明则不可接受。

> 一项没有日期的待裁决事项，在行为上与「决定不做」完全相同。差别只在于待裁决的形式让人以为还有人会去看它。

## 汇总报告

每一份治理报告——合规摘要、闸门报告、KPI 汇总、红线扫描——都是对某个集合提出的宣称。这个宣称的价值，恰好等于它对「自己判不了什么」的交代的价值。

**规则 GOV-RPT-001（必要）**——报告必须打印三个数字，不能只打印两个：**通过**、**失败**、**判不了**（无法解析的文件、缺字段、来源不可达、不支持的格式）。

**规则 GOV-RPT-002（必要）**——「判不了」**不得**并入「通过」，也**不得**省略。一份解析不了的文件不是一份干净的文件。只打印「N 项检查通过」的报告，不论 N 是多少都不合规。

**规则 GOV-RPT-003（必要）**——报告必须写出自己的**分母**以及分母是怎么推导出来的。范围来自硬编码清单的报告，是一份关于那份清单的报告，不是关于这个项目的报告：清单之外的东西全部腐坏，它照样是绿的。要用「走访并排除」推导集合，不要用列举——见[类别层级修正](../../../core/class-level-fix.md)。

**规则 GOV-RPT-004（必要）**——正向与负向计数分开报告；绝不合并成单一的合规分数。**一个「什么都不做」与「把工作做完」得分相同的指标，量的不是那份工作。**「11 项中通过 5 项」与「检查器从未启动」产生同一个数字，而单一分数分不出这两者。

**规则 GOV-RPT-005（建议）**——当报告的正确性取决于它自己的工具能运作时，加一只金丝雀：一个输入已知会失败、因此**必须**失败的检查。若金丝雀通过了，整份报告不可信，必须整份报告为「判不了」，而不是绿灯。

## 新鲜度指标

**规则 GOV-FRESH-001（必要）**——任何新鲜度／停滞指标都必须指名它读的是下列哪一个时钟：

| 时钟 | 回答的问题 | 可以从哪里读 |
|------|-----------|-------------|
| **编辑时间** | 这份产物上次被改动是多久以前？ | 文件 mtime、最后动到它的 commit、「最后更新」字段 |
| **对账时间** | 这份产物上次与它宣称在描述的真实来源做比对是多久以前？ | 那次比对被记下的日期——没有别的东西能提供它 |

**规则 GOV-FRESH-002（必要）**——两者**不得**共用同一个字段或同一个字段标题。它们回答不同的问题，而同一份产物可以在其中一个上满分、在另一个上任意地旧：一份今天刚编辑、内容从未与现实对过的文件，以编辑时间算是零天，以对账时间算是无上限。

**规则 GOV-FRESH-003（必要）**——只有编辑时间可取得时，报告必须把该栏标示为编辑时间，**并且**把对账时间报告为「判不了」（GOV-RPT-001）——绝不能标成新鲜，也绝不能省略不提。

**规则 GOV-FRESH-004（建议）**——对账时间只有在「由执行该比对的东西自己记下」时才有意义。事后由人手动填入的日期是一项断言，不是一次量测；请如实标示。

> 这是「单轴装多维」的失败：一个字段，被两个不同的问题读取。这个字段永远不会被抓到是错的，因为从来没有人问过它在回答哪一个问题。

## 治理文件结构

采用本标准的项目应维护以下文件：

```
governance/
├── vision.md          # 单一句子愿景陈述
├── mission.md         # 承诺 + 红线清单
└── goals.md           # KPI 清单（每个 Sprint 更新）
```

---

## 合规检查清单

- [ ] Vision 为单一句子且 ≤ 50 tokens，不含量测指标
- [ ] Mission 有 3–5 项承诺及含所有必备字段的红线清单
- [ ] 每条红线均有：id、category、clause、action
- [ ] Goals 清单存在，每个 KPI 均含：id、metric_name、threshold、measurement_method
- [ ] 没有任何 KPI 使用模糊词汇（「改善」、「提升」、「更好」）
- [ ] 若 `gate.mode = trace_only`，`mission.md` 中存在风险接受条款
- [ ] 每一份风险接受条款都有 `review_by` 日期，且没有任何一份已经过期
- [ ] 项目已声明待裁决事项记在哪里、以及哪一个固定标记代表一项待裁决
- [ ] 每一项待裁决事项都有裁决期限日期
- [ ] 待裁决事项要么被某个会执行的东西列举，要么被无人看管声明涵盖
- [ ] 每一份治理报告都分开打印「通过／失败／**判不了**」，并写出分母与分母的推导方式
- [ ] 没有任何报告把正向与负向计数合并成单一分数
- [ ] 每一个新鲜度指标都指名自己读的是编辑时间或对账时间，且两者不共用字段
- [ ] 所有 AI 评估器以 0.4/0.3/0.3 权重评分，且任一轴 < 0.3 即不通过

## 执行现实

> **本标准对它的任何一条规则都不提供检查器——不只是 1.1.0 新增的那些，也包括自 1.0.0 起就在里面的那条 fail-closed 风险接受要求。这是已知代价，写在这里，而不是留给采用者自己撞到。**
> 
> 2026-08-20 实测：`review_by`、`risks_accepted`、`gates_bypassed` **没有出现在任何程序里**——UDS CLI 没有，任何消费端也没有。那句写着 pipeline「必须拒绝启动」的条款，在它被写下来的三个半月里，**从来没有让任何一条 pipeline 拒绝启动过**。把这件事讲明白不是外加的但书，它就是本节自己的规则套用在本节身上；而本节的初稿只列出新规则为未执行，那会让人以为旧的那条有在执行。
>
> UDS 定义的是这些要求，它不提供执行这些要求的程序。想要它们被执行的采用者必须自己写那支列举器、那支三态计数报告器、那个对账日期记录器——而多数人不会写。那正是本标准所描述的失败，现在同样适用于本标准自己。
>
> 所以最低标准**不是**「去把工具做出来」，而是：**任何被记载为待裁决、已接受、或新鲜的东西，要么指向一个会执行的检查，要么明白说出没有东西在看它。** 声明「无人看管」是合规的。无人看管却不声明，才是这些规则真正禁止的唯一结果，因为只有它会让读者对「有没有东西在看」产生误解。

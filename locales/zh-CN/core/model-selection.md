# AI 模型选择策略

**版本**: 2.1.0
**最后更新**: 2026-08-11
**适用性**: 使用多模型分级的 AI 辅助开发
**范围**: 通用 (Universal)
**灵感来源**: [Superpowers](https://github.com/obra/superpowers) — subagent-driven-development (MIT)

> **翻译范围（XSPEC-355）**：本翻译只涵盖**规范性（normative）**内容。
> 说明性（informative）段落——成本优化建议、示例清单、参考资料、设计理由的叙述——
> 请参阅[英文原文](../../../core/model-selection.md)。

---

## 目的

定义两个独立决策：**选哪个模型**与**要它想多深**。两者不可压成同一轴。使用能胜任的最便宜组合，失败时沿**正确的轴**升级。

---

## 术语表

| 术语 | 定义 |
|------|------|
| 模型分级 (Model Tier) | 代表模型**推理天花板**与成本的分类等级 |
| 思考深度 (Effort Level) | **单次派工**所要求的推理深度；是请求参数，不是模型属性 |
| 推理天花板 (Reasoning Ceiling) | 超过此限度后，再多的思考时间也得不到更好的答案 |
| 规格明确度 (Specification Definiteness) | 步骤是否已定义，或仅知目标与约束 |
| 硬边界 (Hard Boundary) | 模型**完全不具备**的能力（非「做得比较差」）——如 context 容量、是否支持 effort 参数 |
| 拒绝标记 (Refusal Marker) | 在一则外观正常的回应中，表示请求被拒绝的字段 |
| 升级 (Escalation) | 在 effort 轴用尽后，沿模型轴往上移动 |

## 核心原则 — 两个正交轴

> **模型轴买的是「天花板与性格」，effort 轴买的是「这一次要它想多深」。在一轴上的选择，不决定另一轴。**

```
                        effort →   低         中          高        极高        极限
模型层级 ↓
  fast                             ·          ·           ·         ?           ?
  standard                         ·          ·           ·         ?           ?
  capable                          ·          ·           ·         ?           ?
```

每一格原则上都是合法派工：两个轴各自独立选择。

`?` 标示的格子，**本标准无法断言其可用性**——某个模型接受哪些 effort 级距是**该模型的属性**，而此处的层级名称是与厂商无关的标签，所以答案在各平台自己的「层级 → 模型」映射里，不在这张表里。不支持的级距是**硬边界**，不是「较差的选择」——见 [R3a](#r3a-硬边界)。采用者**必须**逐模型登记它接受哪些级距。

## 轴一 — 模型层级

### 选择准则

两个准则决定分层。**两者都不是「改几个文件」**。

#### 准则 1 — 推理天花板需求

这个任务是否存在**单靠更多思考时间也解决不了**的成分？

- **否** → 较低层即可胜任；用 effort 买深度，而非用钱买天花板。
- **是** → 需要更高天花板；在较低层加多少 effort 都到不了。

#### 准则 2 — 规格明确度

**这是双向准则，并非单调递增。**

| 规格状态 | 偏好 | 反向使用时的失效模式 |
|---|---|---|
| 步骤已定义、路径已知 | 字面遵循型（较低层） | 把已写死的步骤喂给高天花板型会**降低**产出质量——它会重新诠释已经决定过的事 |
| 仅知目标与约束、路径未知 | 模糊性导航型（较高层） | 把模糊任务给字面遵循型，会得到**「精确执行了错误的那句话」** |

> **为何移除「修改文件数」**：3 个文件的模块边界重新设计，比 8 个文件的机械改名更难。
> 文件数会**以固定方向**误判「深而窄」的工作——这是偏差，不是噪音。

### 三个层级

层级标识符（`fast` / `standard` / `capable`）维持不变，只有准则改变。

#### Tier 1: Fast（快速层）

**用途**：无推理天花板需求、规格完全明确的工作。

**信号**：
- 不存在「想更久也想不出来」的成分
- 步骤已写出，无需寻路
- 不需要设计判断
- 字面遵循正是想要的行为

#### Tier 2: Standard（标准层）

**用途**：需要一定推理天花板，规格大致明确但留有局部决策空间。

**信号**：
- 部分成分需要推理，但没有一项是「想更久也想不出来」
- 目标与多数步骤已定义，剩下有限的局部选择
- 需要理解模块间关系

#### Tier 3: Capable（能力层）

**用途**：需要高推理天花板，或规格仅有目标与约束、路径未知。

**信号**：
- 存在单靠更多思考时间解决不了的成分
- 路径未知；答案要找出来，不是套用
- 需要导航模糊性而非遵循文字

> **关于「大型重构」**：目标结构**已定**的大型重构**不**自动属于 Tier 3——
> 依准则 2 它是明确规格，高天花板模型的产出可能比字面遵循型更差。
> 使它升到 Tier 3 的是「目标结构**未定**」。

### 选择决策流程

```
这个任务是否存在单靠更多思考解决不了的成分？
  ├── 是 → 需要高天花板 → Tier 3 (Capable)
  └── 否 → 规格有多明确？
            ├── 步骤完全定义、路径已知   → Tier 1 (Fast)
            ├── 目标＋多数步骤、局部选择 → Tier 2 (Standard)
            └── 仅有目标与约束           → Tier 3 (Capable)
接着，独立地：选择 effort 级距（轴二）。
```

## 轴二 — Effort（思考深度）

Effort 是**单次派工的参数**，不是模型属性。同一个模型在 `low` 与在 `max` 不是同一个工作者。

### 与厂商无关的 effort 级距

各平台自行将这些标签映射至其参数。**标签是契约，映射是在地的。**

| 级距 | 语义 | 典型用途 |
|---|---|---|
| `low`（低） | 最少斟酌，主要依模式作答 | 机械性编辑、查询、格式化 |
| `medium`（中） | 一般斟酌；默认值 | 多数已定义的实作工作 |
| `high`（高） | 延伸斟酌，作答前考虑替代方案 | 含局部决策的整合工作 |
| `very-high`（极高） | 探索并淘汰候选方法 | 设计、审查、非显而易见的除错 |
| `max`（极限） | 该模型可用的最大深度 | 升级模型轴前的最后一次尝试 |

**并非每一层都支持每一个级距。** 是否支持 effort 参数是**硬边界**，不是质量梯度——见 [R3a](#r3a-硬边界)。平台的「层级 → 模型」映射**必须**登记每个模型接受哪些级距。

### 失败诊断 — 深度不足或天花板不足？

> **任务失败时，先判断是哪一轴不足。两者的补救方式不可互换。**

| 观察到的现象 | 诊断 | 补救 | 用错补救的代价 |
|---|---|---|---|
| 产出浅、略过考量、提早收手，但它做过的推理本身是对的 | **深度不足** | 在**同一个**模型上提高 effort | 升级层级＝为一个从来不是瓶颈的天花板多付钱 |
| 产出在种类上就错了——误解问题、提出不可行的方法——**且在 `max` effort 下仍如此** | **天花板不足** | 升级**模型**层级 | 再提高 effort 买不到任何东西；级距已用尽 |

**排序规则**：先调 effort，再升级层级。只有在当前层的**最高可用** effort 也失败之后，才升级层级。未用尽 effort 就升级层级，是对「哪一轴不足」的未经验证假设。

**例外**：若[准则 1](#准则-1--推理天花板需求) 事前已标识出「想更久也想不出来」的成分，直接从较高层开始。排序规则是关于**诊断失败**，不是关于忽略事前准则。

## 反向排除规则

层级准则说的是什么工作该**升到**某层。本节说的是什么工作**不该送给**某层。这是两个不同的问题，而第二个问题的答案无法从第一个推导出来。

### R3a 硬边界

> **硬边界是能力的「有无」，不是能力的「程度」。** 装不下输入的模型不是「把任务做得比较差」——它做不了这个任务。

采用者**必须**在其「层级 → 模型」映射中登记硬边界，且**与能力分数并列而分开记录**：

| 硬边界 | 它回答的问题 | 违反时的后果 |
|---|---|---|
| **Context 容量** | 输入装得下吗？ | 截断或报错——模型从未看过任务的一部分 |
| **Effort 参数支持** | 这个模型接受 effort 级距吗？ | 请求被拒，或静默以模型固定深度执行 |
| **Modality 支持** | 它接受这种输入型别吗（影像、语音）？ | 输入被丢弃或拒绝 |

**规则**：不满足任一必要硬边界的模型，须在**成本比较之前**排除，而非在比较中排名较低。事后才排除，会让比较便宜但做不到的模型在价格上胜出。

**登记格式**：硬边界对应能力登记表的 `declared`——布尔值，连接建立时即可取得，成本趋近零。分数 `1` **不是**硬边界，它是测量到的低质量（见 [R7a 四态表](#routing_rules--四态路由)）。

### R3b 反向风险

能力更高不是全面地更好。有两类风险的方向与层级准则相反：

#### 1. 规格敏感类工作遭安全分类器拒绝

高能力层可能带有更严格的安全分类。合法但形似禁止类别的工作——资安加固、缓解措施实作、凭证处理代码、red-team 工具——可能被**拒绝**。

> **拒绝不是错误。** 调用返回的是**正常回应加上拒绝标记**。
> 对只检查 exit code、或只检查有无抛出例外的调用方而言，**这是静默失效**：
> 管线记录成功，而工作根本没做。

**要求**：

1. 调用方**必须检查回应中的拒绝标记**。没有错误不等于完成的证据。（见 `verification-evidence` 标准：「检查工具跑了但返回了无意义的内容」与「检查根本没跑」是两种不同的失效类型。）
2. 规格敏感类工作在**批次派往**高能力层之前，**必须先验证可行性**——用一则廉价的探测请求，而非整份任务。
3. 遇到拒绝时，**改派至其他层级或其他 provider**；不要以更高 effort 重试同一请求。**effort 移动不了分类器的判定。**

#### 2. 过度详细的 prompt 会降低高天花板模型的质量

把每一个步骤都写出来，对字面遵循型是正确做法，对高天花板型则是**错误**做法：后者会重新诠释已经决定过的事，产出反而变差。

**规则**：prompt 粒度随层级走。若唯一可用的 prompt 是完整写出的步骤清单，[准则 2](#准则-2--规格明确度) 本来就要求把它送到较低层——送到高层是双重错误：付更多钱，得到更差的产出。

## 升级规则

升级现在有两个轴；下表适用于**当前层级的 effort 已用尽之后**。

| 当前层级 | 在最高可用 effort 下仍失败 | 动作 |
|-------------|-----------|--------|
| Fast | → Standard | 以 Standard 层重新派工 |
| Standard | → Capable | 以 Capable 层重新派工 |
| Capable | → 人工 | 标记为需要人工介入 |

### 升级不是重试

升级意味着改用更有能力的模型，不是重复同一个动作。更高层级的模型会收到：
- 原始任务
- 低层级模型的产出与失败原因
- **已尝试过的 effort 级距**
- 其他可用的上下文

## LLM 能力管理（XSPEC-027）

上述两轴回答「选哪个模型、想多深」。本节回答第三个独立问题：**这个模型究竟做不做得到这「种」事，以及做得多好**——用于多模型池环境。

### capability_dimensions — 能力维度

能力维度分为四大类，共 10 个子维度：

| 大类 | 子维度 | 说明 | 基准测试 |
|------|--------|------|---------|
| modality | vision | 图片/截图理解（UI 分析、图表解读） | internal-vision-bench |
| modality | audio | 语音理解能力 | future-audio-bench |
| modality | image_generation | 图片生成能力 | provider-specific |
| reasoning | code_reasoning | 代码理解与生成质量 | humaneval-plus |
| reasoning | math_reasoning | 数学推理准确率 | gsm8k |
| reasoning | instruction_following | 复杂多步骤指令遵循率 | internal-instruction-bench |
| reasoning | long_context_quality | 长文档中间段信息存取 | needle-in-haystack |
| output | structured_output | JSON/Schema 格式输出成功率 | internal-json-bench |
| output | tool_use | Function Calling 正确率 | internal-tool-bench |
| language | multilingual_zh_tw | 繁体中文质量（本系统优先语言） | internal-zh-tw-bench |

#### 每个子维度有「两个」独立字段

> **单一 1–5 分无法表达两件不同的事。**「支不支持」是二元、厂商宣告、连接时即可取得；
> 「有多好」是连续、需要跑 benchmark。把两者编码进同一个数字，
> 会让便宜的事实与昂贵的事实无从分辨——而昂贵的那个会静默胜出。

| 字段 | 型别 | 来源 | 成本 | 意义 |
|---|---|---|---|---|
| `declared` | 布尔 | provider 的模型描述端点或设定宣告 | 趋近零，连接时可得 | **做不做得到这件事** |
| `measured` | `{ score: 1–5, at: 日期, version_identifier: 字串 }` | benchmark 执行 | 高，离线 | **做得多好** |

**规范性规则**：

1. **`declared: false` 是硬边界。** 无论任何分数，该模型做不到这件事。它会被排除，且**不**排入校准队列——测量它没有意义。
2. **`declared: true` 且 `measured` 缺失 = `UNKNOWN`。** 做得到，但不知道做得多好。这是**信息缺口**，不是结论。
3. **`supported` 不得由 `score` 推导。** 任何以 `supported = score > 0`（或类似）计算的实作，都已把两个字段合并回单轴，重新制造了本规则存在所要防止的缺陷。
4. **测量失败不得记为任何分数。** 必须记为缺失（`UNKNOWN`）。以默认值填补失败的测量——包括 `0`，而 `0` 不在 1–5 量表内——会让「我们量不到」与「我们量到了而且很差」无从分辨。

**评分量表（1–5），仅适用于 `measured.score`**：

| 分数 | 意义 |
|------|------|
| 5 | 生产就绪 — 高准确率，可直接使用 |
| 4 | 良好 — 偶有遗漏，可接受 |
| 3 | 基本可用 — 需人工补充 |
| 2 | 部分可用 — 仅供参考 |
| 1 | 不可靠 — 不建议使用 |

**没有 0 分。** 测量缺失以「`measured` 物件不存在」表达，绝不以分数表达。

### capability_registry — 模型能力登记表

各专案依自己的实测，在自己的 `capability_registry` 中维护每个模型的分数。

> **本标准依规则不登记任何具体厂商模型 ID。** 写进标准的模型 ID 是一个
> **有到期日、却没有时钟**的引用端：它会过期，而过期的样子与正常的样子在页面上无从分辨。
> 以下范例一律使用占位符。

**格式**：
```yaml
- model_id: "<provider>/<model-name>"        # 占位符 — 由采用者填入
  version_pinned: "<version-identifier>"      # SHA、日期戳或 model_version
  pin_date: "<YYYY-MM-DD>"
  eol_date: "<YYYY-MM-DD>"                    # 可选
  capabilities:
    "modality.vision":
      declared: true
      measured:
        score: 4
        at: "<YYYY-MM-DD>"
        version_identifier: "<测量时所用的版本标识>"
    "modality.audio":
      declared: false                          # 硬边界 — 无 measured 字段，也不需要
    "output.tool_use":
      declared: true                           # measured 缺失 → UNKNOWN → 排入校准队列
```

**版本锁定（DEC-031 D1）**：`version_pinned` 与 `pin_date` 为**必填**，以防模型静默升级而能力在无人察觉下改变。

**逾期检查（WARN，非 BLOCK）**：`pin_date` 或 `measured.at` 距今超过 **90 天**时，**必须**发出 WARN，并指名受影响的 `model_id` 与子维度。它**不得**阻挡发版——纯档内不变量的误报率过高，不适合作为闸门。

### routing_rules — 四态路由

> **「没测过」与「测过且不可靠」不是同一个状态。** 压成同一态的后果是：
> 新侦测到的模型在第一次评估时就被排除，而且再也回不到候选池——
> **与「支持更多模型」的目标直接相反。**

| 状态 | 条件 | 动作 |
|---|---|---|
| `SUPPORTED` | 所需能力的 `measured.score` 皆 ≥ `min_score` | 正常执行 |
| `DEGRADED` | `measured.score` 存在、≥ 2、但低于 `min_score` | 降级执行；产出标记 `[DEGRADED]` |
| `UNSUPPORTED` | **`measured` 存在**且 `score` ≤ 1 | 排除；**不**排入校准队列（已有结论） |
| `UNKNOWN` | **`measured` 缺失**——未登记、测量失败或资料逾期——而 `declared: true` | **排入校准队列**；在校准完成前**不得**静默排除 |

**`declared: false`** 在本表之前处理：它是硬边界（[R3a](#r3a-硬边界)），排除且**不**排入校准队列。

**可观测性要求**：`UNKNOWN` 与 `UNSUPPORTED` **必须在返回结构上可分辨**，而不只是在 log 上可分辨。调用方必须能分辨「这个模型不行」与「我还不知道这个模型行不行」——两者导向不同的下一步动作。返回单一布尔值、或只返回三态的路由 API，表达不了这件事。

**决策树**：

```
任务需要 capability X
  ├── declared == false                    → 硬边界     — 排除，不校准
  ├── measured 缺失／失败／逾期            → UNKNOWN     — 排入校准队列
  ├── measured.score ≤ 1                   → UNSUPPORTED — 排除，不校准
  ├── measured.score ≥ 2 且 < min_score    → DEGRADED    — 执行并标记 [DEGRADED]
  └── measured.score ≥ min_score           → SUPPORTED   — 执行
```

### 重测触发 — 三条独立路径

> **版本变更是充分条件，不是必要条件。** 降智侦测（DEC-033）之所以存在，
> 正是因为**模型 ID 与版本字串不变而行为改变**。
> 仅由版本变更触发的实作，会漏掉 DEC-033 整个要防的情境。

| # | 触发 | 效果 |
|---|---|---|
| 1 | `version_identifier` 与 `measured` 中记录的不同 | 既有测量**立即失效** → 状态变为 `UNKNOWN` |
| 2 | `measured.at` 距今超过 90 天 | 排入重测；发出 WARN（见 MS-010） |
| 3 | 降智侦测告警（DEC-033，CAP-004／CAP-005） | 排入重测——**即使版本字串未变** |

这三条**彼此独立**：各自单独触发，且没有任何一条是另一条的前提。

### 能力规则

| ID | 条件 | 动作 | 优先级 |
|------|------|------|------|
| CAP-001 | 所需 capability 的 `measured.score` ≥ `min_score` | SUPPORTED — 正常执行 | High |
| CAP-002 | `measured.score` ≥ 2 但低于 `min_score` | DEGRADED — 降级流程，产出标记 `[DEGRADED]` | Medium |
| CAP-003 | **`measured` 存在**且 `score` ≤ 1 | UNSUPPORTED — 替代流程或提示用户；不校准 | High |
| CAP-004 | 降智侦测（DEC-033）触发 moderate 信号 | 启动金丝雀测试，记录降智警告，**并将受影响能力排入重测** | High |
| CAP-005 | 降智侦测触发 critical 信号 | 切换备用模型，上报 P1 Issue，**并将受影响能力排入重测** | Critical |
| CAP-006 | `declared: true` 且 `measured` 缺失、失败或逾期 | UNKNOWN — 排入校准队列；**不得**静默排除 | High |
| CAP-007 | 所需 capability 的 `declared: false` | 硬边界 — 在成本比较之前排除；**不**排入校准队列 | Critical |
| CAP-008 | `version_identifier` 与 `measured.version_identifier` 不同 | 立即失效该测量 → `UNKNOWN` | High |

**选择策略**：`pareto_weighted` — 在**通过硬边界排除的候选之中**，优先选择所需维度得分最高、成本最低的模型。

### 与两个轴的关系

- **模型轴** — 推理天花板与性格（选哪个模型）
- **Effort 轴** — 这次派工的思考深度（想多深）
- **能力维度** — 选中的模型究竟做不做得到这「种」事，以及做得多好

套用顺序：硬边界排除 → 依两个准则选层级 → 确认所需能力为 `SUPPORTED` 或可接受的 `DEGRADED` → 选择 effort 级距。

## 与下一步建议整合

[ai-response-navigation](ai-response-navigation.md) 标准（规则 R6，选用）允许每个「建议下一步」选项携带等级标注。本标准的准则即为判断依据。

> **2.1.0 的变更**：先前的标注是依文件数推导的。依旧准则做出的既有标注可能已不再准确。
> 层级标识符未变，因此**不需要资料迁移**；下次编辑周边文字时顺手重新评估标注即可。

**与厂商无关原则**：等级名称（Fast／Standard／Capable）与 effort 标签（`low` … `max`）都是工具无关的泛称，不对应任何特定厂商的模型标识符或参数名称。各平台自行维护「等级 → 模型」映射、「effort 标签 → 参数」映射，以及自己的硬边界登记。

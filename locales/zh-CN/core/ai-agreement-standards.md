# AI 协议标准

**版本**: 1.0.0
**最后更新**: 2026-01-29
**适用范围**: 所有 AI 辅助开发会话
**范围**: universal
**行业标准**: ISO 12207 §6.1
**参考**: [iso.org](https://www.iso.org/standard/63712.html)
**ISO 12207 映射**: 协议过程（6.1）

---

## 目的

本标准将人类（获取方）与 AI（供应方）之间的交互形式化为可验证的协议。在 "Vibe Coding" 中，prompt 上下文即为约束 AI 行为和交付物的法律合约。

---

## 1. 上下文合约

每个 AI 会话必须以清晰的上下文合约开始。通常通过系统提示文件实现（如 `CLAUDE.md`、`.cursorrules`）。

### 1.1 合约组件

有效的上下文合约必须定义：

| 组件 | 描述 | 示例 |
|------|------|------|
| **角色定义** | 谁代表用户 vs. AI | "你是一位资深后端工程师..." |
| **工作范围** | 操作边界 | "只修改 `src/utils/` 中的文件。不要动 `config/`。" |
| **约束法则** | 不可协商的规则 | "不要硬编码密钥。始终使用 TypeScript。" |
| **验收条件** | 完成的定义 | "代码必须通过 `npm test` 和 `npm run lint`。" |

---

## 2. 需求提案（RFP）标准

复杂任务应结构化为 "RFP"（需求提案），而非简单的聊天消息。

### 2.1 RFP Prompt 结构

请求复杂功能或重构时，使用此结构：

```markdown
# 目标
[任务的单行摘要]

# 上下文与约束
- **当前状态**: [描述现有代码/架构]
- **目标状态**: [描述期望结果]
- **约束**: [如 "必须使用库 X"、"最大复杂度 N"]

# 输入数据
[列出相关文件或粘贴 JSON Schema]

# 交付要求
1. [要求 A]
2. [要求 B]

# 验证计划
- [ ] [测试用例 1]
- [ ] [测试用例 2]
```

---

## 3. 交付验收

### 3.1 AI 自我验证
在输出代码前，AI（供应方）必须依据上下文合约验证自己的输出：
- 这段代码是否违反任何约束法则？
- 是否满足所有验收条件？

### 3.2 人类签核
用户（获取方）在应用"交付物"（AI 输出）之前，必须严格审查：
- **审查**：阅读代码（不要直接信任）。
- **验证**：执行验证计划。
- **接受**：仅在验证通过后才提交变更。

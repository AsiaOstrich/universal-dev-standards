# 技术债管理标准

> 版本: 1.1.0 | 最后更新: 2026-08-20

## 概述

技术债代表因选择权宜之计而非更佳方案所产生的未来重工隐含成本。本标准定义如何分类、登记、排序、预算、衡量及追踪技术债。

## 1. 技术债类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **Design Debt** | 架构捷径或次优设计决策 | 缺少抽象层、紧耦合 |
| **Code Debt** | 增加维护负担的代码质量问题 | 重复代码、过长方法、Magic Number |
| **Test Debt** | 不足或低质量的测试覆盖 | 缺少单元测试、不稳定测试 |
| **Documentation Debt** | 缺失、过时或不正确的文档 | 未文档化的 API、过时 README |
| **Dependency Debt** | 过时、有漏洞或不必要的依赖 | 未修补的库、已弃用框架 |
| **Infrastructure Debt** | 次优的构建、部署或运维工具 | 手动部署、缺少监控 |

### 蓄意 vs 非蓄意

- **蓄意（Deliberate）**：有意识地选择捷径，应立即登记
- **非蓄意（Inadvertent）**：因知识不足而产生，发现后应立即登记

## 2. 技术债登记表

每个技术债项目必须记录以下 11 个字段：

| # | 字段 | 说明 |
|---|------|------|
| 1 | **ID** | 唯一标识符，格式 `TD-NNN` |
| 2 | **Title** | 简短描述性标题 |
| 3 | **Type** | 上述 6 种类型之一 |
| 4 | **Source** | 引入方式（蓄意/非蓄意） |
| 5 | **Impact** | 业务与技术影响描述 |
| 6 | **Estimated Cost** | 解决所需工作量 |
| 7 | **Interest** | 不解决的持续成本 |
| 8 | **Priority** | 优先等级（P0-P3） |
| 9 | **Owner** | 负责团队或个人 |
| 10 | **Created Date** | 登记日期 |
| 11 | **Target Resolution Date** | 计划解决日期 |

### 登记表存储选项

登记表可存放于下列任一位置，但每个选项**只有在同时满足右栏的到期检查条件时才合法**：

| 选项 | 适用对象 | 到期检查条件 |
|------|---------|-------------|
| `docs/tech-debt-registry.md` | 小型团队 | 有一支 repo 检查会解析该表格，并在有行超过 Target Resolution Date 时失败——**或**该文件带有「无人看管声明」 |
| Issue tracker（GitHub Issues、Jira） | 较大团队 | 有一个排程查询实际会**执行**并发出告警；没有人打开的保存查询不算检查——**或**带有「无人看管声明」 |
| 专用电子表格 | 非技术利益相关者 | 仅当该表以明确频率导出到某个会被检查读取的位置时才合法——**或**带有「无人看管声明」 |

> **这一栏为什么必须加。** 一份没有任何程序读得到的登记表，满足本节其余每一条要求：11 个字段齐全、有 Owner、有 Target Resolution Date。它没有任何地方是错的——直到日期过了，然后什么都没发生。电子表格选项**刻意不移除**（电子表格常是出钱的人唯一会打开的格式）；不再合法的是「任何一种存储方式成为日期无声过期的地方」。

### 到期处置

一个过了却没有任何后果的 **Target Resolution Date**，与根本没有日期无从分辨。本小节定义「日期到了」是什么意思。

#### 三种合法处置

项目到达 Target Resolution Date 时，必须发生且只能发生下列三者之一，并且必须留下痕迹：

| 处置 | 含义 | 必留痕迹 |
|------|------|---------|
| **做掉（Resolve）** | 把事情做完 | 关闭登记项 + `Tech-Debt: TD-NNN resolved` commit footer |
| **撤销（Withdraw）** | 决定不做，并删掉这条记载 | 标记为撤销，附理由与日期。它不再被计为技术债，因为它已经不是了 |
| **延期（Extend）** | 设定新的 Target Resolution Date | 新日期**与**书面理由必须一起记下；先前的日期保持可见（用追加，不要覆盖） |

没有第四种处置。「仍然开着、日期过了、没有人看」不是本标准允许的状态——那正是本小节存在要指名的失败。

**规则 TD-EXP-001（必要）**——项目超过 Target Resolution Date 而三种处置皆未施用，该登记表即不合规。到期是一个发现，不是中性的背景状态。

**规则 TD-EXP-002（必要，禁止事项）**——到期**不得**被实现成**自动延期**或**自动关闭**。

- 自动延期使日期变得不可证伪：它永远不会被错过，所以它从未量到任何东西。
- 自动关闭在没有任何人做出决定的情况下删掉了那条记载。

两者都让时钟停止，且都不留下「时钟停了」的痕迹。一个唯一的消费者是「把它往后推的排程」的日期，只是装饰。

**规则 TD-EXP-003（必要）**——延期时理由必须记在新日期旁边。只改日期不是延期，那是一次盖了时间戳的删除。

**规则 TD-EXP-004（建议）**——被延期三次以上、期间没有记录任何进度的项目，应重新分流为**撤销**候选。反复延期是「没有人打算做这件事」的证据；老实记下这件事，比第四个日期对下一位读者更有用。

#### 无人看管声明

不是每个团队都有能力跑一支检查。**没有自动到期检查的登记表仍然合规——但前提是它把这件事写出来。**

「无人看管声明」是写在登记表内部、可见且带日期的一段陈述：

```
无人看管——没有任何自动检查在读这份登记表的到期项目。
由 <负责人> 以 <频率> 人工复查。最后复查日期：<日期>。
```

**规则 TD-EXP-005（必要）**——登记表必须处于下列两种状态之一，且必须让读者看得到它处于哪一种：

1. **已受检（Checked）**——有一支具名、跑得起来的检查在读这份登记表，并在项目超过 Target Resolution Date 时失败。
2. **无人看管（Unattended）**——没有这样的检查，但带有无人看管声明，且声明中写明负责人、复查频率与最后复查日期。

两种状态都不处于的登记表即为不合规。这份声明不是形式：它就是「知道没有东西在看的读者」与「以为有东西在看的读者」之间的全部差别。

**规则 TD-EXP-006（必要）**——无人看管声明里的「最后复查日期」本身，受该声明自己所写的频率约束。最后复查日期比自己声明的频率还旧的声明，本身就是一个到期项目，三种处置同样适用于它。

> **本标准不提供任何检查器，这是已知代价——写在这里，而不是留给采用者自己撞到。**
>
> UDS 定义的是要求，它不提供一支执行该要求的程序。想要**已受检**状态的采用者必须自己写那支检查，而多数团队不会写——那正是上面描述的失败模式，现在同样适用于本小节自己。
>
> 所以这里的最低标准**不是**「去建一支检查器」，而是**「绝不让一份登记表在无声中变成无人看管」**。声明 `无人看管` 只要一段文字，而且完全合规。无人看管**却不声明**才是本标准真正禁止的唯一结果，因为只有它会让读者对「有没有东西在看」产生误解。

## 3. 预算分配

| 团队状态 | 预算 | 说明 |
|---------|------|------|
| 新项目（< 6 个月） | **10%** | 预防性维护 |
| 成熟项目（6+ 个月） | **15%** | 持续维护 |
| 高债务项目 | **20-30%** | 积极偿还 |

## 4. 优先排序矩阵

|  | 低工作量 | 中工作量 | 高工作量 |
|--|---------|---------|---------|
| **高影响** | P0 — 立即 | P1 — 下个 Sprint | P1 — 下个 Sprint |
| **中影响** | P1 — 下个 Sprint | P2 — 本季 | P2 — 本季 |
| **低影响** | P2 — 本季 | P3 — Backlog | P3 — Backlog |

### 利息类型

| 利息类型 | 说明 |
|---------|------|
| **时间利息** | 绕过债务所需的额外开发时间 |
| **风险利息** | Bug、宕机或安全事件的概率增加 |
| **人才利息** | 对开发者体验与留才的负面影响 |

## 5. 量化指标

| 指标 | 公式 | 目标 |
|------|------|------|
| 总债务量 | 所有未关闭债务项目数 | 下降趋势 |
| 债务比率 | 债务项目 / 总 Backlog × 100% | < 15% |
| 平均存活天数 | 总天数 / 债务项目数 | < 90 天 |
| 类型分布 | 各类型占比 | 单一类型不超过 40% |
| 高优先比率 | (P0+P1) / 总数 × 100% | < 20% |

## 6. Commit 标记

引入债务时：`Tech-Debt: TD-042 introduced`
解决债务时：`Tech-Debt: TD-042 resolved`

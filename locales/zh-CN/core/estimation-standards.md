# 估算标准

> **语言**: [English](../../../core/estimation-standards.md) | [繁體中文](../../zh-TW/core/estimation-standards.md) | 简体中文

**版本**: 1.0.0
**最后更新**: 2026-04-01
**适用性**: 所有软件项目
**范围**: universal
**行业标准**: Agile Estimation, PERT, Wideband Delphi
**参考资料**: [Mountain Goat Software](https://www.mountaingoatsoftware.com/), [Steve McConnell - Software Estimation](https://www.construx.com/)

---

## 概述

本文件定义软件开发项目的估算标准。涵盖估算方法、校准机制、常见反模式、信心等级、重新估算触发条件，以及估算与承诺的关键区别。

好的估算不在于精确——而在于对不确定性保持透明，并通过校准持续改进。

## 估算方法

### 1. Planning Poker

一种基于共识的估算技术，团队成员独立使用编号卡片进行估算，然后讨论并收敛。

| 方面 | 详情 |
|--------|--------|
| **适用场景** | Sprint 规划、Story 级别估算 |
| **团队规模** | 3–9 人 |
| **尺度** | Fibonacci（1, 2, 3, 5, 8, 13, 21）或修改版 |
| **优点** | 促进讨论、减少锚定效应、建立共识 |
| **缺点** | 待办项过多时耗时、需要同地办公或工具支持 |

### 2. T-Shirt Sizing

一种使用抽象尺寸标签（XS, S, M, L, XL）进行快速、高层级估算的相对大小估算技术。

| 方面 | 详情 |
|--------|--------|
| **适用场景** | Roadmap 规划、Epic 级别估算、初始待办整理 |
| **团队规模** | 任意 |
| **尺度** | XS, S, M, L, XL（可选 XXL） |
| **优点** | 快速、认知负荷低、适合大量条目 |
| **缺点** | 精度较低、较难汇总为基于时间的计划 |

### 3. 三点估算

一种使用乐观值（O）、最可能值（M）和悲观值（P）估算来计算预期工期与标准差的统计技术。

| 方面 | 详情 |
|--------|--------|
| **适用场景** | 关键路径项目、高不确定性任务、项目级别规划 |
| **公式** | E = (O + 4M + P) / 6; SD = (P - O) / 6 |
| **优点** | 量化不确定性、生成置信区间、具有统计学依据 |
| **缺点** | 每个项目需要三次估算、对小任务可能感觉缓慢 |

## 校准

### 校准机制

团队应（SHALL）定期将估算与实际结果进行校准，以随时间推移提高准确度。

**审查频率**：在每次 Sprint 回顾会议中进行校准审查，或至少每迭代一次。

**估算准确率**：

```
Estimation Accuracy Ratio = Actual Effort / Estimated Effort
```

- 比率 = 1.0：完美估算
- 比率 > 1.0：低估（实际耗时更长）
- 比率 < 1.0：高估（实际耗时更短）

**改进措施流程**：

1. 收集已完成工作项的实际与估算数据
2. 计算每项条目及团队平均的估算准确率（Estimation Accuracy Ratio）
3. 识别系统性模式（例如：始终低估集成任务）
4. 定义纠正措施（例如：为集成增加缓冲、拆解大型工作项）
5. 跟踪后续迭代中的改进情况

## 反模式

以下反模式经常会破坏估算质量。每个反模式均包含识别信号与缓解策略。

### 1. 锚定偏误

**说明**：第一个提到的数字主导了后续估算，将团队拉向该锚点。

**识别**：估算值聚集在第一个分享的数值周围；未对不同意见展开探讨。

**缓解策略**：使用盲估（例如 Planning Poker 同时翻牌）。避免在独立评估之前陈述估算值。轮换先发言的人员。

### 2. 规划谬误

**说明**：系统性地低估时间、成本和风险，同时高估效益的倾向。

**识别**：项目持续超出估算；事后复盘反复提及“未预见的复杂性”。

**缓解策略**：使用参考类别预测（与过去类似项目比较）。应用历史校准数据。添加显式风险缓冲。

### 3. 范围蔓延盲区

**说明**：在估算过程中未能识别或考虑逐渐扩大的范围。

**识别**：随着需求增长，原始估算失效；尽管范围发生明显变化，却未进行重新估算。

**缓解策略**：在估算前锁定范围定义。显式跟踪范围变更。当范围变更超过阈值时触发重新估算（参见“重新估算触发条件”）。

### 4. 学生综合症

**说明**：将工作拖延到最后一刻才开始，消耗所有可用的缓冲时间。

**识别**：尽管时间充裕，工作却始终启动很晚；交付完全由截止日期的压力驱动。

**缓解策略**：设置带有可见进度跟踪的中间里程碑。使用更短的迭代周期。避免给单个估算填补缓冲——改为使用项目级别的缓冲。

### 5. 帕金森定律

**说明**：无论实际复杂度如何，工作总会膨胀以填满可用于完成该工作的时间。

**识别**：无论难度如何变化，任务耗时始终与估算时间完全一致。

**缓解策略**：使用相对估算（Story Points）而非绝对时间。对刚好符合整数的估算提出质疑。跟踪速率趋势以发现异常。

## 信心等级

每个估算均应（SHALL）包含一个表示预期方差范围的信心等级。

| 等级 | 变异范围 | 说明 | 适用场景 |
|-------|----------|-------------|---------------------|
| **高** | **±20%** | 需求明确且具备先前经验的透彻理解工作 | 重复任务、定义明确的 Story、熟悉的技术 |
| **中** | **±50%** | 部分理解且存在一些未知因素的工作 | 已知领域中的新功能、中等技术不确定性 |
| **低** | **±100%** | 高度不确定且存在重大未知因素的工作 | 新技术、不明确的需求、探究性 Spike |

### 沟通指南

- **高信心**：“我们估算 5 天（4–6 天范围）”
- **中信心**：“我们估算 5 天（2.5–7.5 天范围）”
- **低信心**：“我们估算 5 天（0–10 天范围）——建议先进行探究（spike）”

始终在给出点估算的同时沟通信心等级。切勿在未明确说明不确定性的情况下给出低信心估算。

## 重新估算触发条件

当发生以下任一情况时，应（SHALL）触发重新估算：

### 触发条件

| 触发条件 | 说明 | 行动 |
|---------|-------------|--------|
| **需求变更** | 功能或非功能需求被添加、移除或修改 | 重新估算受影响项目；更新信心等级 |
| **技术发现** | 发现新的技术约束、依赖关系或复杂性 | 基于更新的知识重新估算；记录该发现 |
| **外部依赖变更** | 第三方 API、库或服务的可用性或行为发生变化 | 重新估算集成工作；评估对时间线的影响 |
| **时间阈值超过** | 已消耗时间超过原始估算的相当大比例（例如 >50%）但未取得相应进度 | 进行检查点审查；重新估算剩余工作 |

### 重新估算流程

1. **识别**：确认已满足触发条件
2. **评估**：评估对当前估算的影响
3. **重新估算**：对受影响项目应用适当的估算方法
4. **沟通**：向利益相关方通知修订后的估算及更新后的信心等级
5. **记录**：记录重新估算的原因以及与原始估算的差异

## 估算 vs 承诺

### 定义

**估算**是对工作需要多长时间的预测，本质上是不确定的，并以范围形式表示。它是执行工作的人员做出的技术评估。

**承诺**是在特定日期之前或在特定预算之内完成交付的诺言。它是一项商业决策，综合考虑了估算、风险容忍度以及战略优先级。

### 估算 vs 承诺 — 关键差异

| 方面 | 估算 | 承诺 |
|--------|----------|------------|
| **本质** | 带有不确定性的预测 | 带有责任的承诺 |
| **负责人** | 开发团队 | 管理层 / Product Owner |
| **格式** | 范围 + 信心等级 | 具体日期或范围 |
| **变更** | 随信息更新而调整 | 与利益相关方重新协商 |

### 沟通实践

- **估算**：始终以带有信心等级的范围形式呈现。使用如“我们估算”或“我们的评估是”等表述。
- **承诺**：以具体目标形式呈现。使用如“我们承诺”或“我们将在……之前交付”等表述。
- **切勿混淆**：绝不允许在未经明确协商的情况下，将估算悄然转化为承诺。

### 将估算转化为承诺

1. 从团队的估算开始（范围 + 信心等级）
2. 评估组织的风险容忍度（如果我们未按时达成会发生什么？）
3. 根据信心等级添加适当的缓冲
4. 与利益相关方就范围、时间线或质量权衡进行协商
5. 将承诺与底层估算分开记录

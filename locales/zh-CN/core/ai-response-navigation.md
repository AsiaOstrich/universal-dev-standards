# AI 响应导航标准

> **语言**: [English](../../../core/ai-response-navigation.md) | [繁體中文](../../zh-TW/core/ai-response-navigation.md) | 简体中文

**版本**: 1.4.0
**最后更新**: 2026-10-05
**适用范围**: 所有使用 AI 辅助开发的项目
**范围**: universal
**行业标准**: 无（新兴 AI 工具实践）
**参考**: [SPEC-STD-08](../../../docs/specs/standards/SPEC-STD-08-ai-response-navigation.md)

---

## 目的

本标准定义 AI 响应的导航行为：每个实质性的 AI 响应必须包含情境化的下一步建议与推荐选项。确保用户在开发工作流程中持续被引导，无需记忆所有可用命令。

**问题**：用户在收到 AI 响应后不知道下一步该做什么。面对 30+ 个斜杠命令，认知负担高且工作流程连续性中断。

**解决方案**：在每个实质性 AI 响应结尾附加标准化的「导航区块」，包含情境模板、推荐标记和弹性选项数量。

**范围注记（v1.2.0，v1.3.0、v1.4.0 扩充）**：规则 1–6 管的是答案**之后**要附什么。
规则 7–12 管的是答案本身：先讲发现（R7）、每轮重述进度（R8）、不要开场白（R9）、
白话是主语（R10）、每个选项都要带自己的利弊而非只有推荐项有（R11）、受控语言（R12）。
规则 7–11 **属可选**。**规则 12 是唯一的例外，而且只有一部分**：其中「简化后的文字要保留写作者的不确定语气」
这一条**属必须**，其余部分属可选。新增的理由是——
一个响应可以满足规则 1–6 的每一条，同时把结论埋起来、用只有作者持有的词汇讲它、列出读者还得自己比较的选项，
或是靠「比证据更肯定」来变得好读；
**而找不到答案的读者，不会因为结尾有一个正确的导航区块被告知下一步而得到帮助。**

## 核心规则

### 规则 1：每个实质性响应都包含导航

每个构成「逻辑响应单元」的 AI 响应必须以导航区块作为结尾。

**以下情况视为逻辑响应单元：**

1. 完成了一项任务或子任务
2. 提供了分析、解释或建议
3. 向用户询问问题或要求选择
4. 报告了错误或异常状态
5. 展示了代码变更结果

**豁免**：极短确认回复（如「好的」「已完成」「了解」）不构成独立的逻辑单元，可以省略导航区块。

### 规则 2：推荐并说明理由

提供多个选项时，使用 ⭐ **推荐** 标记最佳选项，并在 ` — ` 之后附上理由。

| 情境 | 标记方式 |
|------|----------|
| 有一个选项明显较优 | ⭐ **推荐** — [理由] |
| 各选项无明显优劣 | 说明各选项适用场景，不标记 ⭐ |
| 只有一个合理的下一步 | 直接建议，不需要 ⭐ |

### 规则 3：匹配情境

根据响应类型使用对应的模板（参见[情境模板](#情境模板)）。

### 规则 4：弹性数量

根据情境复杂度调整选项数量：

| 情境 | 选项数量 | 理由 |
|------|----------|------|
| 任务完成 | 2–3 | 建议后续工作流程步骤 |
| 用户询问 | 2–5 | 依问题复杂度调整 |
| 错误/失败 | 1–3 | 聚焦修复方向 |
| 进行中 | 1–2 | 继续或调整 |
| 信息回复 | 1–3 | 探索方向 |

**硬性上限**：不得超过 5 个选项。裁减至最相关的选项。

### 规则 5：优先使用斜杠命令

当下一步建议对应到已知的斜杠命令时，使用 `` `/command` `` 格式引用，让用户可以直接复制执行。没有对应命令的步骤使用自然语言描述。

### 规则 6：模型级别标注（可选）

当某个下一步选项明确对应到特定的复杂度级别时，可**选择性**附加模型级别提示。此标注**严格为可选**——既有技能无需回头修改；新增或修订技能时建议带入。

**标注方式**：在选项描述后加上 `〔模型：Fast〕`、`〔模型：Standard〕` 或 `〔模型：Capable〕`。

**级别判断依据**：参考 [model-selection](model-selection.md) 标准的复杂度信号：
- `Fast` — 修改单一文件、spec 完全明确、无需设计判断
- `Standard` — 2-5 个文件、需要模块间理解
- `Capable` — 5+ 个文件、架构决策、跨系统正确性

级别名称**与厂商无关**——各工具或平台自行将级别映射到可用的模型。

**英文标注对照**：`〔model: Fast〕` / `〔model: Standard〕` / `〔model: Capable〕`

**示例**（任务完成，含模型标注）：

```markdown
> **建议下一步：**
> - 执行 `/derive bdd` 推导 BDD 场景 `〔模型：Fast〕` — 格式转换工作
> - 执行 `/checkin` 进行质量关卡验证 ⭐ **推荐** `〔模型：Standard〕` — 需要模块间判断
> - 执行 `/sdd` 整合架构设计 `〔模型：Capable〕` — 跨系统影响分析
```

## 导航之前的那个答案（规则 7–12）

> **规则 7–9 借鉴自**：[`ayghri/i-have-adhd`](https://github.com/ayghri/i-have-adhd)（MIT），十条中取三条。
> **规则 10–11 于 1.3.0 新增**，来源不同——用户在同一次工作会话中两度指出，
> 一个正确且完整的回答读不懂。当时规则 7–9 已经出货且正在被遵守。
> **规则 12 于 1.4.0 新增**，来源又不同：一则公开的建议——请 LLM 写到「大约达到 ASD-STE100 的 80%」
> （ASD-STE100 是技术文档用的受控英文标准）。只取它的原则；它的英文词典与时态规则不取（见规则 12）。
> 其余七条删去：两条已被上方规则 1–2 涵盖，五条与本标准冲突
> （它的「不要 recap／不要结语」与规则 1 的导航区块直接矛盾；它的「列表上限 5 项」
> 会截断证据表格与遍历分母）或与 [estimation-standards](estimation-standards.md) 重复。

**这一节为何存在**：规则 1–6 管的是答案**之后**要附什么，而答案本身没有任何规则在管——
一个响应可以把结论埋在一整面证据底下，只要结尾附上正确的导航区块，
它仍然满足本标准的每一条。**找不到答案的读者，不会因为被告知下一步而得到帮助。**

**规则 7–11 是可选的**，语义同规则 6：采用项目不必启用，既有 skill 也不需回头补。
项目**可以**在自己的配置中把任一条提升为必须。**规则 12 有一条必须（12.1）**，其余（12.2）可选；
为什么这样分，规则内部有论证。**任何一条都不可选的是它们必须有精确的触发条件**——
一条松到永远不会启动的规则，与没有这条规则无从分辨。

### 规则 7：先讲发现，不要先讲过程（可选）

**触发条件**：回答问题、汇报调查结果、或提出决策的响应。

第一行写**查到了什么**或**该做什么**。不是方法、不是把问题复述一遍、不是回答的计划。

证据——`file:line`、命令输出、表格、测量数字——是**佐证**，应放在它所支持的论断**之后**。
以证据开场会迫使读者自行重建结论，而那正是他请你做的工作。

| 不要写 | 改写成 |
|---|---|
| 「我检查了 44 天、63 个域名的数据，发现……」 | 「那三组查询删掉。它返回的东西有 46% 是下载页。」 |
| 「让我看看这是怎么配置的。」 | 「配置在 `x.yaml:12`，值是错的，因为……」 |

**这不代表可以省略证据**，它规范的是顺序。

### 规则 8：多轮工作中每一轮重述进度（可选）

**触发条件**：跨 3 轮以上的对话，或含 3 个以上步骤的任务。

每条响应用一行说明工作进行到哪里。不能假设读者能在消息之间记住
「我们在 5 步中的第 3 步」，而重述它的成本是一个句子。

本条与下方模板 4（进行中）互补：**规则 8 管开头，模板 4 管结尾。**

### 规则 9：不要开场白（可选）

**触发条件**：任何实质性响应。

从答案开始。不要以「我接下来要做什么」的预告、对请求的确认、或对问题本身的评价开场。

本条把一项既有禁令一般化：[anti-sycophancy-prompting](anti-sycophancy-prompting.md)
已经禁止「以正面肯定开场批评」，但**仅限批评情境**。规则 9 把同一项禁令扩及每一个实质响应，
理由不同：不是为了防拍马屁，而是为了消除它在读者与答案之间制造的延迟。

**规则 9 不适用于结语。** 规则 1 要求的导航区块依然成立——
响应的结尾正是本标准安放「读者下一步」的位置。

### 规则 10：白话是主语，标识符是佐证（可选）

**触发条件**：任何向人解释一个情况、一个缺陷、或一个系统行为的响应。

用读者会用的话说清楚发生了什么。文件路径、符号名称、行号、命令输出、版本字符串是**佐证**——
它们属于它们所支持的那句话**之后**，而不是那句话本身。

| 不要写 | 改写成 |
|---|---|
| 「`intel-scout.py:883` 的 `load_topics()` 读 `intel-topics.yaml`，`:1033` 的 `load_feeds()` 读 `intel-feeds.yaml`。」 | 「它有两种取材方式：搜关键字，和订阅固定几个博客。」*（然后再附两个调用点）* |
| 「`manifest.skillHashes` 有 137 条，key 是 `claude-code/project/<n>/SKILL.md`，而查询用的是 `.claude/skills/<n>`。」 | 「哈希值存在一套命名下，查询用的是另一套，所以一个都找不到。」*（然后再贴两边的 key）* |

这**不是**可以省略标识符的许可——想验证的读者必须验得了。它规范的是**两者之中哪一个当主语**。

**为什么它与 R7 是两条**：R7 规范的是**先讲发现再给证据**的顺序。R10 规范的是**语域**——
一个响应可以先讲发现，却仍然用只有作者持有的词汇讲那个发现。两者都让读者无法行动，但它们是不同的失效。

**白话不可以拿肯定语气来换。** 把说明改成读者的话就是一次改写，而改写正是「可能」悄悄变成「是」的地方。
当 R10 用在写作者原本就有保留的论断上，由[规则 12](#规则-12受控语言部分必须) 的 12.1（必须）管：不确定语气要留着。

### 规则 11：每个选项都要带自己的利弊（可选）

**触发条件**：要求读者在两个以上做法之间选择的响应。

规则 2 要求标示推荐选项并给出**它的**理由。规则 11 把这件事扩及其余：
**每一个**选项都要用它自己的话说明它换到什么、代价是什么。

一份只有推荐项被论证的选项清单，等于**把比较的工作丢回给读者**——而那正是他请你做的事。
而一个没有标出代价的选项，读起来像是没有代价，这很少为真，且从清单本身无从验证。

```markdown
> **请选择：**
> | 选项 | 换到什么 | 代价是什么 |
> |---|---|---|
> | **(A) …** ⭐ **推荐** — [为什么是这个] | … | … |
> | **(B) …** | … | … |
```

**利弊不是模棱两可。**「这可能会稍微难一点」不是代价；「这要重写 110 个文件，而且翻译需要人审」才是。
若某个选项真的没有值得一提的代价，**明说**，不要留空——空白读起来是「没有分析过」，而读者分不出这两者。

**与规则 4 相辅**：选项数维持在 1–5。利弊让每个选项读起来更花力气，所以这条规则让规则 4 的上限**更**要紧，不是更不要紧。

### 规则 12：受控语言（部分必须）

**触发条件**：为「不是原作者」的读者撰写、改写、缩短、简化或翻译文字——典型是一位非专业的读者，要靠这段文字做判断或审批。

受控语言（用变化换可预测性的写作规则）让文字更好读。它有一个已知的失败方式：最好读的句子是肯定的句子，
所以「简化」会朝肯定的方向漂移。本规则取受控写作的原则，并对这个漂移设一道硬性的止损。

#### 12.1 简化后的文字要保留不确定语气（必须）

不确定语气是一个告诉读者「这个论断可以信到什么程度」的词：*可能、推断、大概、尚未确认*——
*might、could、probably、appears to、not yet confirmed*。它是信息，不是赘词。

缩短、简化、改写或翻译时：

- **不可把不确定的论断改成确定的。** 原文说「可能」，结果就说「可能」（或结果语言里对等的说法）。
- **不可为了省字而删掉不确定语气。** 目标是更短的句子；更肯定的句子不被允许。
- **不可加入原文没说的事实**——编出来的原因、编出来的「已确认」，是同一种失败的另一个样子。
- 只有在论断之后**已经被验证**时，不确定语气才可以拿掉；而且要由验证（查了什么、结果是什么）取代它的位置。
  只删掉不确定语气，不算验证。

**为什么只有这一条是必须的**：只有它的失败会让读者**相信不真实的事**，而不只是让文字更难读。
它也不需要校准——检查就是拿改写前后两份文字比对，人或模型在任何语言都做得到；
而下面每一个阈值都取决于语言与读者。

#### 12.2 白话写作原则（可选）

读者是非专业人士时使用。它们与语言无关：每一条都用该语言自己的单位来表达，不附任何词表。

| 原则 | 要求什么 |
|------|----------|
| **句子短，以该语言自己的单位计** | 一句一个意思。**起始范围**，不是上限：英文大约 15–25 个词，中文大约 25–40 个字。远超过范围是「该拆句」的信号，不是要计数的缺陷。按语言与读者校准 |
| **同一个东西只用一个名称** | 每个东西选定一个名称，全文都用它。不要为了文采换说法：读者看到第二个名称，会以为是第二个东西 |
| **主语明确、主动语态** | 说清楚谁做了什么。施事者不明或不重要时，才用被动 |
| **一步一动作** | 流程是编号列表，每项一个动作，不是一段文字 |
| **少用分号** | 分号把读者必须同时记住的两个意思接在一起。拆成两句或一份列表 |
| **数字带单位** | 「30 秒」「3 个文件」「NT$1,200」——不要只写「30」 |

**为什么是可选**：上面的范围只是起始点，**没有**对照读者实际理解度校准过，也没有检查器在执行。
一条**必须**的规则若附带没人能验证的阈值，会产生机械式的遵守——句子被拆到不再像句子——
而专家读者可能反而更适合比较密的文字。这些原则是写作者凭判断使用的指引；12.1 才是不会弯的那一部分。

#### 本规则不取 ASD-STE100 的什么

ASD-STE100 的**核可词典**（每个核可的英文单词只有一个意思，并有一份封闭的允许词表）与它的**时态限制**，
都依赖英文这个语言。它们**不适用于中文**或其他非英文文字，本标准**不附任何形式的词表**。
只取 12.2 的原则，并改写成每一条都能在任何语言使用。

同理，不要用「以空白或 ASCII 字符分词」的计数器去衡量非英文文字：它把一整段中文看成一个「词」，
不论多长都通过。一把在某个语言上永远是绿灯的量尺，在那个语言上什么也没量到。

#### 示例：同一段文字、三种改写，以及一个不被允许的改写

示例刻意用中文：本规则与语言无关，而中文正是只靠英文做法行不通的地方。三个有效版本都保留不确定语气
「可能」、「推断」、「尚未」，且没有加入原文没有的事实。

**原文**

```text
经过检查，登录页面在高流量时段响应变慢，这个问题可能是数据库连接池被耗尽所造成的，我们推断是因为上周的改版新增了一个会长时间占用连接的查询；目前尚未在测试环境复现，所以修复后的效果还需要被确认，建议在确认之前先不要对外宣布已经解决。
```

**约 80%**——句子较短，读起来仍像一段文字

```text
登录页面在高流量时段响应变慢。原因可能是数据库连接池被耗尽。我们推断，上周改版新增了一个查询，它会长时间占用连接。这一点尚未在测试环境复现，修复后有没有效，也还没确认。确认之前，建议先不要对外宣布已经解决。
```

**严格**——一行一个意思、加标签、保留不确定语气

```text
登录页面在高流量时段响应变慢。
1. 原因：可能是数据库连接池被耗尽。
2. 推断：上周改版新增了一个查询，这个查询可能长时间占用连接。
3. 状态：尚未在测试环境复现。
4. 修复效果：尚未确认。
5. 建议：确认之前，不要对外宣布已解决。
```

**不是有效的改写**——最短，而且是错的

```text
登录页面变慢，原因是数据库连接池被耗尽，已确认由上周改版造成。
```

最后这一版最短、也最好读，却两度违反 12.1：「可能」变成直接陈述的原因，「尚未复现」变成「已确认」，
而原文从没说过这件事。读者若凭它批准一个修复，就是被给了一件不真实的事。

## 情境模板

### 模板 1：任务完成

任务、技能执行或代码修改完成时使用。

```markdown
> **建议下一步：**
> - 执行 `/command1` 做 X
> - 执行 `/command2` 做 Y ⭐ **推荐** — [理由]
> - 执行 `/command3` 做 Z
```

### 模板 2：用户询问

AI 需要用户做出选择或提供信息时使用。

```markdown
> **请选择：**
> - **(A) 选项描述** — 补充说明
> - **(B) 选项描述** ⭐ **推荐** — [理由]
> - **(C) 选项描述** — 补充说明
```

### 模板 3：错误/失败

报告错误、失败或异常状态时使用。

```markdown
> **建议修复方向：**
> - 选项描述 ⭐ **推荐** — [理由]
> - 选项描述
```

### 模板 4：进行中

完成多步骤任务的中间阶段时使用。

```markdown
> **当前进度：[N/M]。下一步：**
> - 继续下一阶段 ⭐ **推荐**
> - 调整方向或参数
```

### 模板 5：信息回复

回答知识性问题或提供说明时使用。

```markdown
> **建议下一步：**
> - 深入了解 [相关主题]
> - 执行 `/command` 将知识应用到实现
```

## 格式规范

### 结构

所有导航区块使用 Markdown 引用区块（`>`）：

```markdown
> **[标题]：**
> - [选项/建议] ⭐ **推荐** — [理由]
> - [选项/建议] — [补充说明]
```

### 依情境的标题

| 情境 | 标题 |
|------|------|
| 任务完成 | `建议下一步` |
| 用户询问 | `请选择` |
| 错误/失败 | `建议修复方向` |
| 进行中 | `当前进度：[N/M]。下一步` |
| 信息回复 | `建议下一步` |

### 本地化

对于双语项目，导航区块遵循对话语言。本地化对照：

| English | 繁體中文 | 简体中文 |
|---------|----------|----------|
| Suggested next steps | 建議下一步 | 建议下一步 |
| Please choose | 請選擇 | 请选择 |
| Suggested resolution | 建議修復方向 | 建议修复方向 |
| Progress: [N/M]. Next | 目前進度：[N/M]。下一步 | 当前进度：[N/M]。下一步 |
| Recommended | 推薦 | 推荐 |

## 与技能的整合

### 现有技能

已有 `## Next Steps Guidance | 下一步引导` 区块的技能：

1. **保留**技能特有的场景化建议内容
2. **对齐**格式以符合本标准定义的模板
3. **加入**推荐标记（⭐）

### 新技能

新技能应包含遵循本标准模板的 `## Next Steps Guidance | 下一步引导` 区块。

### 超越技能

本标准适用于**所有 AI 响应**，不仅限于技能执行。一般对话、代码审查、调试过程及任何其他交互，在产生实质性响应时都必须遵循这些导航规则。

## 跨 AI 工具适用性

本标准与工具无关。适用于所有使用 UDS 标准的 AI 工具：

- Claude Code
- Cursor
- Windsurf
- GitHub Copilot
- Cline
- Roo Code
- Augment Code
- Trae
- 其他兼容工具

每个工具的集成层负责根据其 UI 能力渲染导航区块，但行为规则保持一致。

## 示例

### 示例 1：完成功能实现后

```markdown
> **建议下一步：**
> - 执行 `/test` 为新功能编写测试
> - 执行 `/commit` 提交变更 ⭐ **推荐** — 变更已完整且通过验证
> - 执行 `/code-review` 进行自我审查
```

### 示例 2：询问用户设计问题

```markdown
> **请选择：**
> - **(A) 使用新的数据库表** — 更灵活，迁移成本较高
> - **(B) 扩展现有表增加列** ⭐ **推荐** — 迁移更简单，满足当前需求
> - **(C) 使用 NoSQL 存储** — 适合非结构化数据但增加基础设施
```

### 示例 3：报告测试失败

```markdown
> **建议修复方向：**
> - 检查 `tests/auth.test.js:42` 的失败断言 ⭐ **推荐** — 错误信息指向空引用
> - 执行 `/debug` 进行系统性调试
> - 还原上次变更并调查
```

### 示例 4：工作流程中间进度更新

```markdown
> **当前进度：[2/5]。下一步：**
> - 继续第 3 阶段：实现 ⭐ **推荐**
> - 在继续前重新检视第 2 阶段需求
```

### 示例 5：回答技术问题

```markdown
> **建议下一步：**
> - 探索 `config/auth.yaml` 中的相关配置
> - 执行 `/sdd` 创建规格（若计划修改此行为）
```

## 快速参考卡

| 规则 | 摘要 |
|------|------|
| R1 | 每个实质性响应 → 导航区块 |
| R2 | 多选项 → ⭐ 标记最佳 + 理由 |
| R3 | 模板匹配响应类型 |
| R4 | 1–5 个选项，依情境调整 |
| R5 | 适用时使用 `/command` 格式 |
| R6 | *（可选）* 级别明确时附加 `〔模型：Fast｜Standard｜Capable〕` |
| R7 | *（可选）* 先讲发现；证据放在它所支持的论断之后 |
| R8 | *（可选）* 跨 3 轮或 3 步以上 → 用一行重述进度 |
| R9 | *（可选）* 不要开场白。结语仍为必须——见 R1 |
| R10 | *（可选）* 白话是主语；标识符放在论断之后当佐证 |
| R11 | *（可选）* 每个选项都要说明换到什么、代价是什么——不只推荐那一个 |
| R12 | **12.1 *（必须）***：简化、缩短或翻译时，保留不确定语气——不可把「可能」改成「是」。12.2 *（可选）*：句子短（以该语言自己的单位计）、同物同名、主动语态、一步一动作、少用分号、数字带单位。不附英文词典——它无法移到其他语言 |

| 豁免 | 不豁免 |
|------|--------|
| 「好的」「已完成」「了解」 | 任务完成报告 |
| 单词确认回复 | 错误说明 |
| | 分析或建议 |
| | 向用户提问 |
| | 代码变更摘要 |

# 重构标准

> **语言**: [English](../../../core/refactoring-standards.md) | 简体中文

**版本**: 2.2.0
**最后更新**: 2026-07-01
**适用范围**: 所有进行代码改进工作的软件项目
**范围**: partial
**业界标准**: ISO/IEC 25010 可维护性

> **详细模式与教程，请参阅 [重构指南](../../../core/guides/refactoring-guide.md)**

---

## 目的

本标准定义代码重构的完整指引，涵盖从日常 TDD 重构循环到大型遗留系统现代化的所有场景。

---

## 重构 vs 重写决策矩阵

| 因素 | 倾向重构 | 倾向重写 |
|------|----------|----------|
| **代码库规模** | 大型、复杂 | 小型、独立 |
| **测试覆盖率** | 良好（>60%） | 不足或没有 |
| **业务连续性** | 关键 | 可容忍停机 |
| **团队知识** | 团队理解代码 | 缺乏组织内的知识传承 |
| **核心架构** | 健全，只是凌乱 | 根本性缺陷 |
| **时间压力** | 期限紧迫 | 时程弹性 |
| **风险容忍度** | 低 | 较高 |

---

## 何时重构

| 情境 | 建议策略 |
|------|----------|
| 功能开发被凌乱的代码阻碍 | 预备性重构（Preparatory Refactoring） |
| 修复缺陷时顺带接触到代码 | 童子军规则（Boy Scout Rule） |
| 以 TDD 编写新代码 | 红-绿-重构（Red-Green-Refactor） |
| 替换整个遗留系统 | 绞杀者模式（Strangler Fig Pattern） |
| 需要与遗留系统集成但不被污染 | 防腐层（Anti-Corruption Layer） |
| 不使用功能分支重构共享代码 | 抽象分支（Branch by Abstraction） |
| 变更被广泛使用的接口 | 并行变更（Parallel Change，扩展-迁移-收缩） |
| 处理没有测试的遗留代码 | **先写**特征测试（Characterization Tests） |

---

## 策略摘要

| 策略 | 规模 | 风险 | 时长 | 主要使用情境 |
|------|------|------|------|--------------|
| **预备性重构** | 小 | 低 | 数小时 | 在功能开发前降低阻力 |
| **童子军规则** | 极小 | 低 | 数分钟 | 持续偿还技术债 |
| **红-绿-重构** | 小 | 低 | 5-15 分钟 | TDD 开发循环 |
| **绞杀者模式** | 大 | 中 | 数月 | 系统替换 |
| **防腐层** | 中 | 低 | 数周 | 新旧系统共存 |
| **抽象分支** | 大 | 中 | 数周 | 在主干上进行长期重构 |
| **并行变更** | 中 | 低 | 数天至数周 | 接口/schema 迁移 |
| **特征测试** | — | — | — | **所有遗留代码重构的前提** |

## 安全重构工作流程

### 重构前

- [ ] 定义成功标准（可衡量）
- [ ] 确保足够的测试覆盖率（建议 >80%）
- [ ] 提交或暂存（stash）当前工作（保持干净的工作目录）
- [ ] 创建功能分支（或在主干上配合功能开关工作）
- [ ] 与团队沟通以避免冲突

### 重构中

- [ ] 一次只做**一个**小变更
- [ ] **每次**变更后都运行测试
- [ ] 若测试失败，**立即**回退
- [ ] 频繁提交（每次测试通过都是一个保存点）
- [ ] 重构时绝不新增功能

### 重构后

- [ ] 所有测试通过（与重构前相同）
- [ ] 代码有可衡量的改善（复杂度、重复度等）
- [ ] 必要时更新文档
- [ ] 完成团队审查
- [ ] 没有新增功能

## 代码质量指标

### 目标指标

| 指标 | 目标 | 工具 |
|------|------|------|
| **圈复杂度** | 每个函数 < 10 | 静态分析 |
| **认知复杂度** | 越低越好 | SonarQube |
| **代码重复（文本）** | < 3% | 静态分析 |
| **语义重复** | 0 个未受管控的领域事实 | Golden 测试 / 架构测试（见下文） |
| **测试覆盖率** | ≥ 80% | 覆盖率工具 |

> **文本重复 vs 语义重复**：`Code Duplication` 指标只能检测*文本*重复（几乎相同的 token 序列），无法检测*语义*重复——同一个领域事实在多处被重新实现，或派生的聚合值被持久化却没有与其来源建立强制绑定。不是逐字节相同的副本（改写过的逻辑、在一处正确而在另一处错误的公式）能通过静态分析，却会持续各自漂移。语义重复必须由 golden 测试与架构测试来管控（参见[语义重复与复制漂移](#语义重复与复制漂移)），而非依赖上述静态分析阈值。

### ISO/IEC 25010 可维护性目标

| 子特性 | 指标 | 目标 |
|--------|------|------|
| **模块化（Modularity）** | 耦合度、文件大小 | 减少依赖 |
| **可复用性（Reusability）** | 代码重复 | 提取方法、DRY |
| **可分析性（Analysability）** | 圈复杂度 | 简化逻辑 |
| **可修改性（Modifiability）** | 内聚度、测试覆盖率 | 单一职责 |
| **可测试性（Testability）** | 分支覆盖率 | 依赖注入 |

## 语义重复与复制漂移

文本重复指标能抓到复制粘贴，却会漏掉更危险的情况：**同一个领域事实在不止一处被实现**。当这些实现并非逐字节相同时——改写过的分类逻辑、在某个调用点正确而在另一个调用点有细微错误的公式、与其汇总的明细行分开存储的总计——它们能通过静态分析，然后**各自独立地漂移**，产生看似无关、实则同一根因的缺陷。

### 反模式：复制漂移（Copy-Drift）

复制漂移在以下任一情况发生：

- 单一领域事实（分类、规则、计算）在**多个调用点被重新实现**，而不是由一个共享单元计算；或
- **派生值被持久化**（存储的聚合值、计数器或反规范化字段）**却没有与其来源建立强制关系**，导致每条写入路径都能独立更新它。

由于这些副本并非字面上完全相同，文本重复工具不会报告任何问题。分歧日后会以不一致的形式浮现：列表视图与详情视图不一致、存储的计数器因某条更新路径的递减分支被注释掉而重复计数，或同一个公式在不同模块中得出不同答案。

### 模式：单一事实来源 / 派生而非复制（Derive-Don't-Duplicate）

- **一个事实一个单元。** 将每个领域事实提取为**单一**的分类器 / 计算器 / 解析器。每个调用点都调用它——不重新实现，也不改写。
- **派生，而非存储。** 优先在读取时计算值，而不是持久化第二份副本。始终派生的值不会漂移。
- **若聚合值必须存储**，应将其视为**明细行的投影**，并在**单一关卡点**重新计算——例如 `SaveChanges` 拦截器，或一个共享的 `recompute()` 函数——让*每条*写入路径（包括异步作业与失败回写）都经过同一套重新计算并保持一致。**绝不**让个别路径对存储的聚合值做 `col = col + delta` 这类增量调整；增量调整正是递减/回滚分支被跳过、计数器出现分歧的根源。
- **用测试锁定。** 使用 **golden 测试**固定单一事实来源，并加入**架构测试**，一旦该规则在其他地方被重新定义就失败，让未来的副本在 CI 阶段就被拒绝，而不是在生产环境中才被发现。

### 迁移推论——刻意分歧登记表

当新系统**刻意**与遗留行为产生分歧时，必须记录下来——否则日后的“修复”会悄悄把它改回去。移植时常见的情况：遗留*函数*返回 X，但下游的遗留*流水线*会把它调和为 Y；移植时将这个调和过程并入单一单元，于是该函数现在直接返回 Y。

- 将每项刻意分歧登记在**刻意分歧登记表**中（遗留行为、新行为、理由、所属事实）。
- 用 **golden 测试**固定新行为，让未来“修正”回遗留行为时构建失败。
- 将登记表提供给任何针对遗留系统的**差异测试**，使该分歧被视为*预期*，而不是被标记为回归。

### 采用者注意事项

- 逐函数比较遗留与新实现所得到的是**候选项，而非结论**。每个候选项都必须对照**整条**遗留流水线（而不只是单一函数）判定后，才能称为缺陷——遗留流水线可能已在下游调和了表面上的差异。
- 以**程序化 / 基于 token** 的方式（而非手动）提取遗留函数主体，以免在调查抄写错误时又引入新的抄写错误。

## PR 大小指南

| 大小 | 变更行数 | 审查时间 | 建议 |
|------|----------|----------|------|
| 小 | < 200 | < 30 分钟 | ✅ 理想 |
| 中 | 200-500 | < 1 小时 | ⚠️ 可接受 |
| 大 | > 500 | — | ❌ **应拆分** |

**原则**：多个小 PR > 一个大 PR

## 技术债优先级

| 优先级 | 标准 | 行动 |
|--------|------|------|
| **高** | 阻碍开发、频繁引发缺陷 | 立即处理 |
| **中** | 拖慢开发、增加复杂度 | 排入下一个迭代 |
| **低** | 轻微困扰、影响范围局限 | 视机会处理 |

## 数据库重构安全

### 迁移前检查清单

- [ ] 已完成完整备份
- [ ] 迁移脚本已在预发布（staging）环境测试
- [ ] 已准备回滚脚本
- [ ] 已估算迁移时间
- [ ] 已通知维护时段

### 迁移后检查清单

- [ ] 数据一致性验证
- [ ] 应用功能验证
- [ ] 性能基线比较
- [ ] 在回滚期间保留备份

# 理解階梯：評估案例

> **語言**: [English](../../../../skills/comprehension-ladder/eval-cases.md) | 繁體中文 | [简体中文](../../../zh-CN/skills/comprehension-ladder/eval-cases.md)

**狀態：尚未實跑。** 本檔只有案例與跑法。沒有呼叫過任何模型，也沒有任何讀者作過答。實跑完成之前，不要說本技能讓文字比較好懂。

下面五段原文都是為這次評估寫的。它們不描述任何真實的客戶、人物或系統。

## 實跑會產出什麼

一次實跑產出兩個數字：

1. **前後的答對率。** 讀者看原文時（A 組，「之前」）與看技能產出時（B 組，「之後」），答對題目的比例。
2. **防護違反次數。** 技能的產出破壞 G1、G2 或 G3 的次數。

建議的通過線，實跑前要與負責人談定：B 組比 A 組高至少 10 個百分點，而且防護違反次數為 0。10 個百分點只是起始值，還沒有校準過。

## 跑法

### 1. 產出

每個案例都對原文跑一次技能。要求第 1 階與第 2 階。存下大綱與兩階的產出。若也要測第 3 階，就要求它並存下 HTML 檔。

五個案例使用同一個模型、同樣的設定。記下模型名稱。

### 2. 分讀者

至少用 6 位讀者。讀者可以是人，也可以是模型。人給出的證據比較強。模型是比較便宜的替身。

把讀者分成人數相同的兩組。

| 案例 | 第 1 組讀 | 第 2 組讀 |
|------|-----------|-----------|
| 1 | A（原文） | B（技能產出） |
| 2 | B | A |
| 3 | A | B |
| 4 | B | A |
| 5 | A | B |

每位讀者每個案例只看一次。這樣讀者不會在一組學到答案，再帶到另一組。

B 組的讀者只看技能產出，不看原文。

### 3. 問題

把該案例的題目交給每位讀者。讀者只能依手上拿到的文字作答，不得用任何其他來源。

讀者可以答「文字沒有說」。對標為**未提及**的題目，這是正確答案。

### 4. 評分

依下面的標準答案評分。答案要符合「採計」欄才算對。標為**不確定語氣**的題目，若答案把說法講成確定，即使事實對了也算錯。

答對率 = 答對的題數 ÷ 全部答案數，各組分開算。

### 5. 計算防護違反

對照原文，檢查每一份產出。下列情形，每一項各算一次。

| 防護 | 一次違反是 |
|------|------------|
| G1 `no-new-facts` | 某一項或某一句，說了原文沒說的事。每個案例的「陷阱」清單列出最可能的幾種。 |
| G2 `keep-hedges` | 原文的說法有不確定語氣，產出的那一項卻沒有，或語氣變得更強。每個案例的「不確定用詞清單」列出這些用詞。 |
| G3 `trace-and-gaps` | 某一項沒有「對應原文」、指到的位置不是它所宣稱的位置，或沒有「沒涵蓋」註記。另外：產出沒有「這份大綱沒有收的部分」清單。 |

請第二個人也數同一批產出，再比對兩份計數。不同時，逐項討論，記下最後的計數。

### 6. 回報

填這張表。兩個數字都要有。

| 案例 | A 組答對 | B 組答對 | G1 | G2 | G3 |
|------|----------|----------|----|----|----|
| 1 | / | / | | | |
| 2 | / | / | | | |
| 3 | / | / | | | |
| 4 | / | / | | | |
| 5 | / | / | | | |
| **合計** | **A 組答對率** | **B 組答對率** | | | |

### 實跑規模

說明實跑的規模，讓負責人在開跑前決定模型與預算：

- 產出步驟：5 次技能執行，加 5 次防護檢查。共 10 次模型呼叫。
- 讀者步驟，若讀者是模型：5 個案例 × 2 組 × 每組讀者數。
- 題目很短。最長的輸入是一段原文或一份產出。

模型與預算由負責人決定。這裡不設定。

## 案例 1：搜尋結果過期

**類型**：含多處不確定語氣的事件紀錄。

### 原文

> 昨晚商品目錄匯入之後，搜尋頁約有 3 小時顯示舊的商品名稱。最可能的原因是，匯入之後搜尋索引沒有重建。我們認為匯入工作先結束，重建步驟才排進佇列，但我們還沒有檢查工作紀錄。顧客仍然可以購買那些商品。團隊計畫在星期四，替匯入工作加上重建步驟，前提是紀錄證實了事件的先後順序。沒有人量過有多少顧客看到舊名稱。

### 問題與標準答案

| # | 問題 | 類型 | 採計 |
|---|------|------|------|
| 1 | 搜尋頁顯示舊名稱的時間有多久？ | 事實 | 約 3 小時 |
| 2 | 最可能的原因是什麼？已經確認了嗎？ | 不確定語氣 | 匯入之後索引沒有重建。尚未確認：「最可能」 |
| 3 | 工作紀錄檢查過了嗎？ | 事實 | 沒有。還沒有 |
| 4 | 問題發生期間，顧客還能購買商品嗎？ | 事實 | 能 |
| 5 | 修復計畫在什麼時候？它取決於什麼？ | 事實 | 星期四。取決於紀錄是否證實事件的先後順序 |
| 6 | 有多少顧客看到舊名稱？ | 未提及 | 文字沒有說。沒有人量過 |

### 不確定用詞清單

「約 3 小時」、「最可能」、「我們認為」、「還沒有檢查」、「前提是紀錄證實」、「沒有人量過」。

### 陷阱（原文沒說的事實）

受影響顧客的人數。原因已確認的說法。紀錄顯示了事件先後順序的說法。任何退款、營收或客服單的數字。

## 案例 2：退款核准流程

**類型**：有分支的流程（適合第 2 階）。

### 原文

> 顧客在 App 裡申請退款。系統檢查訂單日期。訂單超過 30 天，系統立刻駁回申請，並向顧客顯示一則訊息。訂單在 30 天以內（含 30 天），系統把申請送給客服人員。客服人員在 2 個工作天內核准或駁回。客服人員核准後，系統把錢退回原付款方式，並寄電子郵件給顧客。超過 NT$5,000 的退款，還需要組長第二次核准。規格沒有說組長要在多久內回覆。

### 問題與標準答案

| # | 問題 | 類型 | 採計 |
|---|------|------|------|
| 1 | 45 天前的訂單申請退款，會怎麼處理？ | 事實 | 立刻駁回。顧客會看到一則訊息 |
| 2 | 剛好 30 天的訂單申請退款，會怎麼處理？ | 事實 | 送給客服人員（「30 天以內（含 30 天）」） |
| 3 | 客服人員有多久可以決定？ | 事實 | 2 個工作天 |
| 4 | 核准之後，錢退到哪裡？ | 事實 | 原付款方式。顧客還會收到電子郵件 |
| 5 | 哪些退款需要第二次核准？由誰核准？ | 事實 | 超過 NT$5,000 的退款。由組長 |
| 6 | 組長要在多久內回覆？ | 未提及 | 文字沒有說 |

### 不確定用詞清單

主張裡沒有不確定用詞。文字明說了一個缺口：「規格沒有說組長要在多久內回覆。」產出必須保留這個缺口。

### 陷阱

組長的時限。訊息的內容。剛好 NT$5,000 的退款規則。檢查顧客歷史紀錄的步驟。

### 預期規模

原文有 7 個 `mechanism` 項目（申請、日期檢查、駁回、分流、客服決定、付款與電子郵件、組長核准），以及 1 個 `uncertainty` 項目（組長缺少時限）。每一階都應該呈現同樣的 8 項，或列出沒有畫的項目。

## 案例 3：重試函式

**類型**：含數字與兩處不確定說法的程式碼解說。

### 原文

> 函式 `fetchWithRetry` 最多呼叫付款 API 4 次。第一次呼叫立刻發生。呼叫失敗後，它會先等一會兒，再做下一次。等待從 200 ms 開始，每次加倍，所以等待時間是 200 ms、400 ms 和 800 ms。它只在網路錯誤與 HTTP 狀態 503 時重試。遇到其他狀態，例如 400，它就停止並回傳錯誤。4 次呼叫全部失敗時，它丟出最後一個錯誤。程式沒有加入隨機抖動，所以許多同時失敗的用戶端可能會同時重試。我們還沒有測試 API 回傳狀態 429 時會發生什麼事。

### 問題與標準答案

| # | 問題 | 類型 | 採計 |
|---|------|------|------|
| 1 | 這個函式最多呼叫幾次？ | 事實 | 4 次 |
| 2 | 呼叫之間的等待時間是多少？ | 事實 | 200 ms、400 ms、800 ms |
| 3 | 哪些失敗會重試？ | 事實 | 網路錯誤與 HTTP 狀態 503 |
| 4 | 遇到狀態 400 會怎樣？ | 事實 | 停止並回傳錯誤 |
| 5 | 程式沒有加入抖動。接下來可能發生什麼？ | 不確定語氣 | 許多同時失敗的用戶端可能會同時重試。這是一種可能，不是必然 |
| 6 | 遇到狀態 429 會怎樣？ | 未提及 | 不知道。還沒有測試過 |

### 不確定用詞清單

「可能會同時重試」、「我們還沒有測試」。

### 陷阱

狀態 429 的行為（重試或不重試）。用戶端確實會同時重試的說法。原文沒有給的等待總時間上限。API 的名稱。

## 案例 4：上傳檔案要存在哪裡

**類型**：三個選項與取捨（適合第 2 階）。

### 原文

> 我們比較了三種儲存使用者上傳檔案的方式。選項 A：把檔案放在應用程式伺服器的磁碟上。它最便宜，也不需要新工具。但伺服器一換，檔案就會遺失，而且兩台伺服器無法共用檔案。選項 B：使用雲端供應商的物件儲存。以目前的量來說，費用約為每月 NT$600。更換伺服器後檔案仍在，任何一台伺服器都能讀取。它需要一次性的存取金鑰設定。選項 C：使用網路檔案共用。伺服器之間可以共用檔案，也不需要改程式。但它多出一台要維護的機器，而且我們認為，在高負載下它會比較慢。我們建議選項 B。我們還沒有測試選項 C 的速度。

### 問題與標準答案

| # | 問題 | 類型 | 採計 |
|---|------|------|------|
| 1 | 文字說哪個選項在更換伺服器後檔案仍在？ | 事實 | 選項 B。（文字說選項 A 不會。對選項 C，文字沒有說。） |
| 2 | 選項 B 的費用是多少？ | 事實 | 以目前的量來說，約每月 NT$600 |
| 3 | 哪個選項不需要改程式？ | 事實 | 選項 C |
| 4 | 團隊建議哪個選項？ | 事實 | 選項 B |
| 5 | 在高負載下，選項 C 比較慢嗎？ | 不確定語氣 | 團隊認為是，但還沒有測試過 |
| 6 | 選項 C 的費用是多少？ | 未提及 | 文字沒有說 |

### 不確定用詞清單

「約 NT$600」、「我們認為它會比較慢」、「我們還沒有測試」。

### 陷阱

選項 A 或選項 C 的費用。選項 C 在更換伺服器後檔案仍在的說法。沒有帶不確定語氣、就說選項 C 比較慢。原文沒有給的建議理由。

## 案例 5：存取紀錄裡的工作階段權杖

**類型**：含未知事項與尚未評等風險的資安發現。

### 原文

> 審查 API 閘道時，我們發現存取紀錄可能含有工作階段權杖。用戶端把權杖放在網址的查詢字串、而不是放在標頭時，權杖就會出現在紀錄裡。行動 App 2.3 版在個人資料畫面這樣做。網頁用戶端使用標頭，不受影響。紀錄保存 90 天，有 12 位工程師可以讀取。我們沒有找到有人使用過被記下的權杖的證據。風險大概是中等，但我們還沒有正式評等。我們提出兩項修改：行動 App 把權杖改放標頭，以及在紀錄中遮蔽查詢字串。我們還不知道有多少使用者在用 App 2.3 版。

### 問題與標準答案

| # | 問題 | 類型 | 採計 |
|---|------|------|------|
| 1 | 權杖什麼時候會出現在紀錄裡？ | 事實 | 用戶端把它放在網址的查詢字串、而不是標頭時 |
| 2 | 哪些用戶端受影響？ | 事實 | 行動 App 2.3 版，在個人資料畫面。網頁用戶端不受影響 |
| 3 | 紀錄保存多久？誰能讀？ | 事實 | 90 天。12 位工程師 |
| 4 | 有沒有人被證實濫用被記下的權杖？ | 不確定語氣 | 沒有找到證據。這不等於「沒有人這樣做」 |
| 5 | 風險有多嚴重？ | 不確定語氣 | 大概是中等。尚未正式評等 |
| 6 | 有多少使用者在用 App 2.3 版？ | 未提及 | 還不知道 |

### 不確定用詞清單

「可能含有」、「沒有找到……證據」、「大概是中等」、「還沒有正式評等」、「還不知道」。

### 陷阱

受影響使用者的人數。沒有任何權杖被濫用的說法。正式的風險等級（例如「高」或「中」）。修復日期。網頁用戶端有風險的說法。

## 實跑之後

- 記下日期、模型名稱、讀者人數，以及誰計算防護違反。
- 把填好的回報表放在本檔旁邊。不要覆寫案例。
- 防護違反次數大於 0 時，先修技能，再去解讀答對率。加了事實或拿掉不確定語氣的產出，可能拉高答對率，卻仍然誤導讀者。
- 某段原文被發現有歧義時，把原文與答案一起修正，再重跑那個案例。
